---
title: Migrating an Agent to Eve 0.30
description: What to change in an imported Agent before upgrading its eve dependency to 0.30.
---

**If you are not upgrading eve, you do not need to do anything.** Every project pins its own eve version, and Agents staying on `0.28.x` or `0.29.x` behave exactly as before. This page is only for a project moving to `0.30.x`.

## What changed

Eve 0.30 redefined `localDev()`. It used to authorize on the request Host, admitting `localhost`, `*.localhost`, `127.0.0.0/8`, and `::1`. It now returns a session only when the process is `eve dev` or `vercel dev`:

```ts
// 0.29 — decided per request, from the Host
localDev(); // accepted a loopback Host

// 0.30 — decided once, from the process
localDev(); // accepts nothing unless EVE_DEV=1 or vercel dev
```

Your Agent runs on Eveland under `eve start`, so after upgrading, `localDev()` admits nothing. If it was the only entry in your `auth` array, every Playground request answers 401.

The framework's default channel also gained `placeholderAuth()`. It raises its helpful "Production auth is not configured" error only when `VERCEL_ENV=production`. Self-hosted Eveland sets no `VERCEL_ENV`, so it returns null, the auth walk falls through, and Eve answers a **bare 401 with `www-authenticate: Bearer` and no explanation**. That is the symptom to expect if you upgrade without changing anything.

**Do not set `EVE_DEV=1` to get the old behavior back.** Eve 0.30 reads that variable in several places besides auth: it routes workflows to the `latest` deployment instead of the pinned one, permits runtime installation of optional engine packages, logs every bash command, and skips registering the sandbox teardown handler for SIGINT/SIGTERM, which leaks sandboxes across restarts.

## Step 1 — choose an auth strategy

Edit `agent/channels/eve.ts`. Pick the line that matches what your Agent needs.

**Use Eveland's platform identity.** Callers are identified by Eveland, and your Agent receives a verified principal:

```ts
import { eveChannel } from "eve/channels/eve";
import { localDev } from "eve/channels/auth";
import { evelandIdentity } from "eveland/auth";

export default eveChannel({
  auth: [evelandIdentity(), localDev()],
});
```

Keep `localDev()` at the end if you also run the Agent locally with `eve dev` — there it still works, because the process really is `eve dev`.

```bash
pnpm add eveland
```

`evelandIdentity()` declines rather than throws when Eveland Identity is unreachable or unconfigured, so anything after it in the array still gets its turn.

**Bring your own authentication.** If you already use Auth.js, Clerk, or anything else, `evelandIdentity()` is optional — replace `placeholderAuth()` with your own `AuthFn` and nothing else changes.

**Accept everyone.** If your Agent never authenticated anyone and you are comfortable with it being open:

```ts
import { none } from "eve/channels/auth";

export default eveChannel({ auth: [none()] });
```

This makes the Agent reachable by anyone who can reach its public host. Use it deliberately.

Remove `vercelOidc()` while you are here. It has always been dead code on Eveland, which issues no Vercel OIDC tokens.

## Step 2 — point Playground authentication at it

If you chose `evelandIdentity()`, open the project's **Playground authentication** settings and switch the method to **Eveland Identity**. The default is still `local-dev`, which sends no credential — with a 0.30 Agent that produces the bare 401 described above.

This switch is per project, so you can migrate one Agent at a time.

## Step 3 — deploy

Refresh your lockfile so the build actually resolves `0.30.6`, then redeploy. A range like `^0.30.0` permits it but does not by itself change what is installed.

After deploying, send one Playground message. A verified caller principal means the migration worked; a bare 401 means the auth array still has no AuthFn that admits Eveland's Playground request.
