---
title: Core Concepts
description: Understand source revisions, releases, deployments, routes, sessions, and usage.
---

Eveland separates authored code, build output, running processes, and public traffic. That separation is what makes previews and safe promotion possible.

## Project lifecycle

```text
Project
  └─ Source Revision        Git commit or Zip snapshot
       └─ Release           immutable build output
            └─ Deployment  running Docker container or systemd unit
                 └─ Route  stable, preview, or named hostname
```

### Source revision

A source revision is the exact input to a build. Git imports preserve the fetched revision; Zip imports preserve the uploaded snapshot. Eveland never edits the imported source when it injects runtime integration code—the prepared release tree is modified instead.

### Release and deployment

A release is an immutable build artifact. A deployment is a running instance of that release. Rebuilding creates a new release and deployment rather than modifying the current production process.

Every deployment records its runtime kind. Lifecycle operations use that recorded owner, so Docker deployments are stopped by Docker and systemd deployments are stopped by systemd.

## Routes and traffic

- A **preview route** belongs to one immutable deployment.
- A **stable route** is mutable and represents the project’s production entry point.
- A **named route** can expose another intentional alias.

A route can select one deployment or split new sessions across two deployments. Weights use 10,000 basis points and must total 10,000.

## Session affinity

New traffic is assigned deterministically. Once Eve returns a `sessionId`, Eveland stores a `SessionBinding` between that session and its deployment. Continuations return to the original deployment even after promotion, rollback, or a traffic weight reaches zero.

This is why a deployment may enter **draining** instead of stopping immediately: it can still own non-terminal sessions.

## Sessions and usage

The observer records sessions independently of Playground. Direct agent requests, schedules, and child sessions can therefore appear in the same session history.

Token accounting uses Eve’s reported `step.completed.data.usage` values:

- input and output tokens
- cache-read and cache-write tokens
- provider or gateway cost, when reported

Missing provider usage is marked as missing rather than estimated. Usage is attributed to the Eve agent or subagent that consumed it.
