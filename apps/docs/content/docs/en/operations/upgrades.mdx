title: Upgrade and rollback
description: Upgrade an exact Eveland release while keeping migrations, component identity, and runtime ownership explicit.
---

Treat an Eveland upgrade as a coordinated product change, not an independent restart of four applications.

For the latest release-specific production procedure, use [Upgrade from 0.14 to 0.15](/docs/operations/upgrade-0-14-to-0-15). The [0.13 to 0.14](/docs/operations/upgrade-0-13-to-0-14), [0.12 to 0.13](/docs/operations/upgrade-0-12-to-0-13), and [0.11 to 0.12](/docs/operations/upgrade-0-11-to-0-12) guides remain available for installations upgrading across several minors, and each must be applied in order.

## Before upgrading

1. Read the target GitHub Release notes and compatibility changes.
2. Back up Postgres and the configured data root using your infrastructure's normal procedures.
3. Confirm every component reports the current exact revision.
4. Check for runtime migrations or instructions that require draining deployments.

## Apply the release

Fetch tags, check out the selected stable tag, install the frozen lockfile, and apply versioned database migrations. Set the same release channel and revision for Web, API, Gateway, and Worker, then restart them from that checkout.

Do not call the upgrade complete until public health, Worker startup identity, and **Settings → About** agree.

## Rollback boundary

Checking out an older tag is safe only when that release remains compatible with every migration already applied. Database migrations are not automatically reversed. Follow the release-specific rollback notes instead of assuming a source rollback is sufficient.

Never flip `EVELAND_RUNTIME` as an upgrade shortcut. Existing Deployments retain their recorded runtime owner and must be deliberately drained before a host runtime migration.
