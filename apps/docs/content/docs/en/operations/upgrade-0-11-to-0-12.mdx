---
title: Upgrade from 0.11 to 0.12
description: Apply the 0.12 database and Identity configuration changes, coordinate the first Worker restart, verify the release, and retain a safe 0.11 rollback path.
---

Eveland 0.12 adds authenticated web-chat identity, durable Eve session reset routing, a reorganized Project workspace, and a searchable Source browser. This guide covers a production upgrade from `v0.11.0` to `v0.12.0`.

## Operational impact

Plan a maintenance window. Four additive migrations must run before the new processes, and the first 0.12 Worker start queues one restart for every live Deployment so each runtime receives the new platform-owned Identity configuration.

The upgrade does not change Project slugs, public Agent endpoints, routes, or existing Session ownership. The former Project **Secrets** URL redirects to **Settings → Environment**. Deployment controls move to **Deployments**, while editable display name and description live under **Settings → General**.

## 1. Back up and inspect 0.11

Back up Postgres and `EVELAND_DATA_DIR` with your normal infrastructure procedure. Record the current tag and revision, confirm API and Gateway health, and wait for important import, build, deployment, or deletion jobs to finish.

Stop the host Worker before changing either checkout so 0.11 cannot claim work while the control plane is being migrated:

```bash
sudo systemctl stop eveland-worker
```

## 2. Add the production Identity configuration

The 0.12 production Compose overlay requires these values in the control-plane `.env`:

```dotenv
EVELAND_IDENTITY_ISSUER=https://api.example.com
EVELAND_IDENTITY_ALLOWED_ORIGINS=https://chat.example.com
```

Add the matching issuer and an Agent-reachable JWKS URL to `/etc/eveland/eveland-worker.env`:

```dotenv
EVELAND_IDENTITY_ISSUER=https://api.example.com
EVELAND_IDENTITY_JWKS_URL=http://127.0.0.1:4000/.well-known/jwks.json
```

`EVELAND_IDENTITY_ISSUER` must be identical on API and Worker. The issuer is the stable public API origin embedded in Caller Tokens; the systemd Worker may inject the private loopback JWKS URL because Agents run on the same host. `EVELAND_IDENTITY_ALLOWED_ORIGINS` accepts comma-separated exact browser origins and never a wildcard.

The Identity API and browser chat must share one schemeful site, normally sibling HTTPS subdomains, because the separate `eveland_identity` cookie uses `SameSite=Lax`. If authenticated chat is not enabled yet, still configure the intended exact same-site origin, but do not create its return target until that origin is deployed.

## 3. Install 0.12 and apply migrations

In the control-plane checkout:

```bash
git fetch --tags origin
git checkout v0.12.0
pnpm install --frozen-lockfile
pnpm --filter @evelandhq/api db:migrate
git rev-parse --short=12 HEAD
```

Put the printed revision in the shared production environment as `EVELAND_REVISION` and keep `EVELAND_RELEASE_CHANNEL=stable`.

The migration command applies:

- `0027_lonely_blue_shield`: Identity providers, realms, grants, return targets, principals, sessions, and signing keys.
- `0028_shocking_black_panther`: the single-enabled-Internal-Provider constraint.
- `0029_sparkling_hammerhead`: continuation-token backfill and the unique SessionBinding routing index required by Eve 0.27.4+ reset.
- `0030_zippy_albert_cleary`: the nullable Project description field.

All four changes are additive. Migration `0029` reads existing Sessions to backfill known continuation tokens; the migration runner records and applies it once. Complete the migration command before API, Gateway, or Worker 0.12 starts.

Update the separate Worker checkout to the same tag and rebuild the vendored sandbox backend:

```bash
cd /opt/eveland
git fetch --tags origin
git checkout v0.12.0
pnpm install --frozen-lockfile
pnpm --filter @evelandhq/sandbox-bwrap build
git rev-parse --short=12 HEAD
```

Set that same revision and `stable` channel in `/etc/eveland/eveland-worker.env`.

## 4. Start the coordinated release

Validate the merged Compose configuration, start the unprivileged control plane, and only then start the host Worker:

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml config
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d
sudo systemctl start eveland-worker
sudo journalctl -u eveland-worker -n 100 --no-pager
```

On its first 0.12 start, the Worker persists an Identity configuration fingerprint and queues one targeted `restart_deployment` job for every `running` or `draining` Deployment. This is expected. Watch the Jobs and Worker logs until the queue drains, and investigate any failed restart before ending the maintenance window. A later Worker restart with unchanged Identity configuration does not repeat this work.

## 5. Verify 0.12

Complete all of these checks:

1. API and Gateway `/health` return `version: 0.12.0`, `channel: stable`, and the same revision.
2. **Settings → About** reports matching Web, API, Gateway, and Worker configuration without missing Identity values.
3. Worker startup logs show the same build identity and the Deployment restart queue finishes without failures.
4. Existing public Agent create, continue, cancel, and stream traffic still reaches the pinned Deployment.
5. Project **Overview**, **Deployments**, **Source**, and **Settings → Environment** load as expected.
6. If Identity is enabled, the public `/.well-known/jwks.json` endpoint returns an ES256 key and the exact chat return origin works.

Eveland 0.12 still supports imported Agents on Eve `0.25.x`, `0.26.x`, and `0.27.x`; a platform upgrade does not force an immediate Agent dependency change. To use durable reset or remote principal forwarding, refresh the Agent lockfile to Eve `0.27.6` and redeploy it. Remote principal forwarding remains opt-in on both Agents and requires a precise `trustedForwarders` predicate.

## Roll back to 0.11

Stop the Worker, restore both checkouts to `v0.11.0`, reinstall the frozen lockfile, rebuild `@evelandhq/sandbox-bwrap`, set the 0.11 revision, restart the Compose services, and then restart the Worker.

Do not reverse migrations `0027`–`0030`. Their new tables, indexes, and nullable columns can remain in place while 0.11 ignores them; deleting them would destroy 0.12 Identity configuration and continuation-token routing state needed for a later retry.

After rollback, authenticated web-chat Identity, durable reset routing, and the 0.12 navigation and Source browser are unavailable. Standard 0.11 Agent traffic continues to use the pre-existing Session binding path. Re-run this guide from the migration step when attempting 0.12 again.

For the invariant upgrade procedure, see [Upgrade and rollback](/docs/operations/upgrades). For Agent dependency details, see [Eve compatibility](/docs/reference/eve-compatibility).
