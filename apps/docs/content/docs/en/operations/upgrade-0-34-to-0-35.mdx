---
title: Upgrade from 0.34 to 0.35
description: Migrate the shared Workflow World to 0.9, hand shared storage maintenance to the single-owner Dispatcher, and roll out bounded Deployment and Sandbox execution.
---

Eveland 0.35 makes durable workflow storage and Agent command execution bounded by default. It upgrades the shared `@evelandhq/workflow-world` from `0.6.0` to `0.9.0`, moves shared-world maintenance from the Worker to the Dispatcher, classifies scheduled workflow graphs for outcome-aware retention, and adds cgroup and Sandbox limits to both runtime adapters. This guide covers a production upgrade from `v0.34.0` to `v0.35.0`.

## Operational impact

Plan a maintenance window for the host Worker and Workflow Dispatcher. Public traffic can keep reaching already-running Agents while those services are stopped, but cold activation, durable workflow dispatch, schedules, imports, builds, and deployment operations pause until they return.

**There are no Eveland control-plane database migrations in this release.** Continue to run `pnpm --filter @evelandhq/api db:migrate`; it should be a no-op and confirms the control-plane database is current.

Installations using the shared Workflow World have a separate migration boundary. Worker or Dispatcher startup automatically applies package migrations `0007` through `0012` under a PostgreSQL advisory lock. Those migrations add storage-v2 metadata and checkpoints, retention classes and deadlines, dead-letter recovery indexes, outcome-specific scheduled retention, and materialized workflow lineage. They also backfill existing terminal runs as `interactive` and assign retention roots. No separate `workflow-world-setup` command is required.

The first Dispatcher start with maintenance enabled immediately performs a bounded pass. Existing terminal shared-world runs can therefore become eligible at once: non-EOF stream data older than 24 hours and interactive workflow graphs older than 30 days may be deleted. EOF markers remain. Take a backup of the shared Workflow World before starting 0.35, even if the main Eveland database is backed up separately.

If `EVELAND_WORKFLOW_WORLD_URL` is unset and no Project uses the shared World, the shared migration, Dispatcher, and shared-retention sections below do not apply. The Deployment and Sandbox limits still apply.

### Behavior changes to expect

- **The Workflow Dispatcher is single-instance per shared database.** It holds a lifecycle advisory lock, reclaims stranded Graphile worker locks only from active runs' exact per-run queues, re-enqueues them, and starts its worker pool last. A second 0.35 Dispatcher fails closed. Because the 0.34 Dispatcher did not participate in this ownership lock, it must be stopped before the 0.35 process starts.
- **Dispatcher connection accounting is stricter.** One pool connection belongs to lifecycle ownership and one to Graphile `LISTEN`; therefore `WORKFLOW_DISPATCHER_CONCURRENCY` must be at most `WORKFLOW_DISPATCHER_POOL_SIZE - 2`. With the default pool size of 10, the default concurrency is 8. An explicitly configured value of 9 that worked in 0.34 must be reduced.
- **Shared storage has a physical bound and an expiry policy.** New readers understand legacy rows and storage-v2 blocks. The Dispatcher packs terminal streams, expires non-EOF stream data by deadline, deletes expired workflow graphs, and reclaims empty per-run Graphile queues. `EVELAND_WORKFLOW_SWEEP_*` now controls only legacy per-Project worlds; `EVELAND_WORKFLOW_SHARED_SWEEP_MAX_BATCHES` is obsolete.
- **Scheduled graphs retain failures longer than successes.** A newly built 0.35 Scheduler Channel marks newly created Markdown and handler Sessions as `scheduled`; descendants inherit the root class through Workflow SDK lineage. Completed scheduled graphs keep stream data for 15 minutes and graph detail for 24 hours; failed graphs keep them for 1 hour and 7 days; cancelled graphs keep them for 1 hour and 3 days. Interactive graphs keep stream data for 24 hours and graph detail for 30 days. Persistent graphs do not expire automatically. Delivery into an existing Session keeps that Session's stored root class.
- **Every Deployment gets cgroup limits.** Docker now applies the same memory and CPU settings as systemd, and both adapters add a task limit. Defaults are 2 GiB, 200% CPU, and 512 processes/threads per Deployment. Docker also runs an init process so orphaned bwrap helpers are reaped instead of becoming permanent zombies.
- **Sandbox commands are bounded.** One injected bwrap `run()` has a 10-minute wall-clock limit, a compute generation admits at most 64 live Sandbox commands, and one `run()` retains at most 16 MiB of combined stdout/stderr by default. Timeout or caller abort terminates the complete bwrap process group. Authored long-running services must use `spawn()`.
- **Authored Sandbox lifecycle now runs.** A newly built Release still receives Eveland's managed backend, but preserves the Project's `bootstrap()`, `onSession()`, `description`, `revalidationKey`, relative imports, and `sandbox/workspace/**` seeds. Review those hooks before redeploying a Project that was relying on 0.34 accidentally discarding them.

## 1. Back up and inventory 0.34

Back up all of the following with the normal infrastructure procedure:

1. the Eveland control-plane Postgres database;
2. the database named by `EVELAND_WORKFLOW_WORLD_URL`, when configured;
3. `EVELAND_DATA_DIR`.

Record the current tag and revision. Wait for important imports, builds, deploys, deletes, schedules, and interactive workflow turns to settle. Review only the non-secret workflow settings in the two host environment files:

```bash
sudo grep -E '^(EVELAND_WORKFLOW_WORLD_ROLLOUT|EVELAND_WORKFLOW_RUNNER|EVELAND_WORKFLOW_STREAM_COMPACTION)=' /etc/eveland/eveland-worker.env
sudo grep -E '^(WORKFLOW_DISPATCHER_POOL_SIZE|WORKFLOW_DISPATCHER_CONCURRENCY|WORKFLOW_DISPATCHER_MAINTENANCE_INTERVAL_MS|EVELAND_WORKFLOW_STREAM_COMPACTION)=' /etc/eveland/eveland-workflow-dispatcher.env
```

Stop the old Dispatcher first, then the Worker:

```bash
sudo systemctl stop eveland-workflow-dispatcher
sudo systemctl stop eveland-worker
```

Do not start an old Dispatcher elsewhere while upgrading. The new ownership lock cannot fence a 0.34 binary that never takes it.

## 2. Set the 0.35 limits and rollout controls

Use [`infra/systemd/eveland-worker.env.example`](https://github.com/evelandhq/eveland/blob/main/infra/systemd/eveland-worker.env.example) and [`infra/systemd/eveland-workflow-dispatcher.env.example`](https://github.com/evelandhq/eveland/blob/main/infra/systemd/eveland-workflow-dispatcher.env.example) as checklists without overwriting your secrets or topology-specific URLs.

Choose explicit Worker limits. Keeping the defaults is valid, but writing them into production configuration makes the boundary deliberate:

```bash
EVELAND_MEMORY_MAX=2G
EVELAND_CPU_QUOTA=200%
EVELAND_TASKS_MAX=512
EVELAND_SANDBOX_RUN_TIMEOUT_MS=600000
EVELAND_SANDBOX_MAX_CONCURRENT_PROCESSES=64
EVELAND_SANDBOX_MAX_OUTPUT_BYTES=16777216
```

Review Agents before increasing any value. In particular, do not turn `run()` into a long-lived service by raising its deadline indefinitely; use `spawn()` for an authored process whose lifecycle is intentionally tied to the Session.

For the Dispatcher:

- remove `EVELAND_WORKFLOW_SHARED_SWEEP_MAX_BATCHES` if it is present;
- leave the legacy `EVELAND_WORKFLOW_SWEEP_INTERVAL_MS`, `EVELAND_WORKFLOW_STREAM_RETENTION_MS`, and `EVELAND_WORKFLOW_SWEEP_BATCH_SIZE` on the Worker only;
- set `WORKFLOW_DISPATCHER_CONCURRENCY` no higher than `WORKFLOW_DISPATCHER_POOL_SIZE - 2`;
- add the `WORKFLOW_DISPATCHER_MAINTENANCE_*` controls from the example file, or accept their bounded defaults;
- set `EVELAND_WORKFLOW_STREAM_COMPACTION` to the same value on Worker and Dispatcher.

For the safest first boot of an existing shared World, temporarily use:

```bash
# Dispatcher: migrate and dispatch, but do not delete or repack on first boot.
WORKFLOW_DISPATCHER_MAINTENANCE_INTERVAL_MS=0

# Worker and Dispatcher: keep the same value; on is the normal setting.
EVELAND_WORKFLOW_STREAM_COMPACTION=on
```

Pausing maintenance is important when retained Sessions still route to 0.34-built Deployments: their bundled 0.6 reader does not understand a v2 physical block, while 0.35 readers accept both formats. `EVELAND_WORKFLOW_STREAM_COMPACTION=off` is not a migration switch: it disables snapshot stripping, but maintenance would still pack physical v2 blocks. Leave maintenance at `0` until no retained Session or active shared-world run needs a 0.34-built Deployment, or until you deliberately accept that those old Sessions can no longer replay through their original Deployment.

If this is a new or empty shared World, or all relevant Deployments were already rebuilt with a mixed-format reader, use the normal values immediately:

```bash
WORKFLOW_DISPATCHER_MAINTENANCE_INTERVAL_MS=60000
EVELAND_WORKFLOW_STREAM_COMPACTION=on
```

## 3. Install 0.35

In the control-plane checkout:

```bash
git fetch --tags origin
git checkout v0.35.0
pnpm install --frozen-lockfile
pnpm --filter @evelandhq/api db:migrate
git rev-parse --short=12 HEAD
```

Put the printed revision in the shared production environment as `EVELAND_REVISION` and keep `EVELAND_RELEASE_CHANNEL=stable`.

Update the host checkout used by both Worker and Dispatcher:

```bash
cd /opt/eveland
git fetch --tags origin
git checkout v0.35.0
pnpm install --frozen-lockfile
git rev-parse --short=12 HEAD
```

Set the same revision and channel in both `/etc/eveland/eveland-worker.env` and `/etc/eveland/eveland-workflow-dispatcher.env`.

There is no `@evelandhq/sandbox-bwrap` build step. Version `0.2.0` ships prebuilt from npm and the frozen lockfile selects the tested artifact.

## 4. Start in migration order

Validate and start the control plane first so the Dispatcher's activation health gate has a live API:

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml config
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d
```

Start Worker next. It applies shared-world migrations before accepting jobs or starting a Deployment:

```bash
sudo systemctl start eveland-worker
sudo journalctl -u eveland-worker -n 150 --no-pager
```

When a shared World is configured, wait for `Shared workflow-world database schema is ready.` followed by the Worker ready line. Then start exactly one Dispatcher:

```bash
sudo systemctl start eveland-workflow-dispatcher
sudo journalctl -u eveland-workflow-dispatcher -n 150 --no-pager
```

Do not proceed until it prints `workflow-dispatcher: ready`. `Another workflow dispatcher already owns this database` means another 0.35 generation is active and must be located; it is not a reason to add another replica or clear every Graphile lock.

## 5. Verify 0.35

Complete all applicable checks:

1. API and Gateway `/health` return `version: 0.35.0`, `channel: stable`, and the same revision.
2. **Settings → About** reports matching Web, API, Gateway, and Worker build identity and shows the intended Worker limits.
3. Worker logs report the shared schema ready, and only one Dispatcher reports ready.
4. On the shared database, the migration registry contains `0007` through `0012`:

   ```sql
   select name
   from workflow.eveland_migrations
   where name >= '0007'
   order by name;
   ```

5. Run a normal Playground turn and a Schedule. Confirm the Session timeline, usage, ScheduleRun, and final response remain visible in Eveland's read models.
6. Deploy a canary Project. Confirm its build log says the authored Sandbox lifecycle was preserved when it declares one, and exercise one short Sandbox `run()`.
7. Restart or cold-activate a canary Deployment and inspect its runtime boundary. For systemd, `systemctl show <deployment-unit> -p MemoryMax -p CPUQuotaPerSecUSec -p TasksMax` should reflect the configured values; Docker should show matching memory, CPU, and PID limits.
8. If maintenance is enabled, confirm `workflow_dispatcher.storage_maintenance` reports block, stream, and run roles without errors. A batch limit means bounded backlog remains for later passes, not that an unbounded cleanup should be run manually.

## 6. Enable bounded maintenance after the staged boot

If the first boot used `WORKFLOW_DISPATCHER_MAINTENANCE_INTERVAL_MS=0`, confirm the shared-world backup is usable and that the retention windows match your operational expectations. Then set it to `60000` and restart only the Dispatcher:

```bash
sudo systemctl restart eveland-workflow-dispatcher
sudo journalctl -u eveland-workflow-dispatcher -n 150 --no-pager
```

The first maintenance pass runs immediately, repacks eligible terminal streams, and may delete already-expired data. Do not run `VACUUM FULL` as part of this upgrade; ordinary deletes make pages reusable and the database file need not shrink immediately.

Keep `EVELAND_WORKFLOW_STREAM_COMPACTION=on` in normal operation. If stream-shape diagnosis requires the emergency `off` setting, apply it to both Worker and Dispatcher; it changes snapshot stripping, not storage-v2 reader compatibility or the maintenance schedule. Restart Worker and Dispatcher so they agree, then restart or redeploy 0.35-built Deployments that should receive the changed write policy.

## Agent redeployment boundary

The platform upgrade does not mutate an immutable Release. Existing Agents keep their bundled `workflow-world@0.6.0` and `sandbox-bwrap@0.1.1` until a new Release is built under 0.35.

Redeploy deliberately to pick up:

- the mixed-format shared-world reader, storage-v2 writer, and retention lineage;
- scheduled root classification in the injected Scheduler Channel;
- complete process-group termination plus command concurrency/output limits from `sandbox-bwrap@0.2.0`;
- preservation of authored Sandbox lifecycle and metadata.

Before redeploying, replace any intentionally long-running `run()` call with `spawn()` and review `bootstrap()` or `onSession()` for effects that 0.34 had accidentally suppressed. Cgroup limits apply the next time a Deployment process is created; the injected Sandbox and Scheduler changes require a new Release.

No Agent source migration or `eveland` SDK upgrade is otherwise required by 0.35.

## Roll back to 0.34

If the installation never configured a shared Workflow World, there are no database changes to undo: stop Dispatcher and Worker, check out `v0.34.0` in both locations, reinstall the frozen lockfile, restore the previous revisions and environment, start Compose, then start Worker.

For an installation using the shared World, **restoring its pre-upgrade database backup is the supported complete rollback**. The package migrations are additive, but 0.34 readers cannot decode repacked storage-v2 rows, and maintenance can irreversibly delete expired non-EOF stream data and workflow graphs. A source checkout cannot reconstruct either.

Stop Dispatcher first, then Worker and the 0.35 control-plane services. Restore the shared-world database to the pre-upgrade point, restore the control-plane database and `EVELAND_DATA_DIR` too if your backup procedure requires one matched point, check out `v0.34.0` in both checkouts, reinstall the frozen lockfile, restore the previous environment and revision, start Compose, start Worker, and start the single 0.34 Dispatcher last.

The restore discards shared workflow activity after the backup. Do not start a 0.34 Dispatcher against the shared database while a 0.35 Dispatcher still holds ownership or while the restore is in progress.
