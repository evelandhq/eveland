---
title: Upgrade from 0.14 to 0.15
description: Apply the 0.15 migrations that make a Deployment's loopback port and its Session event order database-enforced, set NODE_ENV explicitly so development fallback secrets stop applying, and understand why 0.14 cannot run against a 0.15 database.
---

Eveland 0.15 closes a cross-project isolation defect: two Deployments could be assigned the same loopback port, and a request routed to one Project's Agent was then answered by another Project's Agent. The listening port becomes a property of the live RuntimeInstance with a database-enforced reservation, readiness verifies that the deployment's own process holds the socket, and jobs serialize per Project. The same release makes Session event ordering a database invariant, hardens several credential boundaries, and adds indexes to the hot read paths. This guide covers a production upgrade from `v0.14.0` to `v0.15.0`.

## Operational impact

Plan a maintenance window. Four database migrations must run before any 0.15 process starts, two of them rewrite existing rows, and `NODE_ENV` becomes load-bearing for secret resolution.

Four consequences are not undone by checking out 0.14 again:

- Migration `0039` adds a unique index on `(session_id, index)` in `session_events`. The 0.14 control plane re-points events during a Session merge without renumbering them, so **every merge fails** against a migrated database, and its `count(*)`-based event numbering can violate the constraint under concurrent ingest.
- Migration `0037` adds a unique index over the live RuntimeInstance ports. 0.14 always writes `endpointPort = deployments.host_port`, so once 0.15 has reallocated any Deployment onto a different port, a 0.14 activation can collide with a live instance and fail.
- Migration `0037` also marks duplicate live RuntimeInstances `failed` before it can build that index. On an installation that hit the port collision, those rows are corrected in place.
- Migration `0039` renumbers `session_events.index` for any Session that already contains a duplicate, rebuilding order from `(event_at, created_at, id)`. Those orderings were already ambiguous, but the stored values change.

Agents keep serving traffic throughout the upgrade and no redeploy is required. Sessions, usage, and existing routes are preserved.

The upgrade does not change Project IDs, slugs, Stable or Preview endpoints, route weights, or Deployment runtime ownership. The verified Eve compatibility window is unchanged: imported Agents on `0.25.x`, `0.26.x`, and `0.27.x` remain accepted, verified through `0.27.8`.

### Behavior changes to expect

- **A Deployment's loopback port is no longer fixed.** `deployments.host_port` becomes a first-deploy preference; the authoritative endpoint is the live RuntimeInstance's `endpointPort`. Gateway and the internal activation route already read it. Any external monitoring that probes a Deployment's port directly must resolve the instance endpoint instead. Raw Agent ports remain private loopback upstreams, never product URLs.
- **Jobs serialize per Project.** A queued job waits until that Project's running job finishes, fails, or is recovered as stale. Different Projects are unaffected. Two deploys queued against the same Project now run one after the other rather than concurrently.
- **A crash-looping unit gives up.** systemd Deployment units get `StartLimitIntervalSec=60` and `StartLimitBurst=5`, so a Deployment that cannot come up settles in `failed` instead of restarting indefinitely.
- **Processes of stopped Deployments are reaped, not adopted.** The orphan sweep previously adopted any surviving non-archived Deployment's process back into the runtime lifecycle. It now does that only while the Deployment is `running` or `draining`; a process belonging to a `stopped`, `failed`, or `archived` Deployment is stopped after the grace period.
- **Only three Better Auth endpoints are publicly routable**: `sign-in/email`, `sign-out`, and `get-session`. Everything else returns 404, including `change-password` — password changes go through Eveland's own `/profile/password`, which always revokes other sessions.
- **Promote reports precise status codes.** Promoting an unknown Deployment now returns 404 and a non-running one 409, where both previously returned 500. A Gateway cache invalidation failure after a committed promote no longer fails the request; the route change stands and Gateway converges at its cache TTL.
- **Zip uploads are capped and stricter.** `POST /projects` and `POST /source-preflights` reject archives above `EVELAND_MAX_UPLOAD_BYTES` (default 100 MiB) with 413, and archives containing symbolic links with 400.
- **On the Docker runtime, decrypted Deployment secrets move off the process argv** into a root-owned `0600` file under `<EVELAND_DATA_DIR>/deployment-env/`, matching what the systemd runtime already did. The file is deleted when the container stops.

## 1. Back up and inspect 0.14

Back up Postgres and `EVELAND_DATA_DIR` with your normal infrastructure procedure. This backup is the only supported rollback path — see the rollback section below. Record the current tag and revision, confirm API and Gateway health, and wait for important import, build, deployment, schedule, or deletion jobs to finish.

Stop the host Worker before changing either checkout:

```bash
sudo systemctl stop eveland-worker
```

If this installation was affected by the port collision, take the opportunity to inspect it before migrating. This lists Deployments sharing a port and the units actually holding those ports:

```bash
psql "$DATABASE_URL" -c "
  select host_port, count(*), array_agg(project_id || '/' || id)
  from deployments where status <> 'archived'
  group by host_port having count(*) > 1;"
sudo ss -ltnp '( sport >= :41000 and sport <= :41100 )'
systemctl list-units 'eveland-*' --no-pager
```

Migration `0037` resolves the database side of this. Any surviving host process whose Deployment is already `stopped` or `archived` is stopped by the 0.15 orphan sweep after its grace period.

## 2. Set NODE_ENV explicitly

0.15 no longer treats an unset `NODE_ENV` as "not production". The publicly known `eveland-dev-*` fallback secrets — the Gateway internal service token, the Gateway affinity secret, and the scheduler runtime and dispatch secrets — now apply **only** under an explicit `NODE_ENV=development` or `NODE_ENV=test`. Anything else, including unset, fails closed and the process refuses to start without the real secret.

The documented production topology already satisfies this: `docker-compose.prod.yml` sets `NODE_ENV=production` on each service command, and `infra/systemd/eveland-worker.env.example` sets it for the host Worker. Confirm your actual files agree, because a host that omitted it was silently running on the repository's published dev secrets:

```bash
grep -n NODE_ENV /etc/eveland/eveland-worker.env
docker compose -f docker-compose.yml -f docker-compose.prod.yml config | grep -n "NODE_ENV"
```

If either is missing, set `NODE_ENV=production` and configure the real secrets before starting 0.15. Treat any secret that was previously served from a dev fallback as compromised and rotate it: `EVELAND_GATEWAY_SERVICE_TOKEN`, `EVELAND_GATEWAY_AFFINITY_SECRET`, `EVELAND_SCHEDULER_RUNTIME_SECRET`, and `EVELAND_SCHEDULER_DISPATCH_SECRET` must each be a long random value, kept identical across the components that share them and independent of one another.

## 3. Confirm the host prerequisites

Worker startup preflight now also requires `ss` and `ps`. Readiness verifies that the listening socket on a Deployment's port belongs to that Deployment's own unit — `ss` finds the listener's pid and `ps -o unit=` maps it back — so a foreign process holding the port fails activation loudly instead of being adopted as healthy. Both commands ship in Ubuntu's base image; confirm rather than assume:

```bash
command -v ss && command -v ps
# if absent: sudo apt-get install -y iproute2 procps
```

No other host prerequisite changes in this release.

## 4. Install 0.15 and apply migrations

In the control-plane checkout:

```bash
git fetch --tags origin
git checkout v0.15.0
pnpm install --frozen-lockfile
pnpm --filter @evelandhq/api db:migrate
git rev-parse --short=12 HEAD
```

Put the printed revision in the shared production environment as `EVELAND_REVISION` and keep `EVELAND_RELEASE_CHANNEL=stable`.

The migration command applies:

- `0036_omniscient_molten_man`: adds `jobs.sequence`, a generated identity column used as a FIFO tiebreaker. `created_at` has finite resolution, so jobs enqueued in the same instant previously claimed in plan-dependent order.
- `0037_black_cerebro`: marks duplicate live RuntimeInstances `failed` — keeping the newest claimant per port — then creates a unique index on `endpoint_port` across the `starting`, `ready`, and `draining` statuses.
- `0038_foamy_tomorrow_man`: creates indexes on `sessions (project_id, eve_session_id)`, `session_nodes (root_session_id, created_at)`, `logs (project_id, created_at)`, and three on `jobs`, two of which are partial indexes over non-terminal rows.
- `0039_far_maria_hill`: renumbers `session_events.index` for Sessions that contain a duplicate, then creates a unique index on `(session_id, index)`.

Complete the migration command before API, Gateway, or Worker 0.15 starts.

`0038` and `0039` build indexes with a plain `CREATE INDEX`, which holds a write lock on each table for the duration, and `0039` additionally rewrites rows in affected Sessions. On an installation with a large `logs`, `sessions`, or `session_events` history this is the slowest part of the upgrade. Run it inside the maintenance window, or build those indexes by hand with `CREATE INDEX CONCURRENTLY` beforehand so the migration finds them already present.

Update the separate Worker checkout to the same tag and rebuild the vendored sandbox backend:

```bash
cd /opt/eveland
git fetch --tags origin
git checkout v0.15.0
pnpm install --frozen-lockfile
pnpm --filter @evelandhq/sandbox-bwrap build
git rev-parse --short=12 HEAD
```

Set the same revision and `stable` channel in `/etc/eveland/eveland-worker.env`.

## 5. Start the coordinated release

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml config
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d
sudo systemctl start eveland-worker
sudo journalctl -u eveland-worker -n 100 --no-pager
```

Watch the first Worker ticks. Preflight failures name the missing prerequisite directly, and the orphan sweep logs each process it stops, including ones left behind by Deployments the control plane had already stopped.

## 6. Verify 0.15

Complete all of these checks:

1. API and Gateway `/health` return `version: 0.15.0`, `channel: stable`, and the same revision.
2. **Settings → About** reports matching Web, API, Gateway, and Worker build identity.
3. Every port in the Deployment range has exactly one listener, and each belongs to the unit for the Deployment that claims it:

   ```bash
   sudo ss -ltnp '( sport >= :41000 and sport <= :41100 )'
   ```

4. No live RuntimeInstance shares a port. This must return no rows:

   ```bash
   psql "$DATABASE_URL" -c "
     select endpoint_port, count(*) from runtime_instances
     where status in ('starting','ready','draining') and endpoint_port is not null
     group by endpoint_port having count(*) > 1;"
   ```

5. Wake a scale-to-zero Deployment through its public URL and confirm the reply comes from that Project's Agent. This is the defect the release exists to fix, so verify it on a Project that previously shared a port if you had one.
6. Deploy a Project and confirm the new Deployment reaches `running`, then promote it and confirm the stable route moves and returns 200.
7. Run one Playground turn and confirm the Session, its nodes, events, and provider-reported usage all appear.
8. **Settings → Instance health** shows a fresh Worker heartbeat and host capacity sample.
9. Sign out and back in through the control panel to confirm the narrowed Better Auth surface still serves the normal login path.

## Roll back to 0.14

**Restoring the pre-upgrade database backup is the only supported rollback.** Do not point 0.14 processes at a database that has applied `0037` and `0039`: 0.14 re-points Session events during a merge without renumbering them and violates the `(session_id, index)` unique index, and its activation writes `endpointPort = deployments.host_port`, which can collide with a live instance running on a reallocated port.

To roll back, stop the Worker and all 0.15 control-plane services, restore the pre-upgrade Postgres backup, restore `EVELAND_DATA_DIR` if your backup procedure requires a matched database and filesystem point, check out `v0.14.0` in both locations, reinstall the frozen lockfile, rebuild `@evelandhq/sandbox-bwrap`, restore the previous revision, then start Compose and start the Worker last.

The restore discards database changes made after the backup, including new Sessions, Jobs, and route changes. It also restores the pre-0.15 port assignments, so confirm no orphaned 0.15 process is still holding a port before starting the Worker:

```bash
systemctl list-units 'eveland-*' --no-pager
sudo ss -ltnp '( sport >= :41000 and sport <= :41100 )'
```

Keep `NODE_ENV` set after a rollback. 0.14 accepts an unset value, but leaving it unset silently reinstates the published dev fallback secrets.

## Agent-side change

The published `eveland` SDK gains an optional Realm allowlist. Eveland's identity broker authenticates callers but does not decide which Realm may reach which Agent, so a Caller Token minted for any enabled Realm verifies in every Agent by default. An Agent that serves a specific audience can now say so:

```ts
evelandIdentity({ allowedRealms: ["irlm_staff"] });
```

The allowlist also reads `EVELAND_ALLOWED_REALM_IDS` (comma-separated). Leaving both unset keeps the existing accept-any-Realm behavior, so no deployed Agent changes behavior on upgrade.

The same release makes the `name` attribute optional. Eveland omits that claim when the upstream identity provider supplies no display name, and the SDK previously rejected such tokens — users of those providers signed in successfully and then had every Agent request rejected as unauthenticated. Treat both `name` and `email` as optional when reading the principal's attributes.
