---
title: Deploy an Eve Project
description: Import source, configure secrets, build a preview, and promote it safely.
---

Eveland deploys ordinary Eve projects. Keep agent instructions, tools, skills, channels, connections, subagents, sandboxes, and schedules in their standard Eve filesystem locations.

Until Eve publishes a stable product compatibility contract, Eveland supports a sliding two-minor window: the latest fully verified Eve minor and the one immediately before it. The current window is `0.24.x` and `0.25.x`, verified at `0.24.6` and `0.25.1`. A newly published minor enters the window only after source review and the full compatibility matrix pass; versions and broad ranges outside the window fail closed.

## 1. Import source

Use either:

- a Git repository URL, or
- a Zip archive containing the project.

Eveland extracts a source revision, validates the project shape, and presents a read-only source view. A Git project can later use **Sync & deploy** to fetch a new revision. Zip revisions remain fixed snapshots.

## 2. Configure secrets

Add required provider keys and application environment variables from the **Secrets** page. Values are encrypted at rest, injected only at runtime, and never displayed again.

Secrets do not belong in:

- the Git repository or uploaded Zip
- build logs
- source browsing
- session timelines

Administrators can also create encrypted, revisioned **Secret profiles** in System settings and bind them to a Project or one Deployment. Runtime precedence is Project Secret, Project Profile, Deployment Profile, then Eveland-reserved values. Effective runtime changes queue targeted restarts; profile values remain outside source and releases.

## 3. Build and deploy

**Build & Deploy** creates a prepared release tree, installs dependencies, runs `eve build`, allocates a private loopback port, starts the deployment, and waits for the Eve health endpoint.

In development, the Worker uses Docker by default. In a production Linux installation, the host Worker uses systemd and an unprivileged application user.

## 4. Test the preview

Every successful build starts beside the current production deployment. Use the immutable preview hostname and Playground to check:

- the final response and streaming behavior
- tool and subagent events
- runtime stdout/stderr
- token usage and completeness
- required connections and schedules

Raw dynamic ports are private implementation details. Use the preview hostname instead.

## 5. Promote or roll back

Promoting changes the stable route atomically; it does not rebuild the release. Existing sessions stay bound to their original deployment while new sessions follow the updated route.

Rollback is the same routing operation in reverse: select a retained healthy deployment and move the stable route back to it.

## Retention rules

Eveland keeps at least the newest three release artifacts. A release cannot be archived while it is selected by a mutable route or while its deployment owns an active session binding.
