---
title: 从 0.11 升级到 0.12
description: 应用 0.12 的数据库与 Identity 配置变更，协调 Worker 首次重启，完成发布验收，并保留安全的 0.11 回滚路径。
---

Eveland 0.12 新增带认证的 Web Chat Identity、Eve Durable Session Reset 路由、重新组织的 Project Workspace，以及可搜索的 Source Browser。本文说明如何将生产环境从 `v0.11.0` 升级到 `v0.12.0`。

## 运维影响

请安排维护窗口。四个 Additive Migration 必须先于新进程执行；0.12 Worker 第一次启动时，还会为每个在线 Deployment 排入一次重启，让 Runtime 获得新的平台保留 Identity 配置。

本次升级不会改变 Project Slug、公开 Agent Endpoint、Route 或已有 Session Ownership。原 Project **Secrets** 地址会重定向到 **Settings → Environment**；Deployment 操作移至 **Deployments**；可编辑的 Display Name 与 Description 位于 **Settings → General**。

## 1. 备份并检查 0.11

按照现有基础设施流程备份 Postgres 与 `EVELAND_DATA_DIR`。记录当前 Tag 和 Revision，确认 API 与 Gateway Health 正常，并等待重要的 Import、Build、Deployment 或 Delete Job 完成。

修改两个 Checkout 前先停止宿主机 Worker，避免 0.11 在控制面迁移期间继续领取任务：

```bash
sudo systemctl stop eveland-worker
```

## 2. 增加生产 Identity 配置

0.12 的生产 Compose Overlay 要求在控制面 `.env` 中提供：

```dotenv
EVELAND_IDENTITY_ISSUER=https://api.example.com
EVELAND_IDENTITY_ALLOWED_ORIGINS=https://chat.example.com
```

在 `/etc/eveland/eveland-worker.env` 中增加相同 Issuer 与 Agent 可访问的 JWKS URL：

```dotenv
EVELAND_IDENTITY_ISSUER=https://api.example.com
EVELAND_IDENTITY_JWKS_URL=http://127.0.0.1:4000/.well-known/jwks.json
```

API 与 Worker 的 `EVELAND_IDENTITY_ISSUER` 必须完全相同。Issuer 是写入 Caller Token 的稳定公开 API Origin；systemd Worker 可以向 Agent 注入私有 Loopback JWKS URL，因为 Agent 运行在同一宿主机。`EVELAND_IDENTITY_ALLOWED_ORIGINS` 只接受逗号分隔的精确 Browser Origin，不能使用通配符。

Identity API 与 Browser Chat 必须位于同一个 Schemeful Site，通常是同一主域下的 HTTPS 子域，因为独立的 `eveland_identity` Cookie 使用 `SameSite=Lax`。如果尚未启用带认证 Chat，也应先配置计划使用的精确同站 Origin；该 Origin 上线前不要创建 Return Target。

## 3. 安装 0.12 并执行 Migration

在控制面 Checkout 中执行：

```bash
git fetch --tags origin
git checkout v0.12.0
pnpm install --frozen-lockfile
pnpm --filter @eveland/api db:migrate
git rev-parse --short=12 HEAD
```

将输出的 Revision 写入共享生产环境的 `EVELAND_REVISION`，并保持 `EVELAND_RELEASE_CHANNEL=stable`。

Migration 命令会应用：

- `0027_lonely_blue_shield`：Identity Provider、Realm、Grant、Return Target、Principal、Session 与 Signing Key。
- `0028_shocking_black_panther`：只允许一个启用的 Internal Provider。
- `0029_sparkling_hammerhead`：回填 Continuation Token，并创建 Eve 0.27.4+ Reset 所需的唯一 SessionBinding 路由索引。
- `0030_zippy_albert_cleary`：可为空的 Project Description 字段。
- `0031_fancy_wild_child`：删除已经废弃的 Realm → Project Grant 表。
- `0032_agent_catalog_capability_backfill`：为显式导出标准 `eveChannel()` 的既有 Source Revision 回填 Agent Catalog Capability 元数据。

`0029` 会读取现有 Session 并回填已知 Continuation Token。`0031` 会有意删除已被替代的 Grant 表；Caller Token 签发与 Catalog Membership 已不再使用它。`0032` 只填充缺失的 `eveChat` Capability 元数据，保留既有 Summary 字段和显式 Capability 值，并且在数据库恢复后重复执行仍然安全。Migration Runner 会记录每项 Migration 并只应用一次。必须在 API、Gateway 或 Worker 0.12 启动前完成 Migration 命令。

将独立的 Worker Checkout 更新到同一 Tag，并重新构建会被注入 Release 的 Sandbox Backend：

```bash
cd /opt/eveland
git fetch --tags origin
git checkout v0.12.0
pnpm install --frozen-lockfile
pnpm --filter @eveland/sandbox-bwrap build
git rev-parse --short=12 HEAD
```

在 `/etc/eveland/eveland-worker.env` 中设置相同 Revision 与 `stable` Channel。

## 4. 协调启动 Release

先验证合并后的 Compose 配置并启动非特权控制面，随后再启动宿主机 Worker：

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml config
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d
sudo systemctl start eveland-worker
sudo journalctl -u eveland-worker -n 100 --no-pager
```

0.12 Worker 第一次启动时会保存 Identity 配置指纹，并为每个 `running` 或 `draining` Deployment 排入一个定向 `restart_deployment` Job。这是预期行为。请持续观察 Jobs 和 Worker Log，直到 Queue 清空；维护窗口结束前必须处理所有失败的 Restart。Identity 配置未变化时，之后重启 Worker 不会重复排入这些任务。

## 5. 验收 0.12

完成以下全部检查：

1. API 与 Gateway `/health` 返回 `version: 0.12.0`、`channel: stable` 和相同 Revision。
2. **Settings → About** 中 Web、API、Gateway 与 Worker 配置一致，且没有缺失 Identity 配置。
3. Worker Startup Log 显示相同 Build Identity，Deployment Restart Queue 无失败并最终清空。
4. 既有公开 Agent 的 Create、Continue、Cancel 与 Stream 流量仍到达被 Pin 的 Deployment。
5. Project **Overview**、**Deployments**、**Source** 与 **Settings → Environment** 均能正常加载。
6. 如果启用了 Identity，公开 `/.well-known/jwks.json` 返回 ES256 Key，精确配置的 Chat Return Origin 可正常完成流程。

Eveland 0.12 仍支持使用 Eve `0.25.x`、`0.26.x` 与 `0.27.x` 的导入 Agent；升级平台并不强制立即修改 Agent 依赖。若要使用 Durable Reset 或 Remote Principal Forwarding，请将 Agent Lockfile 刷新到 Eve `0.27.6` 并重新部署。Remote Principal Forwarding 仍需两端 Agent 显式启用，接收端必须配置精确的 `trustedForwarders` Predicate。

## 回滚到 0.11

停止 Worker，将两个 Checkout 都恢复到 `v0.11.0`，重新安装 Frozen Lockfile、构建 `@eveland/sandbox-bwrap`、设置 0.11 Revision，重启 Compose Service，最后启动 Worker。

不要反向执行 `0027`–`0030`。其中新增的 Table、Index 与 Nullable Column 可以保留，0.11 会忽略它们；删除这些结构反而会破坏 0.12 已保存的 Identity 配置与 Continuation Token 路由状态，影响之后再次升级。

回滚后，带认证的 Web Chat Identity、Durable Reset 路由，以及 0.12 的 Navigation 与 Source Browser 均不可用。标准 0.11 Agent 流量继续使用原有 Session Binding 路径。再次尝试 0.12 时，从本文 Migration 步骤重新执行。

通用升级约束请阅读[升级与回滚](/zh/docs/operations/upgrades)，Agent 依赖细节请阅读 [Eve 兼容性](/zh/docs/reference/eve-compatibility)。
