---
title: 从 0.14 升级到 0.15
description: 应用 0.15 的四个 Migration，把 Deployment 的 Loopback 端口与 Session Event 顺序变成数据库强制的不变量，显式设置 NODE_ENV 使开发回退密钥失效，并理解为什么 0.14 无法在 0.15 的数据库上运行。
---

Eveland 0.15 修复了一个跨 Project 隔离缺陷：两个 Deployment 可能被分配到同一个 Loopback 端口，发往某个 Project Agent 的请求会由另一个 Project 的 Agent 应答。监听端口从此是 live RuntimeInstance 的属性并由数据库强制预留，就绪判定会核实持有 socket 的进程确实属于该 Deployment 自己，Job 也按 Project 串行。同一版本还把 Session Event 顺序变成数据库不变量、收紧了若干凭据边界，并为热读路径补齐索引。本文说明如何将生产环境从 `v0.14.0` 升级到 `v0.15.0`。

## 运维影响

请安排维护窗口。四个数据库 Migration 必须先于任何 0.15 进程执行，其中两个会改写既有数据行，`NODE_ENV` 也开始参与密钥解析。

其中四项后果无法通过重新 Checkout 0.14 撤销：

- Migration `0039` 为 `session_events` 增加 `(session_id, index)` 唯一索引。0.14 控制面在 Session 合并时直接改写事件归属而不重新编号，因此在迁移后的数据库上**每一次合并都会失败**；它基于 `count(*)` 的事件编号在并发 Ingest 下也会违反该约束。
- Migration `0037` 为 live RuntimeInstance 端口增加唯一索引。0.14 始终写入 `endpointPort = deployments.host_port`，一旦 0.15 把某个 Deployment 重新分配到别的端口，0.14 的激活就可能与 live 实例冲突并失败。
- Migration `0037` 在建立该索引前，会先把重复的 live RuntimeInstance 标记为 `failed`。曾经踩到端口冲突的安装，这些行会被就地纠正。
- Migration `0039` 会对已经含有重复 index 的 Session 重新编号 `session_events.index`，按 `(event_at, created_at, id)` 重建顺序。这些顺序本来就是有歧义的，但存储值会发生变化。

升级期间 Agent 持续服务流量，且**不需要重新部署**。Session、Usage 与既有 Route 都被保留。

本次升级不会改变 Project ID、Slug、Stable 或 Preview Endpoint、Route Weight，也不会改变 Deployment 的 Runtime Ownership。Eve 兼容窗口没有变化：仍接受使用 `0.25.x`、`0.26.x` 与 `0.27.x` 的导入 Agent，验证到 `0.27.8`。

### 预期中的行为变化

- **Deployment 的 Loopback 端口不再固定。** `deployments.host_port` 降级为首次部署的偏好值，权威 Endpoint 是 live RuntimeInstance 的 `endpointPort`。Gateway 与内部激活路由已经读取它。任何直接探测 Deployment 端口的外部监控都必须改为解析实例 Endpoint。Agent 裸端口始终是私有 Loopback 上游，从来不是产品 URL。
- **Job 按 Project 串行。** 排队中的 Job 会等待该 Project 正在运行的 Job 完成、失败或被回收为 stale，不同 Project 之间互不阻塞。针对同一 Project 排队的两次部署现在依次执行，而不是并发执行。
- **反复崩溃的 unit 会放弃重启。** systemd Deployment unit 增加了 `StartLimitIntervalSec=60` 与 `StartLimitBurst=5`，起不来的 Deployment 会停在 `failed`，而不是无限重启。
- **已停止 Deployment 的进程会被收割，而不是被收养。** Orphan Sweep 过去会把任何非 archived Deployment 的存活进程收养回 Runtime 生命周期，现在只在 Deployment 处于 `running` 或 `draining` 时这样做；属于 `stopped`、`failed` 或 `archived` Deployment 的进程会在宽限期后被停止。
- **只有三个 Better Auth 端点公开可路由**：`sign-in/email`、`sign-out` 与 `get-session`，其余一律返回 404，包括 `change-password`——改密码走 Eveland 自己的 `/profile/password`，它始终撤销其他 Session。
- **Promote 返回精确的状态码。** Promote 一个不存在的 Deployment 返回 404，非 running 的返回 409，二者此前都返回 500。Promote 提交之后的 Gateway 缓存失效失败不再让请求失败：Route 变更已经生效，Gateway 会在缓存 TTL 到期时收敛。
- **Zip 上传有了上限并更严格。** `POST /projects` 与 `POST /source-preflights` 对超过 `EVELAND_MAX_UPLOAD_BYTES`（默认 100 MiB）的归档返回 413，对含有符号链接的归档返回 400。
- **Docker Runtime 下解密后的 Deployment 密钥不再出现在进程 argv 上**，改为写入 `<EVELAND_DATA_DIR>/deployment-env/` 下 root 所有的 `0600` 文件，与 systemd Runtime 的既有做法一致。容器停止时该文件被删除。

## 1. 备份并检查 0.14

按照现有基础设施流程备份 Postgres 与 `EVELAND_DATA_DIR`。该备份是唯一受支持的回滚路径，原因见下文回滚一节。记录当前 Tag 和 Revision，确认 API 与 Gateway Health 正常，并等待重要的 Import、Build、Deployment、Schedule 或 Delete Job 完成。

修改两个 Checkout 前先停止宿主机 Worker：

```bash
sudo systemctl stop eveland-worker
```

如果这套安装曾受端口冲突影响，建议在迁移前先检查现状。下面的命令列出共用端口的 Deployment，以及实际持有这些端口的 unit：

```bash
psql "$DATABASE_URL" -c "
  select host_port, count(*), array_agg(project_id || '/' || id)
  from deployments where status <> 'archived'
  group by host_port having count(*) > 1;"
sudo ss -ltnp '( sport >= :41000 and sport <= :41100 )'
systemctl list-units 'eveland-*' --no-pager
```

Migration `0037` 负责数据库一侧的纠正。Deployment 已经是 `stopped` 或 `archived` 却仍存活的宿主机进程，会被 0.15 的 Orphan Sweep 在宽限期后停止。

## 2. 显式设置 NODE_ENV

0.15 不再把未设置的 `NODE_ENV` 当作"非生产"。仓库中公开可见的 `eveland-dev-*` 回退密钥——Gateway 内部服务 Token、Gateway Affinity Secret，以及 Scheduler Runtime 与 Dispatch Secret——现在**仅**在显式的 `NODE_ENV=development` 或 `NODE_ENV=test` 下生效。其他取值（含未设置）一律 fail closed，缺少真实密钥时进程拒绝启动。

文档化的生产拓扑本身已满足该要求：`docker-compose.prod.yml` 在每个服务命令上设置 `NODE_ENV=production`，`infra/systemd/eveland-worker.env.example` 也为宿主机 Worker 设置了它。请确认你实际使用的文件与之一致——遗漏该变量的宿主机此前是在静默使用本仓库公开的 dev 密钥运行：

```bash
grep -n NODE_ENV /etc/eveland/eveland-worker.env
docker compose -f docker-compose.yml -f docker-compose.prod.yml config | grep -n "NODE_ENV"
```

任一处缺失时，请在启动 0.15 前设置 `NODE_ENV=production` 并配置真实密钥。任何此前依赖 dev 回退值的密钥都应视为已泄露并轮换：`EVELAND_GATEWAY_SERVICE_TOKEN`、`EVELAND_GATEWAY_AFFINITY_SECRET`、`EVELAND_SCHEDULER_RUNTIME_SECRET` 与 `EVELAND_SCHEDULER_DISPATCH_SECRET` 都必须是长随机值，在共享它们的组件之间保持一致，且彼此独立。

## 3. 确认宿主机前置条件

Worker 启动 Preflight 新增要求 `ss` 与 `ps`。就绪判定会核实 Deployment 端口上的监听 socket 属于它自己的 unit——`ss` 找到监听者的 pid，`ps -o unit=` 把它映射回 unit——因此被外来进程持有端口时激活会大声失败，而不是被当作健康收下。两个命令都包含在 Ubuntu 基础镜像中，请确认而不是假定：

```bash
command -v ss && command -v ps
# 缺失时：sudo apt-get install -y iproute2 procps
```

本次发布不改变其他宿主机前置条件。

## 4. 安装 0.15 并应用 Migration

在控制面 Checkout 中：

```bash
git fetch --tags origin
git checkout v0.15.0
pnpm install --frozen-lockfile
pnpm --filter @evelandhq/api db:migrate
git rev-parse --short=12 HEAD
```

把打印出的 Revision 作为 `EVELAND_REVISION` 写入共享生产环境，并保持 `EVELAND_RELEASE_CHANNEL=stable`。

该命令会应用：

- `0036_omniscient_molten_man`：新增 `jobs.sequence`，一个用作 FIFO 决胜键的 generated identity 列。`created_at` 精度有限，同一瞬间入队的 Job 此前的 claim 顺序取决于查询计划。
- `0037_black_cerebro`：先把重复的 live RuntimeInstance 标记为 `failed`（每个端口保留最新的持有者），再为 `starting`、`ready`、`draining` 状态上的 `endpoint_port` 建立唯一索引。
- `0038_foamy_tomorrow_man`：为 `sessions (project_id, eve_session_id)`、`session_nodes (root_session_id, created_at)`、`logs (project_id, created_at)` 以及 `jobs` 上的三个索引建表，其中两个是仅覆盖非终态行的 partial 索引。
- `0039_far_maria_hill`：对含有重复 index 的 Session 重新编号 `session_events.index`，再建立 `(session_id, index)` 唯一索引。

必须在 API、Gateway 或 Worker 0.15 启动之前完成该命令。

`0038` 与 `0039` 使用普通 `CREATE INDEX` 建索引，建索引期间会持有表级写锁，`0039` 还会改写受影响 Session 的数据行。如果安装中的 `logs`、`sessions` 或 `session_events` 历史很大，这会是整个升级中最慢的一步。请放在维护窗口内执行，或事先用 `CREATE INDEX CONCURRENTLY` 手工建好这些索引，让 Migration 直接发现它们已存在。

把独立的 Worker Checkout 更新到同一 Tag 并重新构建 vendored sandbox backend：

```bash
cd /opt/eveland
git fetch --tags origin
git checkout v0.15.0
pnpm install --frozen-lockfile
pnpm --filter @evelandhq/sandbox-bwrap build
git rev-parse --short=12 HEAD
```

在 `/etc/eveland/eveland-worker.env` 中设置相同的 Revision 与 `stable` 渠道。

## 5. 启动协调发布

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml config
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d
sudo systemctl start eveland-worker
sudo journalctl -u eveland-worker -n 100 --no-pager
```

留意 Worker 的最初几个 tick。Preflight 失败会直接点名缺失的前置条件；Orphan Sweep 会记录它停止的每一个进程，包括控制面早已停止的 Deployment 遗留下来的那些。

## 6. 验证 0.15

请完成以下全部检查：

1. API 与 Gateway `/health` 返回 `version: 0.15.0`、`channel: stable` 以及相同的 Revision。
2. **Settings → About** 中 Web、API、Gateway 与 Worker 的 build identity 一致。
3. Deployment 端口范围内每个端口恰好只有一个监听者，且属于声明该端口的 Deployment 对应的 unit：

   ```bash
   sudo ss -ltnp '( sport >= :41000 and sport <= :41100 )'
   ```

4. 没有任何 live RuntimeInstance 共用端口。下面的查询必须返回空：

   ```bash
   psql "$DATABASE_URL" -c "
     select endpoint_port, count(*) from runtime_instances
     where status in ('starting','ready','draining') and endpoint_port is not null
     group by endpoint_port having count(*) > 1;"
   ```

5. 通过公开 URL 唤醒一个 scale-to-zero 的 Deployment，确认应答来自该 Project 自己的 Agent。这正是本次发布要修复的缺陷，如果此前有共用端口的 Project，请优先在它上面验证。
6. 部署一个 Project，确认新 Deployment 达到 `running`，再 Promote 并确认 Stable Route 迁移且返回 200。
7. 运行一次 Playground 对话，确认 Session、Node、Event 与 Provider 上报的 Usage 都出现。
8. **Settings → Instance health** 显示新鲜的 Worker 心跳与宿主机容量采样。
9. 在控制面退出并重新登录，确认收窄后的 Better Auth 面仍然支持正常登录路径。

## 回滚到 0.14

**恢复升级前的数据库备份是唯一受支持的回滚方式。** 不要让 0.14 进程连接已经应用了 `0037` 与 `0039` 的数据库：0.14 在 Session 合并时直接改写事件归属而不重新编号，会违反 `(session_id, index)` 唯一索引；它的激活写入 `endpointPort = deployments.host_port`，可能与运行在重新分配端口上的 live 实例冲突。

回滚步骤：停止 Worker 与全部 0.15 控制面服务，恢复升级前的 Postgres 备份，如果备份流程要求数据库与文件系统时间点匹配则同时恢复 `EVELAND_DATA_DIR`，在两个位置 Checkout `v0.14.0`，重新安装 frozen lockfile，重新构建 `@evelandhq/sandbox-bwrap`，恢复此前的 Revision，然后启动 Compose，最后启动 Worker。

恢复会丢弃备份之后的所有数据库变更，包括新的 Session、Job 与 Route 变更。它同时会恢复 0.15 之前的端口分配，因此启动 Worker 前请确认没有 0.15 的遗留进程仍占着端口：

```bash
systemctl list-units 'eveland-*' --no-pager
sudo ss -ltnp '( sport >= :41000 and sport <= :41100 )'
```

回滚后请保留 `NODE_ENV` 设置。0.14 接受未设置的取值，但保持未设置会静默恢复使用公开的 dev 回退密钥。

## Agent 侧变化

已发布的 `eveland` SDK 增加了可选的 Realm allowlist。Eveland 的 Identity Broker 只负责认证调用者，不决定哪个 Realm 可以访问哪个 Agent，因此默认情况下为任意已启用 Realm 铸造的 Caller Token 在每个 Agent 中都能通过验证。服务特定受众的 Agent 现在可以显式声明：

```ts
evelandIdentity({ allowedRealms: ["irlm_staff"] });
```

该 allowlist 也可从 `EVELAND_ALLOWED_REALM_IDS`（逗号分隔）读取。两者都不设置时保持既有的"接受任意 Realm"行为，因此升级不会改变任何已部署 Agent 的行为。

同一版本还把 `name` 属性改为可选。上游身份提供方没有提供显示名时 Eveland 会省略该 claim，而 SDK 此前会拒绝这类 Token——使用这类提供方的用户能正常登录，随后对 Agent 的每个请求都被判为未认证。读取 Principal 属性时请把 `name` 与 `email` 都当作可选。

关于不随版本变化的通用升级流程，见[升级与回滚](/docs/operations/upgrades)。本文提到的每个变量，见[配置](/docs/reference/configuration)。
