# Eve 0.24 Scheduler and Scale-to-Zero Handoff

**Date:** 2026-07-15  
**Status:** implementation handoff  
**Eve baseline:** exactly `0.24.2`  
**Scope:** Eveland-owned Scheduler, cron execution history in Sessions, and the runtime activation path required for scale-to-zero

## How to use this plan

This plan is grounded in Eve 0.24.2's documentation and source rather than the
current Scheduler text in `docs/spec.md`. Do not begin by conforming the code to
the old Scheduler spec. Implement and verify the behavior below first, then
update product and deployment documentation to the behavior that actually
ships.

Do not propose or depend on an Eve upstream change. Do not import
`eve/dist/src/internal/**`, patch generated Nitro chunks, run `eve dev` in
production, or use `TEST=1` to suppress Nitro's schedule runner. Eve is moving
quickly; all Eve-specific adaptation must be explicit, version-gated, and
covered by a real Eve 0.24.2 build/runtime fixture.

Follow repository TDD guidance for every implementation phase: add the narrow
failing test first, observe it fail, implement the smallest vertical slice,
then broaden verification.

## Confirmed Eve 0.24.2 behavior

The following facts are implementation inputs, not open design questions:

1. Schedules are root-only files under `agent/schedules/`; nested paths are
   valid and identity is the complete relative path without the extension
   (`billing/sweep.ts` becomes `billing/sweep`).
2. A schedule has a standard five-field, minute-granularity `cron` and exactly
   one of:
   - `markdown`, which starts one task-mode Eve Session; or
   - `run`, which can call `receive()` zero, one, or many times and can register
     `waitUntil()` work.
3. `eve start` starts Nitro's in-process schedule runner. Every concurrently
   running Deployment process containing the schedule registrations therefore
   gets its own clock.
4. `POST /eve/v1/dev/schedules/:scheduleId` is dev-only and is absent from
   production builds.
5. Eve's internal dispatch result is `{ scheduleId, sessionIds[] }`, but
   `scheduleId` is not propagated into Session context or Session events.
   Observer `channelKind=schedule` cannot identify which authored schedule ran.
6. A handler schedule can complete successfully with zero Sessions. One cron
   tick must not be modeled as exactly one Eve Session.
7. The 0.24.2 release itself contains no Scheduler contract change relative to
   0.23; its published patch changes concern compaction, tool approvals, and
   Vercel build isolation.

## Decisions

These decisions are settled for the first implementation:

1. **Eveland owns the clock and ledger.** Eve owns execution of the authored
   prompt/handler and durable workflow state.
2. **The injected Scheduler Channel is an execution RPC, not a daemon.** It
   exists inside a temporarily started Eve process and does not require that
   process to remain alive between jobs.
3. **Deployment and process lifetime are separate.** A Deployment remains an
   immutable, addressable target while its Runtime Instance may be dormant.
4. **Cron targets exactly one Deployment.** It never resolves through a
   weighted Gateway route. Preview and A/B candidate Deployments do not run
   cron merely because they are alive.
5. **Eve's native timer performs no business execution on Eveland.** Prepared
   Releases preserve schedule registrations for Eve compatibility but replace
   their native handlers with no-ops. Only Eveland's authenticated dispatch
   path invokes the preserved original definition.
6. **One ScheduleRun relates to zero or more Sessions.** ScheduleRun is the
   durable execution record; Sessions retain Eve conversation/workflow event
   history and usage.
7. **Source cron semantics are Eve semantics.** Support five fields and UTC in
   the first platform scheduler. `timezone` and `enabled` are not accepted as
   Markdown frontmatter. Enable/disable is an Eveland control-plane override.
8. **Missed ticks coalesce in v1.** When a Deployment was dormant or the worker
   was unavailable across multiple due times, enqueue at most one catch-up run,
   record the coalesced/missed count, and calculate the next future tick. Do
   not replay an unbounded backlog.
9. **Activation is lease-driven.** A process remains alive while a public
   request, active stream, running turn, or schedule dispatch owns a lease. A
   durably parked Session does not keep a process alive.

## Explicit non-goals

- No Eve upstream proposal or fork.
- No second-granularity cron.
- No arbitrary source-defined timezone in the first slice.
- No exactly-once guarantee for arbitrary external side effects inside
  authored handlers. Eveland guarantees one durable ScheduleRun per due tick
  and idempotent dispatch claiming; authored side effects still need their own
  idempotency where a process can fail after making an external call.
- No public access to the injected Scheduler Channel.
- No assumption that a running process is the Deployment's durable identity.

## Target architecture

```text
Postgres schedule definitions and nextRunAt
                 |
                 v
Worker planner atomically creates ScheduleRun + trigger_schedule job
                 |
                 v
Worker acquires schedule activation lease for exact Deployment
                 |
          dormant? start prebuilt Release with eve start
                 |
          wait for private-port readiness
                 |
                 v
POST injected, authenticated Eveland Scheduler Channel
                 |
       execute preserved markdown or run definition
                 |
       return zero or more Eve session ids
                 |
                 v
Persist ScheduleRun -> Sessions relationships
Observer merges events, nodes, status, and provider usage
                 |
          release activation lease
                 |
        idle TTL and no other leases -> stop process
```

The executable is still `eve start`, but it is a cold-started execution engine,
not a permanently running scheduler. The Channel supplies the production
one-shot dispatch surface that Eve 0.24.2 does not expose.

## Domain and persistence model

Do not extend the existing project-only `schedules` row with more nullable
fields until its identity problem is fixed. Introduce explicit current
identity, version, execution, and runtime-lifecycle records.

### ProjectSchedule

Stable logical identity across source revisions:

```ts
type ProjectSchedule = {
  id: string; // sch_...
  projectId: string;
  key: string; // full Eve path-derived id, e.g. billing/sweep
  enabled: boolean; // Eveland override
  createdAt: string;
  updatedAt: string;
};
```

Add a unique constraint on `(projectId, key)`.

### ScheduleVersion

Immutable definition discovered from a SourceRevision and later executed from
a Release:

```ts
type ScheduleVersion = {
  id: string; // schv_...
  scheduleId: string;
  sourceRevisionId: string;
  kind: "markdown" | "handler";
  cron: string;
  sourcePath: string;
  definitionHash: string;
  createdAt: string;
};
```

The prompt or handler source remains in the immutable source/release artifact;
do not duplicate arbitrary source into this table. Add uniqueness on
`(scheduleId, sourceRevisionId)`.

### Schedule target

Add an explicit project scheduler target, preferably a small dedicated table
rather than overloading route policy:

```ts
type ProjectSchedulerTarget = {
  projectId: string;
  deploymentId: string;
  updatedAt: string;
};
```

`promoteDeployment()` may update this target only as an explicit part of the
promotion transaction. Generic weighted route edits must not silently move the
cron target. A target Deployment's Release selects the active ScheduleVersion.

### ScheduleRun

One durable cron/manual execution envelope:

```ts
type ScheduleRun = {
  id: string; // srun_...
  scheduleId: string;
  scheduleVersionId: string;
  releaseId: string;
  deploymentId: string;
  dueAt: string;
  trigger: "cron" | "manual";
  status:
    | "queued"
    | "activating"
    | "dispatching"
    | "running"
    | "succeeded"
    | "failed"
    | "dispatch_unknown"
    | "skipped";
  attempt: number;
  missedTicks: number;
  error: string | null;
  startedAt: string | null;
  completedAt: string | null;
  createdAt: string;
  updatedAt: string;
};
```

For cron runs, enforce uniqueness on `(scheduleVersionId, dueAt)`. Manual runs
receive a distinct `dueAt`/request id and do not collide with cron.

### ScheduleRun to Session

Add nullable `scheduleRunId` to `sessions`, indexed for history lookup. Every
Eve Session id returned by dispatch is pre-bound/upserted with:

- exact `projectId` and `deploymentId`;
- `trigger="cron"` or `trigger="manual"` as appropriate;
- logical `scheduleId`;
- `scheduleRunId`.

Observer ingestion must merge into these pre-created/bound Sessions rather
than creating duplicate `direct_http` or generic `cron` Sessions. A successful
zero-Session ScheduleRun remains visible even though no `sessions` row points
to it.

### RuntimeInstance and ActivationLease

Keep process state separate from Deployment health/history:

```ts
type RuntimeInstance = {
  id: string; // rti_...
  deploymentId: string;
  generation: number;
  status: "starting" | "ready" | "draining" | "stopped" | "failed";
  endpointHost: string | null;
  endpointPort: number | null;
  startedAt: string | null;
  readyAt: string | null;
  stoppedAt: string | null;
  lastError: string | null;
};

type ActivationLease = {
  id: string; // lease_...
  deploymentId: string;
  runtimeInstanceId: string | null;
  kind: "public_request" | "stream" | "turn" | "schedule_run";
  ownerId: string; // request id, session id, or schedule run id
  expiresAt: string;
  releasedAt: string | null;
};
```

Use uniqueness on `(deploymentId, kind, ownerId)` and lease expiration for
crash recovery. Do not rely solely on in-memory reference counts.

## Phase 2: build the Eve 0.24 Release adapter

Create a focused package such as `packages/agent-scheduler` rather than putting
AST rewriting directly in `apps/worker`. Model it after the existing observer
injection boundary: it receives a prepared Release directory and mutates only
that disposable overlay, never the imported source snapshot.

### Version gate

The adapter must:

- require exact detected Eve version `0.24.2` initially;
- fail closed on an unknown Eve minor/manifest shape;
- expose a clear diagnostic telling operators to add/update an adapter;
- have a real Eve fixture test, not only generated-string snapshots.

### TypeScript schedule rewrite

Use a TypeScript AST transform, not regular expressions.

For each authored TS/JS module schedule:

1. Preserve its original default definition as a reserved named binding/export.
2. Replace the default export with a definition that has the same `cron` and a
   no-op `run` handler.
3. Keep authored relative imports and module initialization semantics intact.
4. Reject collisions with all reserved identifiers/files.

The injected Channel imports the reserved original binding and invokes its
`run` function. Cover direct default expressions, default identifiers, nested
paths, supported JS/TS extensions, and malformed/default re-export cases.

### Markdown schedule rewrite

For each Markdown schedule:

1. Parse the strict Eve 0.24 Markdown contract.
2. Replace the overlay file with an equivalent generated module at the same
   logical schedule key.
3. Default-export the same cron plus a no-op `run` handler.
4. Preserve the original markdown prompt in a reserved named export consumed
   by the injected Channel.

### Injected Scheduler Channel

Generate a reserved root channel, for example:

```text
agent/channels/eveland-scheduler.ts
```

Requirements:

- use only public `eve/channels` and `eve/schedules` imports;
- set `kindHint: "schedule"` so Markdown task Sessions retain schedule channel
  semantics;
- expose one POST route keyed by ScheduleRun id and schedule key;
- require a platform-owned runtime secret from the environment;
- compare credentials safely and never include them in generated source,
  responses, logs, or observer events;
- validate the requested key against a generated closed dispatch table;
- for Markdown, call route `send()` with `mode: "task"`, a deterministic
  ScheduleRun continuation token, schedule app auth, and a useful title;
- for handlers, invoke the preserved `run` with wrapped `receive` and
  `waitUntil`, collect every returned Session, and await all registered tasks
  using Eve's `Promise.allSettled` behavior;
- return `{ scheduleRunId, scheduleKey, sessionIds }`;
- report handler failure without leaking secrets or arbitrary response bodies.

Recreate only the documented Eve schedule app-auth literal. Do not import its
internal constant.

### Dispatch idempotency

Before executing authored code, the injected route must redeem a short-lived,
single-use dispatch credential for this exact ScheduleRun and Deployment
against an internal API endpoint. The API atomically transitions the run from
`activating` to `dispatching`; a duplicate request cannot execute the handler.

After the route starts Sessions, it reports their ids and terminal handler
dispatch result. If the process dies after redemption and before reporting,
the lease expires and the run becomes `dispatch_unknown`; do not automatically
re-execute arbitrary handler side effects. Expose an operator/manual retry that
creates a new attempt with an explicit audit trail.

### Exit criteria

- Leaving a transformed Deployment warm across multiple native cron ticks
  produces no Sessions or external handler calls.
- Authenticated manual dispatch executes the original Markdown/handler logic.
- Unknown schedule keys, replayed credentials, and public unauthenticated calls
  fail without execution.
- `ctx.channel.kind` is `schedule` for generated Markdown task Sessions.

## Phase 3: Worker planner and ScheduleRun execution

### Planner

Add a small recurring planner loop to the Worker process. It must not block the
existing job poller and must be safe when multiple Workers exist.

For each claim transaction:

1. Read enabled ProjectSchedules whose active ScheduleVersion is due.
2. Insert the unique ScheduleRun.
3. Enqueue `trigger_schedule` with `scheduleRunId`, not only `scheduleId`.
4. Advance `nextRunAt` to the next future UTC occurrence.
5. Record coalesced missed tick count.

Use bounded batches and deterministic ordering. Worker restart must discover
the next due work from Postgres; an in-memory timer is only a wakeup hint.

### `trigger_schedule` job

Replace the current log-only implementation with:

1. Load and validate ScheduleRun, target Deployment, Release, ScheduleVersion,
   and enabled state.
2. Transition `queued -> activating` idempotently.
3. Acquire a `schedule_run` ActivationLease.
4. Ensure the exact Deployment Runtime Instance is ready.
5. Call the RuntimeAdapter's private dispatch endpoint with the one-time
   credential.
6. Persist/attach all returned Eve Session ids before acknowledging the job.
7. Complete or fail the ScheduleRun according to the route result.
8. Release the activation lease in `finally` without masking the primary
   failure.

Never resolve the target through Gateway or stable-route weights. RuntimeKind
must come from the target Deployment, as with stop/restart/delete.

### Manual run

Add an authenticated control-plane endpoint that creates a manual ScheduleRun
and enqueues the same `trigger_schedule` job. Do not create a second execution
path.

### Exit criteria

- A due run on a dormant Deployment starts, dispatches once, records its
  Sessions, and releases its lease.
- Two Workers and duplicate jobs still execute once.
- A preview Deployment never runs schedules unless explicitly selected as the
  scheduler target.
- Promotion/rollback deterministically changes the version used by future
  runs while historical runs retain old Release provenance.

## Phase 4: runtime activation and scale-to-zero

Implement activation as a shared worker/runtime service, not schedule-specific
shell code.

### RuntimeAdapter additions

Extend `apps/worker/src/runtime/types.ts` with operations along these lines:

```ts
inspectProcess(processName): Promise<"missing" | "starting" | "ready" | "stopped" | "failed">;
ensureProcess(input: ProcessStartInput): Promise<ProcessStartResult>;
```

`ensureProcess` must be idempotent for concurrent leases and must start the
prebuilt Release only. It must not reinstall dependencies or rebuild source on
a cold request.

Docker and systemd implementations must preserve existing path mounts,
observer outbox, sandbox cache, secrets, process-group cleanup, and runtimeKind
ownership.

### Activation manager

Add a worker-owned activation manager that:

- atomically creates/renews/releases ActivationLeases;
- elects one starter for a dormant Deployment;
- waits for the existing readiness probe with a bounded timeout;
- publishes RuntimeInstance state for other waiters;
- does not stop while any unexpired lease exists;
- starts an idle deadline after the final lease is released;
- rechecks leases transactionally before stopping;
- recovers stale `starting`, `ready`, and lease rows after Worker/process crash.

Use a configurable idle TTL. Tests should use a short injected clock; production
must not use sleeps in unit tests.

### Schedule lifecycle

The schedule lease remains held while the injected route is executing the
handler and registered `waitUntil` tasks. It can be released once the workflow
has completed or durably parked and the route has returned. A parked Session
does not keep the process alive.

### Public request wake path

Scale-to-zero is incomplete until public Agent traffic can wake a dormant
Deployment.

Preserve privilege boundaries:

1. Gateway detects that the bound/selected Deployment is dormant.
2. Gateway calls a service-authenticated internal API activation endpoint.
3. API enqueues/coalesces `ensure_deployment_running`; it does not gain
   Docker/systemd privileges.
4. Worker starts the Deployment and publishes readiness.
5. Gateway waits within a bounded cold-start timeout, then opens the private
   upstream and preserves the original Agent auth, cookies, headers, body
   stream, abort signal, and NDJSON response stream.

Do not buffer an unbounded request body while waiting. Keep the inbound stream
unread/backpressured until readiness where the server permits it, retain the
existing body limit, and propagate client abort during activation.

Continuation requests must wake the Deployment already selected by the
SessionBinding, not re-run route weighting.

### Exit criteria

- A dormant Deployment wakes for cron and returns to stopped after idle TTL.
- A dormant Deployment wakes for a new public request.
- A continuation wakes its bound Deployment after promote/rollback.
- Concurrent cold requests cause one process start.
- Active stream/running turn prevents shutdown; durable park allows shutdown.
- Client abort during cold start cancels the request lease without stopping a
  process still needed by other leases.

## Failure and recovery matrix

Implement and test these cases explicitly:

| Failure                                            | Required result                                                        |
| -------------------------------------------------- | ---------------------------------------------------------------------- |
| Worker crashes before ScheduleRun insert           | next planner discovers due schedule                                    |
| Crash after run insert, before job                 | reconciliation enqueues missing job                                    |
| Duplicate planner/job                              | unique run and atomic dispatch claim prevent double execution          |
| Runtime cold start fails                           | run becomes failed; no Session is fabricated                           |
| Process dies before dispatch credential redemption | safe retry of same activation/job                                      |
| Process dies after redemption, result unknown      | `dispatch_unknown`; no automatic side-effect replay                    |
| Handler throws before Session creation             | failed run with zero Sessions                                          |
| Handler starts multiple Sessions                   | one run links all Sessions                                             |
| Observer delivery is delayed/duplicated            | prebinding merges idempotently                                         |
| Promotion during queued run                        | queued run keeps pinned Deployment/Release; future runs use new target |
| Native Nitro cron fires while warm                 | no-op, no business execution or Session                                |
| Last lease expires during shutdown race            | transactional recheck prevents stopping a newly leased instance        |
| Public client aborts during cold start             | request lease released; other leases preserved                         |

## Post-handoff correction: ScheduleRun execution lifetime

Issue #147 exposed that the original completion point described above covered
Scheduler Channel dispatch, not the asynchronous Eve turn it started. A
dispatch returning Session IDs must remain `running` and retain its
`schedule_run` ActivationLease until Observer reports a root turn boundary for
every returned Session. Zero-Session dispatches still complete immediately.

Observer projection records the exact RuntimeInstance generation on Session
nodes and events. Worker reconciliation fails active executions when that
generation disappears and applies a separate 24-hour hard deadline when no
Observer boundary arrives. The normal five-minute activation idle TTL is not an
execution timeout.
