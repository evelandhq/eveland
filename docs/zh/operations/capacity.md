Eveland 允许多个 Agent 共享同一台宿主机硬件。在规划资源时，核心需要关注三类工作负载对内存、CPU 与数据库连接的竞争：

| 工作负载类型         | 典型内存占用    | CPU 消耗特性        | PostgreSQL 连接消耗                               |
| :------------------- | :-------------- | :------------------ | :------------------------------------------------ |
| **单次构建 (Build)** | 峰值 1–2 GB     | 突发性高（约 2 核） | **无**（构建环境不连数据库）                      |
| **运行中 Agent**     | 150–300 MB RSS  | 空闲低，对话时突发  | 至多 `WORKFLOW_POSTGRES_MAX_POOL_SIZE`（默认 10） |
| **平台核心服务**     | 合计约 1–1.5 GB | 低，运行平稳        | 约 30 个连接（API、Gateway 与 Worker 共享池）     |

---

## 1. 并发管控机制

### 运行中 Agent 数量

- **无硬性数量上限**：得益于缩容至零机制，5 分钟内无请求租约的 Agent 进程会自动退出并释放内存。因此，稳态下的活跃进程数仅取决于**真实并发访问量**，而非部署的 Agent 总数。

### 并发构建上限

- 为防止突发构建打垮宿主机，Worker 启动时会根据机器硬件规格自动计算并发构建上限：
  $$\text{并发构建上限} = \max(1, \min(\lfloor \text{RAM} / 4\text{GiB} \rfloor, \text{CPU核数} - 2))$$
- 超出上限的构建请求将在队列中排队等待；而轻量级任务（如重启、归档、删除）不受此限制，继续流转。

---

## 2. PostgreSQL 连接预算规划

`max_connections` 是生产环境中最常见的瓶颈之一。在 Postgres 中，空闲连接本身占用内存很小（约 2 MB），而运行中 Agent 的内存开销远高于连接本身。因此应按以下顺序核算：

### 计算步骤

1. **核算可支持的并发活跃 Agent 数量**：
   $$\text{可用内存} = \text{总内存} - 2\text{GB (系统与核心服务)} - (\text{并发构建数} \times 2\text{GB})$$
   $$\text{并发活跃 Agent 数量} \approx \frac{\text{可用内存}}{0.3\text{GB}}$$
2. **设置 Postgres `max_connections`**：
   $$\text{max\_connections} \approx (\text{并发 Agent 数量} \times \text{连接池大小}) + 30\text{ (核心服务)} + 10\text{ (Dispatcher)} + \text{安全余量}$$

## 4. 磁盘与网络容量规划

- **沙箱持久化工作区**：位于 `EVELAND_DATA_DIR/sandboxes` 下的会话工作区会随长期会话数累积。可定期使用 Worker 的清理接口进行巡检修剪。
- **发布包归档**：历史发布版本会由系统保留策略（Retention Policy）自动控制，旧版本的构建镜像和产物会自动清理。
- **网络端口段**：systemd 运行时下，每个活跃部署分配一个独立的本地回环端口（`18000–18999`），单机支持最多 1000 个端口分配。
