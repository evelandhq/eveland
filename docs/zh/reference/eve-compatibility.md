Eveland 只支持通过完整兼容矩阵的 Minor Line，并显式变更该窗口；Eve 1.0 也发布了 Stability Policy，其稳定 API 只会在 Major 版本中做不兼容变更。代码中的产品契约支持 `0.83.x` 与 `1.0.x`，验证版本为 `0.83.3` 与 `1.0.0-rc.1`。Eve 0.84 至 0.91（2026-11-02 跳过：每条都在数日内被取代，且它们与 1.0 说同一套 v27 Session 协议，而 1.0 是 Eve 第一条纳入 Semver 的线）、Eve 0.81（2026-11-02 随 1.0 进入而退役；Eveland v0.65.0 自 2026-10-27 起已带上 0.83，因此每个 0.81 的 Release 都已有更新的线可供重建）、Eve 0.82（2026-10-27 跳过：0.83.0 在两天内取代了它，没有任何 Eveland 发布版带上过它）、Eve 0.79（2026-10-27 随 0.83 进入而退出；Eveland v0.64.0 从 2026-10-21 起就已带上 0.81，因此每个 0.79 的 Release 早已有更新的线可供重建）、Eve 0.80（2026-10-21 跳过：0.81.0 在四天内取代了它，没有任何 Eveland 发布版带上过它）、Eve 0.76（2026-10-21 随 0.81 进入而退出；Eveland v0.63.0 从 2026-10-14 起就已带上 0.79，因此每个 0.76 的 Release 早已有更新的线可供重建）、Eve 0.77 与 0.78（2026-10-14 跳过：0.79.0 在几天内就取代了它们，没有任何 Eveland 发布版带上过它们）、Eve 0.74（2026-10-14 随 0.79 进入而退出；Eveland v0.62.0 从 2026-10-10 起就已带上 0.76，因此每个 0.74 的 Release 早已有更新的线可供重建）、Eve 0.75（2026-10-10 随 0.76 进入而退出，距它自己进入仅一天，没有任何 Eveland 发布版带上过它）、Eve 0.68（2026-10-09 随 0.75 进入而退出；Eveland v0.61.0 从前一天起就已带上 0.74，因此每个 0.68 的 Release 早已有更新的线可供重建）、Eve 0.73（2026-10-08 随 0.74 进入而退出，距它自己进入只有几个小时，没有任何 Eveland 发布版带上过它）、Eve 0.72（2026-10-08 随 0.73 进入而退出，距它自己进入仅一天，没有任何 Eveland 发布版带上过它）、Eve 0.70（2026-10-07 随 0.72 进入而退出，距它自己进入只有五天，没有任何 Eveland 发布版带上过它）、Eve 0.71（2026-10-07 被跳过：0.72.0 在四天内取代了它，没有任何 Eveland 发布版带上过它）、Eve 0.69（2026-10-02 随 0.70 进入而退出，距它自己进入仅一天，没有任何 Eveland 发布版带上过它）、Eve 0.62（2026-10-02 随 0.69 进入而退出）、Eve 0.67（2026-09-29 随 0.68 进入而退出，距它自己进入只有三天，没有任何 Eveland 发布版带上过它）、Eve 0.66（2026-09-26 随 0.67 进入而退出，距它自己进入只有两天，没有任何 Eveland 发布版带上过它）、Eve 0.63、0.64 与 0.65（2026-09-23 与 2026-09-24 被跳过：只要后台 Subagent 调用遇到订阅了 Subagent 事件的 Hook——Eveland 自己的 Observer 就是这样的 Hook——0.63.0 就会让该 Session 失败，0.64.0 发布了修复，0.65.0 在一天之内取代了 0.64.1，0.66.0 又在六小时内取代了 0.65.0，任何 Eveland 发布版都来不及带上其中任何一个）、Eve 0.58（2026-09-23 随窗口收窄到 0.62 下限而退出）、Eve 0.59、0.60 与 0.61（2026-09-19 被跳过：每一条都在一天之内被下一条取代，没有任何 Eveland 发布版带上过它们）、Eve 0.55（2026-09-19 随 0.62 进入而退出）、Eve 0.56 与 0.57（2026-09-17 被跳过：0.58.0 在任何 Eveland 发布版带上它们之前就已取代二者）、Eve 0.54（2026-09-16 随 0.56 进入一个本就是两条线的窗口而退出）、Eve 0.52 与 0.53（2026-09-15 同时退出）、Eve 0.50 与 0.51（2026-09-12 同时退出）、Eve 0.49（2026-09-07 退出）、Eve 0.48（2026-09-02 窗口滑到它之后即被 0.49.0 取代、被跳过，没有任何 Deployment 在其上运行过）以及 Eve 0.47 及更早版本不再允许 Import、Build、Restart、Activation、Playground、Agent Gateway 或 Schedule Execution。

项目 `package.json` 中允许的 Eve 依赖声明形式为：受支持线内的精确 Patch（`1.0.0-rc.1` 这类 Release Candidate 作为精确版本同样计入）、锚定在受支持 Minor Patch 上的 `~` Range、锚定在受支持 `0.x` Minor Patch 上的 `^` Range（npm 按 `~` 解读），以及 `0.83` / `0.83.x` / `0.83.*`、`1.0` / `1.0.x` / `1.0.*`。`^1.x` Range 会覆盖之后所有 1.x Minor，因此被拒绝。缺少 Eve 依赖、跨 Minor 的宽泛 Range 或任何可能解析到窗口之外的声明都会 Fail Closed。项目 Overview、Source 与 Playground 会显示当前 Deployment 对应 Source Revision 的 Eve 依赖版本与平台要求。

窗口是一组经过验证的线，而不是"下限以上的一切"：`1.0.x` 于 2026-11-02（`1.0.0-rc.1` 发布两天后，它是 npm 的 `latest` Tag）进入，`0.81.x` 下限随之离开——2026-10-27 发布的 Eveland v0.65.0 已带上 `0.83.x`，因此每个 0.81 的 Release 都有更新的线可供重建。SDK 的 Peer Range 变为 `>=0.83.0 <1.0.0 || >=1.0.0-0 <2.0.0`；正是 `-0` 这个比较符让 npm 接受 1.0 的 Release Candidate。`0.84.x` 至 `0.91.x` 位于外包络内，与已退役的线一样以升级诊断拒绝。Release 构建于已退役线上的 Deployment，在 Eveland 带上更窄窗口后立即不可服务：Agent Gateway 以 409 应答，Activation 拒绝它，平台会结算仍停在其上的 Workflow Run 而不是反复重试。**这个窗口跨越了 Session 协议边界。** 0.83 说 v26 Session Stream，1.0 说 v27，因此与此前每一对线不同，两者的线上格式并不相同；Eveland 中每个读取 Session Stream 的组件都同时读取两者：注入的 Observer、Session/用量投影、Session 回放与 Trace、Schedule 结果、Agent Gateway 的路由分类，以及 Playground——它同时打包两个 Eve Client，并选用与当前 Deployment 所跑 Eve 相匹配的那个。`0.83.3` 与 `1.0.0-rc.1` 之间逐字节一致的是 Discovery Manifest（v15）、打包的 Workflow 集合（core 5.2.3，因此一个 World 服务两条线）、稳定 Workflow 名称、Sandbox Provider 连接契约（除一个改名的选项）以及 Observer 钉住的 Instrumentation 表达式；Compiled Agent Manifest 从 54 变为 55，Session Checkpoint 从 17 变为 18。Peer Range 是两段的并集（`>=0.83.0 <0.84.0 || >=1.0.0-0 <1.1.0`），绝不是会放行 0.84 至 0.91 的外包络。`0.81.x`、`0.82.x`、`0.79.x`、`0.80.x`、`0.76.x`、`0.77.x`、`0.78.x`、`0.74.x`、`0.75.x`、`0.68.x`、`0.69.x` 至 `0.73.x`、`0.62.x`、`0.63.x` 至 `0.67.x`、`0.59.x` 至 `0.61.x` 以及 `0.48.x` 与 `0.58.x` 及更早的线一同留在窗口外；`1.1.x` 在通过矩阵之前不会被接纳。

UI 仅将最新支持线 `1.0.x` 标为绿色。Eve 0.83.x 保持可运行，不过会以红色显示并提醒升级；不受支持的版本同样显示为红色且继续阻断。

## 窗口基线

平台曾为更老 Eve 线保留的兼容路径已全部移除，以下能力是整个窗口的基线：

- Session 只按 ID 寻址。Continuation Token 已从平台中彻底消失：Token 列、基于 Token 的 Reset 翻译以及 `POST /eve/v1/session/reset` Token 路由都已删除。Clear、Compact 与 Reset 位于 `POST /eve/v1/session/:sessionId/{clear,compact,reset}`。
- `localDev()` 只看进程，在 `eve start` 下不放行任何请求；Eveland 上的 Agent 必须改用 `evelandIdentity()`、`httpBasic()` 或 OIDC。
- Channel 消息发送默认 `turnPolicy: "steer"`；Eveland 注入的 Scheduler Adapter 始终显式使用 `"queue"`，因此 Schedule 不会抢占用户正在等待的 Turn。
- 每个 Sandbox 在哪里运行由 Eveland 决定：它把受管的 bwrap Sandbox（`@evelandhq/sandbox-bwrap`）注入每个 Release。窗口内每条线编译的 Sandbox 模块都导出一个 Provider `environment` 和一个 `defineSandbox()` Selector（0.64 引入的形态），因此 Eveland 保留 Agent 自己编写的模块，只把它的 `eve/sandbox` 导入重定向，让每个内置 Provider（`DefaultSandbox`、`DockerSandbox`、`VercelSandbox`、`MicrosandboxSandbox`、`JustBashSandbox`）都改为构建 bwrap Environment（对 `eve/sandbox/microsandbox` 的导入——0.83 已连同该 Provider 一起移除这个入口——在两条线上仍会落到 bwrap）：Agent 编写的 `prepare` 与 Selector 照常运行，镜像、Dockerfile 等 Provider 专属选项被忽略；项目留空的 Sandbox 位置会得到一个生成的模块。`eve build` 会准备每个 Template 并记录准备它的 Provider；只要有任何 Sandbox 由其他 Provider 准备——在辅助文件里构建的 Environment、来自 `eve/sandbox/provider` 的自定义 Provider，或由 Extension 提供的 Sandbox——Eveland 就拒绝该 Release。Eveland 为 0.62.x 生成的对象形态 `defineSandbox({ backend })` 模块已随该线一起退役。0.75 把 Provider Handle 的生命周期 Hook 改了名（`onSessionStop()` / `onSessionDelete()` 变为 `onSandboxStop()` / `onSandboxDelete()`，不再回退到旧名字），并在 Durable Session 完成、过期或失败后释放它的 Sandbox——通过 Provider 可选的 `onSessionEnd()`，没有该方法时则先 Resume 再删除。0.83 替换了 Provider 契约本身：Provider 不再交给 eve 一个 Session Handle，而是交出一个字节级 Connection（`spawn`、`readFile`、`writeFiles`、`removePath`、`stop`、`close`），由 eve 据此派生 Session，并由 eve 自己为 Template 写入文件、运行 Agent 编写的 `prepare`；`start()` 变成以 Session Id 为键的 Upsert，`onSessionEnd()` 还会收到 `sandbox.delete()` 以及从未记录过 Sandbox 的 Session。注入的 `@evelandhq/sandbox-bwrap` 0.6.0 用同一个定义同时应答两种契约，并在两者下记录相同的 Session 状态，因此一份 Vendored 副本即可服务整个窗口，从 0.83 回滚到 0.81 的 Deployment 仍能打开它的 Session；它直接实现 `onSessionEnd()`：不 Resume 任何东西，直接移除该 Session 的 Workspace 与元数据，可安全重试，因此结束的 Session 在两条线上都会回收其 bwrap Workspace。Worker 拒绝 Vendor 不带 Connection 契约的副本。由于 Shim 在每条线上都构建 bwrap Environment，Session 把 Sandbox 记录在 `bwrap` 名下，而不是 0.83 的 `DefaultSandbox` 所记录的 `default`；0.83 在生产构建中不再回退到 just-bash，这一点也不会影响 Eveland。自 0.78 起 eve 的内置 Sandbox 会以 `AI_AGENT=eve` 运行命令；注入的 bwrap Sandbox 不设置它。
- 受支持的构建产出 Discovery Manifest v15；投影器只接受它（仅 0.45.0 产出的 v14 已随 0.45 线一起离开窗口）。v15 携带 `memories` 列表；0.62.0 在不再发现扁平的 `agent/instrumentation.ts` 时不再写入可选的 `instrumentation` 模块引用，且没有提升版本号，Eveland 也从未读取过该字段。
- Session Stream 在 0.83 上是 **v26**，在 1.0 上是 **v27**。v26（由 0.69 引入）每行一个事件，Append 事件只带 Delta，并以 `task.started`、`task.settled`、`agent.started` 与 `turn.waiting` 表示任务。v27（由 0.84 引入）每次状态变化写一条 Commit 行，包含它产生的全部 Fact（`{ at, facts }`），流式文本与工具输入作为单独的 Progress 记录发送，每个 Fact 以行号与行内序号定位而不是事件 ID（`startIndex` 按行计数），每个条目以一个带 `outcome` 的 Settled Fact 结束（`turn.settled`、`session.ended`、`call.settled`、`task.ended`、`interaction.settled`、`delivery.settled`）。Provider 用量是由 Model Run 拥有的独立 `usage.recorded` Fact；审批、提问、登录与预算提示统一为一个 `interaction`，以 `{ interactionId, optionId?, text? }` 作答。0.83 的 `eve/client` 读取 v21 至 v26，1.0 的只读取 v27，因此 Dashboard 的 Playground 同时打包两个 Client，并渲染与当前 Deployment 所跑 Eve 相匹配的那个。每个响应都在 `x-eve-stream-version` 中带上版本，Eveland 的 Playground 与 Agent Gateway 原样转发；自定义 NDJSON 消费者应继续读取它，而不是假设形状。两条线都带有 0.57 加入的可选 Transport Lease（`?streamControlVersion=1`：心跳，以及空闲 60 秒后的 `stream.lease-ended` 控制行）；v27 还会在跳过的行之后写入 `{"$eve":"position"}` 标记。Agent Gateway 原样转发 Query String，并保留自己的 5 秒心跳。
- Eve 的隐式默认 Model 在两条线上都是高推理强度的 `openai/gpt-6-luna-fast`；请显式钉住 `model` 以控制 Provider、行为与成本。
- Durable 委托与 Invocation Channel 属于基线：远端子 Session 流经父 Agent 在 `GET /eve/v1/session/:parentSessionId/subagents/:callId/:childSessionId/stream` 跟随、`operationId` 幂等创建 Session，以及 `mcpChannel()` 的 Durable Agent Tool 都走 Eveland 的 Durable Deployment 路由边界。在 1.0 上，根 Session 还会在 `GET /eve/v1/session/:sessionId/descendants/stream` 提供所有被跟随的后代，Agent Gateway 像 Session Stream 一样按根 Session 固定它；并在 `POST /eve/v1/session/:sessionId/end` 退役 Session，Agent Gateway 像 `reset`（仍作为别名提供）一样固定它。`POST /eve/v1/task-input/:token` 只由 0.83 提供；0.84 移除了它（它在没有认证的情况下结算审批），Agent Gateway 透明转发该路径，因此 1.0 的 Agent 会以自己的 404 应答。由于每条受支持的线都说这些路由，Agent Gateway 不再维护按操作划分的 Eve 版本下限——窗口本身就是闸门。
- 前端 `stop()` 已不存在；取消是 Durable、由 Hook 持有的 `cancel()` 命令。Eveland 的 Playground 会等待它（包括第一条事件确定 Durable Turn 之前的窗口），并在 Settlement 完成前保持 Stream Attached。
- Workflow 运行在存储 Spec v8（Hook 强制接管）上：自 `@evelandhq/workflow-world` 0.27.0 起，World 声明 `mintedSpecVersion()`（默认 8，Deployment 设置 `WORKFLOW_SEALED_LOG=0` 时为 6），用 0.18.0 到 0.26.x 构建的 Release 保留其 Spec 7（Sealed Log）的运行，用 0.17.0 及更早版本构建的 Release 保留其 Spec 6 的运行，因为平台同时接纳这三个世代。窗口内每条线的运行时都接受声明 6 到 8 的 World（0.81.1 与 0.75.1 一样自带 5.2 系列——core `5.2.0`、world 与 errors `5.0.3`、world-local `5.1.0`——0.83.3 自带它的补丁版本——core `5.2.3`、world 与 errors `5.0.5`、world-local `5.1.2`——Spec 范围相同），并且只比较 World 所声明 `@workflow/*` 的 Major 与 Prerelease 标签（Eve 自带的 Bundle 在 0.61.0 移到 `5.0.0-beta.53/21/36/45`，0.62.0 带的就是它；0.64.0 又移到 `5.0.0-beta.55/22/37/46`，其中的 `@workflow/world` 新增了一个可选的 `invoke` 能力，Eveland 的 World 不声明它；0.66.3 再移到 `5.0.0-beta.56/23/38/47`，其中的 `@workflow/world` 铸造 Spec 8——Hook 强制接管的读取者契约，另一个 Run 可以用 `createHook({ experimental_force: true })` 接管某个 Hook 的 Token；0.67.2 又移到 `5.0.0-beta.57/24/39/48`，所有 Spec 常量原地不动，0.68.0 带的就是它；0.70.2 再移到同一组的稳定版 `5.0.1`，所有 Spec 常量原地不动、只新增可选的 World 成员，0.72.1 带的就是它；0.73.0 再移到 core `5.1.0` 与 world、world-local、errors `5.0.2`（0.74.0 与 0.75.0 带的是同一组），World 调用与 Spec 常量不变，只新增可选成员（Stream Writer 的 `release`、建议性的 `afterStepBody` 标记、Hook 的 `nodeVersion`）；0.75.1 又移到稳定版 5.2 系列——core `5.2.0`、world 与 errors `5.0.3`、world-local `5.1.0`——World 调用与 Spec 常量依然不变，0.83.0 再移到它的补丁版本——core `5.2.3`、world 与 errors `5.0.5`、world-local `5.1.2`——只新增 Eveland 的 World 不声明的可选 World 成员（`regionForRunId`、`inBandFence` Capability、Queue 路由注册、投递次数元数据、事件写入上的 `eventCursor`）；任何一侧是稳定版时都与同一 Major 的任何 Prerelease 匹配），因此同一个 World 能服务两条线。平台为每个新构建注入 `@evelandhq/workflow-world@0.28.0`，它钉住 0.83 自带的 `@workflow/world` 5.0.5 与 `@workflow/world-local` 5.1.2（0.27.0 钉住的是 0.81 的 5.0.3 与 5.1.0，World 调用相同），声明 `capabilities.deploymentAffinity`，使 eve 无论 Eve 版本如何都在持有 Session 的 Deployment 上继续它（见 0.81.x 条目），声明并实现 `capabilities.hookForceClaim`——`createHook({ experimental_force: true })` 从打戳 8 及以上、仍在运行的 Run 接管 Token 时，先在该 Run 的日志里写入带 `forceClaimedBy` 的 `hook_disposed`，再改指 Token；对打戳低于 8、仍在运行的 Run 则以带 `forceRefusedReason: "victim-spec-version"` 的 `hook_conflict` 拒绝；已解析到旧持有者的投递会得到 `HookForceClaimedError`，从而跟随 Token——eve 0.81.1 及之后的版本需要它才能把 Session 移到新的 Run（见 0.81.x 条目），并且对运行时以 `resolveData: "skip-step-inputs"` 发出的事件读取，应答与对 `"all"` 完全相同；0.23.0 到 0.26.x 在 0.62.0（其运行时会在启动时拒绝高于 7 的 World）仍在窗口内时把声明上限定在 Spec 7，也从不接管 Hook Token。它还改用 Node 核心 HTTP 客户端投递被持有的 Dispatch，运行超过五分钟的 Step 不会再被全局 `fetch` 的 300 秒期限截断并重投，把跨 Deployment 的 `start()` 投递给它所指定的 Deployment 而不是发起入队的那个，把一分钟以后才到期的投递挪出 Run 的队列、到期再放回（自 0.26.0 起，休眠中的 Session 不再让 Dispatcher 的每次 Claim 多锁一行），在 Run 的队列被正在运行的 Step 占住时让 Hook 唤醒越过它、使取消能中止这个 Step 而不是等它跑完（自 0.26.1 起），不受 0.83 拒绝未经认证的 `/.well-known/workflow/v1/flow` 请求的影响——eve 只把这项检查接在它自己的 Local World 上，Dispatcher 的投递照常送达——并且（自 0.21.0 起）在同一个事务里提交一个 Run 及其 `run_created` 事件；`@workflow/world-postgres@5.0.0-beta.34` 只存在于历史 Release 中，从不为新构建选用。更老的 Spec v5 World 会在启动门禁处失败。共享 World 还通过 Snapshot 剥离、Block 打包、Checkpoint 与截止期驱动的 Retention 约束物理 Stream 存储。
- MCP Channel 默认 `/eve/v1/mcp` 且可声明其他 `route`；Eveland 的路径透明 Agent Gateway 会保留任一路径及对应的 OAuth Protected-resource Metadata Route。
- Durable Tool 用 `eve/tools` 的 `defineWorkflowTool` 声明，委托写法是 `ctx.agent()`——`ctx.agent(name)` 返回一个 Session，其 `send(message, { outputSchema })` 给出一个 Response，用 `result()` 取得该 Turn 的结果；Eve 自行推导可重放的调用身份；父 Turn 上的 Workflow Tool 经由一个有序 Inbox 处理、重试的 Dispatch 可能再开一个 Run，`defaultTools: false` 可让 Agent 跳过 Eve 的可选默认工具。`experimental.workflow.retention: 0` 与 `experimental.workflow.modelCallsPerStep` 在整个窗口内都是可选的 Agent 选项：Retention 偏好以保留属性 `$retention` 记录在 Run 上，Eveland 的共享 World 会存储但不执行它，而更大的 Step 批次会在中断后扩大重放单元。
- `task_update` 工具、其子到父的进度回调以及后台任务在整个窗口内都已不存在：一次调用会占住所在 Turn，直到它结束（0.83 上是 `task.settled`，1.0 上是 `call.settled` 与 `task.ended`；见 0.83.x 条目）。
- OpenTelemetry Agent Trace Schema 在整个窗口内都是 4：每次 Activation 都是按 `gen_ai.conversation.id` 分组的 `invoke_agent` Span，模型输入只以 `gen_ai.input.messages` 记录一次，Memory 的 Recall/Capture 有自己的 Span 与 `memory.operation.*` Hook 事件。Eveland 的 Observer 与 Collector 映射不依赖任何 Schema 4 之前的名字，但基于 Agent 自己 `otel()` 导出搭建的 Dashboard 必须面向 Schema 4。
- Extension 契约：0.84 把按能力划分的契约 Epoch 换成了构建该 Extension 分发包所用的 Eve 版本与分发代际，1.0 在加载任何 Extension 代码前就会以重建提示拒绝基于 Epoch 的 Manifest。因此预构建的 Extension 必须针对项目所用的线重新构建（为 0.83 构建的不能在 1.0 上加载）；Eveland 自己注入的 Extension 在每个 Release 内从源码编译，不受影响。
- Extension 可以提供 Channel、Schedule 与带命名空间的 Subagent；其完整的平台调度与观察集成作为单独的兼容性跟进交付。
- `chatgpt()` 是稳定 API，由 Codex 负责认证——但 ChatGPT 订阅模型在设计上仅限本地：Eveland Deployment 内没有 Codex 登录，钉住 `chatgpt()` 的 Agent 可以部署成功但会在运行期失败。部署的 Agent 请使用 AI Gateway 或服务端认证的 Model。
- `glob` 与 `grep` 不在默认 Agent 工具集中；依赖它们的 Agent 必须在对应 Tool 文件从 `eve/tools/glob` / `eve/tools/grep` 再导出提供的定义（`defineGlobTool()` / `defineGrepTool()` 工厂已随 0.44 一起移出窗口）。
- 子 Agent 可以通过导出 `defineParentSandbox()` 共享发起调用的父 Agent 的活 Sandbox；这样的子 Agent 不能再声明受管 Workspace 或 Skill 资源，Eveland 的平台 Sandbox 照常作用于父 Agent。

## 窗口内各版本支持情况

Observer 的 Instrumentation 钉点都与 0.75.1 逐字节相同；Extension 契约只新增版本（`tool` 84、`dynamicTool` 77、`channel` 56、`schedule` 29、`subagent` 33、`connection` 45、`hook` 43、`skill` 3、`dynamicSkill` Channel 地址发来的消息则开启一个注明 `predecessor` 的新 Session——而不是继续它。Eveland 让不同 Eve 版本的 Deployment 并行运行，它的 Dispatcher 本来就会把每个 Run 投递给其记录的 Deployment，因此 `@evelandhq/workflow-world` 0.25.0 声明了这一能力：跨越改变 Eve 版本的 Promote，Session 仍在持有它的 Deployment 上继续，与更早的线一致；用更老的 World 构建的 0.76.2 或 0.76.3 Release 在重建之前仍会重置这类 Session。获批的调用现在总是以发起该 Turn 的主体身份运行：他人批准的调用不再以批准人的身份与凭据运行（推翻了上文 0.72 的规则），获批的 Workflow 与 Agent 调用在派发前会被再次检查，`response` 策略仍可检查 `response.principal`。当 Channel 的 `fetchFile` 什么都没返回时，eve 会自己下载附件链接（仅限公开的 `https:` 链接，每个链接 25 MB、30 秒，每条消息最多 10 个）；每个附件都会带着它的 Sandbox 路径标签送达模型，只有不超过 3 MiB 且每边不超过 8000 像素的 PNG、JPEG、GIF、WebP 图片以及不超过 20 MiB 的 PDF 会以字节形式送给模型，`read_file` 会把 PDF 作为文件返回（其输出的 `image` 字段改名为 `file`）。`message.received` 的文件部件不再回显 `data:` URL，因此 Playground 回放这类附件时显示图标而不是缩略图。`turn.failed` 带上 `terminal`（随后有 `session.failed` 时为 true），`session.started` 带上替代 Session 所注明的 `predecessor`，模型步骤停在阻塞式 Workflow 调用上时现在也会发出 `on: "tasks"` 的 `turn.waiting`；Eveland 不读取这些新字段，并继续把等待自身 Task 的 Session 标为运行中。动态 Resolver 不再自行加入 Catalog 工具——eve 会在 Session 遇到它们能找到的东西时才加入 `eve__search`、`eve__tool` 与 `eve__skill`——`eve__search` 的结果会报告 `searched` 与 `remaining`。10 分钟没有任何输出的模型流会被放弃并重试，使用 0.77 及以后版本的 Agent 必须解析到 `ai` 7.0.137 或更新版本。0.79 把 eve 自己的 Span 移到共享的 Tracing 库上，Trace Schema 4 不变；Eveland 的 Observer 在私有 Provider 上依据 Stream 事件构建 Span，它的 Instrumentation 钉点仍然匹配。审批策略会收到被调用 MCP 工具的 `toolAnnotations`，工具可以定义感知输入的 `approval.prompt`，`eve/evals` 新增 `t.score()`，`eve/tanstack` 可以把 Agent 托管在 TanStack Start 应用内。Extension 契约只新增了版本（`tool` 88、`dynamicTool` 83、`channel` 60、`schedule` 32、`subagent` 37、`connection` 48、`hook` 45、`skill` 3、`dynamicSkill` 37、`dynamicInstructions` 38、`state` 13），因此 0.76 的构建仍能加载。0.79.1 让获批的 `defineTool` 调用可以从 `ctx.approval.responder` 读取批准人，调用本身仍以请求者身份运行；读取已超过 World 保留期的 Session Stream 会得到带 `code: "session_expired"` 的 `410`。0.79.2 把 Session Checkpoint 移到 15，是从 14 的真正升级（Session 留在自己的 Deployment 上，Eveland 从不跨越它），为 `action.result` 新增可选的 `error.name`，并在 Sandbox 无法恢复时把附件变为一条说明，而不是让 Step 失败。0.80 与 0.81 沿用 0.79 的执行模型，并让 Message Stream（v26）、Discovery Manifest（v15）、Compiled Manifest（54）、Hook、`eve/channels/auth`、Eveland 转发的路由、稳定的 Session 与 Tool Workflow 名称、Sandbox Provider API 以及自带的 Workflow 版本组（稳定版 5.2 系列）都与 0.79.0 逐字节相同；Session Checkpoint 仍为 15。0.81.1 把 Session Handoff 改建在 Hook 强制接管之上：Session 移到新的 Workflow Run 时——压缩之后，或移到另一个 Deployment 时——后继 Run 以 `createHook({ experimental_force: true })` 接管 Session 的收件 Token，因此 Session 在迁移期间仍能接收消息，而不是回答 `409 session_not_ready`。只有当 World 同时声明 `capabilities.hookForceClaim` 与有效的 `hookRetention` 时 eve 才这样做；否则它记录 `session handoff unavailable`，让 Session 终生留在第一个 Run 里，其事件日志不断增长，直到 World 的单 Run 事件上限让它失败。`@evelandhq/workflow-world` 0.27.0 声明并实现了这一能力（见窗口基线），因此在 Eveland 上，压缩后的空闲 Session 仍会移到同一 Deployment 上的新 Run，保留其 ID、Stream 与 Deployment 绑定；Deployment Handoff 依然不生效，因为 Eveland 把每个 Session 绑定在它的 Deployment 上。在 0.81.0 及更早版本上开始的 Session，第一次迁移仍走旧方式。0.80 会在 Run 结束时请求 World 删除未完整记录 Trace 的 Run 的数据（Run 带有 `$retention: "0"`；设置 `experimental.workflow.retention: "default"` 可以退出）；共享 World 不读取这一属性，仍按自己的保留类别处理，因此不会提前删除任何数据。`authorization.required` 与 `authorization.completed` 新增 `grant` 与 Connection 主体（`{ type: "app" }` 或 `{ type: "user", id, issuer }`），失败的 `authorization.completed` 新增 `retryable`；被登录打断的调用现在会在其 Step 中等待，登录回调后自行运行，并在其 `action.result` 之前报告 `authorization.completed`。Eveland 只读取结果、显示名称与描述，因此投影不变。工具审批由第一个回答决定，对有请求者的调用，未认证的回答会被拒绝。实验性的 Connect 托管事件订阅（MCP Connection 上的 `experimental_events`，需要 `@vercel/connect` 2.5.2 或更新版本）新增两个稳定 Workflow——每个订阅一个所有者 Run、每个投递事件一个 Run，二者都已做过保留审计——以及一个公开的 `POST /eve/v1/hooks/:connection` 接收端，Agent Gateway 像转发其他公开请求一样转发它，不绑定 Session。订阅可以要求存活至多 365 天或直到停止；在 Eveland 上，其所有者 Run 继承发起 Session 的保留类别，因此会在该类别的截止期被回收。定时 Session 可以使用动态 Schedule 工具，Eveland 的调度器仍会因其没有声明静态 `cron` 而在构建时拒绝。eve 自己的 Tracing 在 0.80.1 移到自带的 `@vercel/agent-runs`，Observer 钉住的 Instrumentation 表达式仍然匹配。`eve/client` 新增 `closeStream()` 与 `followIdle` 选项，`git({ github })` 新增 `authorize` 回调，MCP Connection 在每次请求前刷新 Token 并在 Step 结束时关闭远端 Session，压缩会保留超大工具结果的开头与结尾，可选的 `chat` Peer 必须为 4.42.0 或更新版本。Extension 契约只新增了版本（`tool` 93、`dynamicTool` 87、`channel` 62、`schedule` 34、`subagent` 39、`connection` 51、`hook` 47、`skill` 3、`dynamicSkill` 39、`dynamicInstructions` 40、`state` 13），因此 0.79 的构建仍能加载。0.82 与 0.83 沿用 0.81 的执行模型，并让 Message Stream（v26，因此 Dashboard 的 Playground Client 能服务两条线）、Discovery Manifest（v15）、Compiled Manifest（54）、Hook 入口、`eve/client` 的 Stream Reader、Eveland 转发的路由、稳定的 Workflow 名称、Observer 钉住的 Instrumentation 表达式，以及 Session Handoff 的 Force-claim 与 Deployment Affinity 门槛都与 0.81.1 逐字节相同。Session Checkpoint 在 0.82 移到 16、在 0.83 移到 17；Session 始终留在自己的 Deployment 上，因此 Eveland 不会跨越这两处边界。0.82 新增 `history.imported` 事件，用于 Channel 把此前的消息作为真实 Turn 补入（`send({ history })`、Channel Address 上的 `create()`），Eveland 的投影都不读取它；以单个 `limits.sessionUsage` 函数取代 `limits.maxInputTokensPerSession`、`maxOutputTokensPerSession` 与 `maxTokenCostUsdPerSession`（默认每个窗口 4000 万新输入 Token，不再计入 Cache 读取），并以 `SESSION_USAGE_LIMIT_REACHED` 取代 `SESSION_TOKEN_*` 失败码；把 `limits.sessionTimeoutMs` 改为每当 Turn 结束就重新计时的空闲超时，因此仍在使用的 Session 不会再在创建 30 天后结束；Channel 与 Session 的发送接受 `idempotencyKey`，在共享 World 上于 Session 的近期 Key 窗口内对重试去重，不需要新的 World 调用。自托管的 `eve build` 会把由内容派生的构建身份暴露为 `WORKFLOW_DEPLOYMENT_ID`；Eveland 及其 World 读取的任何东西都不以它为键。0.83 自带 Workflow 5.2 系列的一个补丁版本（core 5.2.3、world 5.0.5、world-local 5.1.2；见窗口基线），并且只有在运行 eve 自己的 Local World 时才拒绝不是来自其自身队列的 `eve/sandbox/microsandbox`，并在生产构建中不再回退到 just-bash；注入的 `@evelandhq/sandbox-bwrap` 0.6.0 同时应答两种契约（见窗口基线）。它还丢弃了 Extension 契约 `state` 13，因此在 0.81 上构建的 Extension 必须重新构建。`prewarm()` 可以用不带 Body 的 `POST /eve/v1/session/:sessionId` 为已有 Session 预备一个空闲的 Owner；Agent Gateway 把它归类为 Continuation，并转发到该 Session 绑定的 Deployment，因此预热永远不会移动 Session。在 `eve dev` 上，`localDev()` 拒绝来自其他机器的调用方，以及浏览器代表其他站点发出的请求；Eveland 上的 Agent 使用 `evelandIdentity()`、`httpBasic()` 或 OIDC 认证，因此已部署的内容没有变化。Connection 工具调用在五分钟没有回应后失败，OpenAPI Connection 只在基础 URL 的 Origin 内跟随重定向，父 Agent 发给子 Agent 的消息不再回答子 Agent 待处理的审批；Compaction 在摘要旁最多保留最近对话的 20,000 个 Token，无法把历史压到阈值以下时直接让 Session 失败而不重试。`eve start --no-schedules` 与 `EVE_SCHEDULES_DISABLED=1` 会阻止 Agent 编写的 Cron Schedule 触发；Eveland 本来就用自己的 Scheduler Channel 取代了它们。Extension 契约位于 `tool` 102、`dynamicTool` 92、`channel` 69、`schedule` 37、`subagent` 41、`connection` 57、`hook` 51、`dynamicSkill` 40、`dynamicInstructions` 41 与 `state` 16。
- **Eve 1.0.x（推荐，验证版本 `1.0.0-rc.1`；v27 Session 协议）**：Eve 1.0 把稳定 API 纳入 Semver（见其 Stability Policy）；1.0.0-rc.1 在 Eveland 读取的每个面上都与 0.91.0 逐字节一致。把 Agent 从 0.83 迁移过来，需要按 Eve 自己的"Upgrade to 1.0"指南进行；与平台相关的部分是：（1）**Session 事件是 v27**（见上面的基线）。Hook 仍是 `(event, ctx)`，但收到的是 v27 Fact，并带有 `ctx.position` 与 `ctx.view`；未处理的 Hook 错误现在会让正在运行的 Turn 失败。Eveland 注入的 Observer 读取两套词汇，且从不抛出。（2）**编写**：构建会拒绝不是 `defineAgent(...)` 的 `agent.ts`、不是 `defineMcpClientConnection` / `defineOpenAPIConnection` 的 Connection，以及与 `agent/sandbox/` 并列的 `agent/sandbox.ts`；`sleep`、`askQuestion` 与 `noReply` 直接导出而不再调用；Durable 原语来自 `eve/workflow` 与 `eve/workflow/api`（裸 `workflow` 导入会失败）；`compaction.thresholdPercent` 改为 `compaction.threshold`（0–1 的比例）；Schedule 的提示词是 `content` 而不是 `markdown`，`send()` 解析为 `Delivery`（`sessionId`）而不是 Session——Eveland 注入的 Scheduler Channel 在两条线上都能读取。`defineChannel` 不再读取 `kindHint`；每个 Channel 的 Kind 都是 `channel:<name>`（HTTP Channel 是 `channel:eve`），Session 投影按该名称归类 Trigger。（3）**HTTP**：eve Channel 以 400 拒绝未知的顶层 Body 字段，并以 `answers` 代替 `inputResponses`；`reset` 改为 `end`（旧路径保留为别名）；`GET /eve/v1/info` 现在只应答运维身份（service、runtime 或 `localDev()` 调用方），Eveland 从不调用它；Client 默认拒绝重定向。（4）**Sandbox**：Provider 连接契约保留 0.83 的形状，但把 `abortSignal` 改名为 `signal`，并新增可选的 `spawn({ stdin: true })`。Worker 注入的 `@evelandhq/sandbox-bwrap` 0.7.0 同时读取两种 Signal 名称，并实现了 `spawn({ stdin: true })`（以管道接通的 stdin，关闭即发送 EOF），因此注入的 bwrap Sandbox 在两条线上都能工作，包括 stdin。（5）**Workflow**：打包的 Workflow 集合与 0.83.3 逐字节一致（core 5.2.3、world 5.0.5、Spec 6–8），因此 `@evelandhq/workflow-world` 0.28.0 无需修改即可服务两条线，Dispatcher 不受影响。Session Checkpoint 为 18。（6）**跨版本 Session 迁移**：自 0.85 起，v27 Deployment 能导入 0.69–0.83 的 Checkpoint，因此空闲的 0.83 Session 若其 Owner 收到由另一个 Deployment 接收的投递——1.0 Release 被提升后，来自未固定的 Channel 入口、`ctx.to()` 或 Schedule，绝不会来自 Agent Gateway 固定的流量——就会迁移到 1.0 Deployment，并在途中被压缩（已记住的审批与用量限额重新开始）。迁移是单向的，因此 Session 投影会在 1.0 Deployment 第一次报告该 Session 时，把 SessionBinding 改指过去，续写、Stream、Playground Client 与保留策略都随之跟进。（7）**用量**：Provider 用量以由 Model Run 拥有的 `usage.recorded` 到达；Eveland 每个 Run 存一行用量（`run_key`），只计入 Run 与 Change 拥有的记录（Call 拥有的记录是在重报子 Session 自己的花费），并且由于 v27 会把缺失的 Token 数填为零，没有记录的 Model Run 被视为用量缺失。（8）**构建**：Dynamic Model 从构建时记录的 AI Gateway Catalog 读取 Context Window，因此无网络的构建需要缓存该 Catalog 或设置 `modelContextWindowTokens`；`eve start` 不再把 `CI` 与 `NITRO_UNIX_SOCKET` 传给服务端。对当前最新线，Agent 项目应刷新 Lockfile 并重新部署，才能实际获得 `1.0.0-rc.1`。

npm 上出现新版本并不自动扩大窗口。新的 Minor 只有在 Changelog 与源码审阅加上完整兼容矩阵之后才会进入；移除旧 Minor 同样是显式的产品变更。

## 强制执行点

当依赖缺失、超出窗口或无法证明兼容时，Eveland 在以下环节 Fail Closed：

- Source Import 与 Preflight
- Build 与 Restart
- 冷激活（构建时装入窗口外 Eve 版本的 Release 在激活请求时即被终态拒绝：绑定它的 Workflow Run 只会被 Dead-letter 一次，而不是每次冷启动后反复重试）
- Playground 流量
- 公开 Session 的 Create、Continue、Cancel 与 Stream
- 公开 Session Reset
- 到达所选 Deployment 的其余全部公开 Agent Gateway 请求，包括自定义 Channel Route 与 Webhook（休眠的窗口外 Deployment 直接回答 409，而不会被唤醒）
- Schedule Execution

诊断信息会请项目所有者升级，而不是猜测旧协议。在生产环境升级 Eve 或 Eveland 之前，请先阅读对应 Release Notes。
