2026-11-02 起已带上 1.0，因此每个 0.83 的 Release 都已有更新的线可供重建）、Eve 0.84 至 0.91（2026-11-02 跳过：每条都在数日内被取代，且它们与 1.0 说同一套 v27 Session 协议，而 1.0 是 Eve 第一条纳入 Semver 的线）、Eve 0.81（2026-11-02 随 1.0 进入而退役；Eveland v0.65.0 Schedule Execution。

项目 `package.json` 中允许的 Eve 依赖声明形式为：受支持线内的精确 Patch（`1.0.0-rc.2` 这类 Release Candidate 作为精确版本同样计入）、锚定在受支持 Minor Patch 上的 `~` Range、以及 `1.0` / `1.0.x` / `1.0.*`。`^1.x` Range 会覆盖之后所有 1.x Minor，因此被拒绝。缺少 Eve 依赖、跨 Minor 的宽泛 Range 或任何可能解析到窗口之外的声明都会 Fail Closed。项目 Overview、Source 与 Playground 会显示当前 Deployment 对应 Source Revision 的 Eve 依赖版本与平台要求。

窗口是一组经过验证的线，而不是"下限以上的一切"：`1.0.x` 于 2026-11-02（`1.0.0-rc.1` 发布两天后）进入，自 `0.83.x` 于 2026-11-04 退役起，它是唯一的线。SDK 的 Peer Range 为 `>=1.0.0-0 <2.0.0`；正是 `-0` 这个比较符让 npm 接受 1.0 的 Release Candidate。平台自身的 Peer Range 为 `>=1.0.0-0 <1.1.0`。`0.84.x` 至 `0.91.x` 与 1.0 说同一套 v27 Session 协议，但被跳过，与已退役的线一样以升级诊断拒绝。Release 构建于已退役线上的 Deployment，在 Eveland 带上更窄窗口后立即不可服务：Agent Gateway 以 409 应答，Activation 拒绝它，平台会结算仍停在其上的 Workflow Run 而不是反复重试。窗口内每条线都说 v27 Session 协议，因此注入的 Observer、Session/用量投影、Schedule 结果、Agent Gateway 的路由分类以及 Playground 唯一的 Eve Client 都只读取一套词汇。v26（Eve 0.83）Deployment 已记录的 Session 与用量依然可读：Session 回放、Trace 与用量视图会继续读取 Eveland 已存储的 v26 事件。`0.83.x`、`0.81.x`、`0.82.x`、`0.79.x`、`0.80.x`、`0.76.x`、`0.77.x`、`0.78.x`、`0.74.x`、`0.75.x`、`0.68.x`、`0.69.x` 至 `0.73.x`、`0.62.x`、`0.63.x` 至 `0.67.x`、`0.59.x` 至 `0.61.x` 以及 `0.48.x` 与 `0.58.x` 及更早版本一样留在窗口之外；`1.1.x` 在通过矩阵之前不会被接纳。

UI 仅将最新支持线 `1.0.x` 标为绿色；不受支持的版本（包括已退役的 0.83.x）显示为红色且继续阻断。

## 窗口基线

平台曾为更老 Eve 线保留的兼容路径已全部移除，以下能力是整个窗口的基线：

- Session 只按 ID 寻址。Continuation Token 已从平台中彻底消失：Token 列、基于 Token 的 Reset 翻译以及 `POST /eve/v1/session/reset` Token 路由都已删除。Clear、Compact 与 Reset 位于 `POST /eve/v1/session/:sessionId/{clear,compact,reset}`。
- `localDev()` 只看进程，在 `eve start` 下不放行任何请求；Eveland 上的 Agent 必须改用 `evelandIdentity()`、`httpBasic()` 或 OIDC。
- Channel 消息发送默认 `turnPolicy: "steer"`；Eveland 注入的 Scheduler Adapter 始终显式使用 `"queue"`，因此 Schedule 不会抢占用户正在等待的 Turn。
- 每个 Sandbox 在哪里运行由 Eveland 决定：它把受管的 bwrap Sandbox（`@evelandhq/sandbox-bwrap`）注入每个 Release。1.0 编译的 Sandbox 模块都导出一个 Provider `environment` 和一个 `defineSandbox()` Selector（0.64 引入的形态），因此 Eveland 保留 Agent 自己编写的模块，只把它的 `eve/sandbox` 导入重定向，让每个内置 Provider（`DefaultSandbox`、`DockerSandbox`、`VercelSandbox`、`MicrosandboxSandbox`、`JustBashSandbox`）都改为构建 bwrap Environment（对 `eve/sandbox/microsandbox` 的导入——0.83 已连同该 Provider 一起移除这个入口——仍会落到 bwrap）：Agent 编写的 `prepare` 与 Selector 照常运行，镜像、Dockerfile 等 Provider 专属选项被忽略；项目留空的 Sandbox 位置会得到一个生成的模块。`eve build` 会准备每个 Template 并记录准备它的 Provider；只要有任何 Sandbox 由其他 Provider 准备——在辅助文件里构建的 Environment、来自 `eve/sandbox/provider` 的自定义 Provider，或由 Extension 提供的 Sandbox——Eveland 就拒绝该 Release。Eveland 为 0.62.x 生成的对象形态 `defineSandbox({ backend })` 模块已随该线一起退役。Provider 契约是一个字节级 Connection（`spawn`、`readFile`、`writeFiles`、`removePath`、`stop`、`close`）：eve 从中推导出 Session，自己播种模板并运行 Agent 编写的 `prepare`，`start()` 是以 Session ID 为键的 Upsert，Durable Session 完成、过期或失败后，其 Sandbox 通过 Provider 的 `onSessionEnd()` 释放。注入的 `@evelandhq/sandbox-bwrap` 直接实现 `onSessionEnd()`：不 Resume 任何东西，直接移除该 Session 的 Workspace 与元数据，可安全重试，因此结束的 Session 会回收其 bwrap Workspace。Worker 拒绝 Vendor 不带 Connection 契约的副本。由于 Shim 总是构建 bwrap Environment，Session 把 Sandbox 记录在 `bwrap` 名下，而不是 eve 的 `DefaultSandbox` 所记录的 `default`；eve 在生产构建中不回退到 just-bash，这一点也不会影响 Eveland。自 0.78 起 eve 的内置 Sandbox 会以 `AI_AGENT=eve` 运行命令；注入的 bwrap Sandbox 不设置它。
- 受支持的构建产出 Discovery Manifest v15；投影器只接受它（仅 0.45.0 产出的 v14 已随 0.45 线一起离开窗口）。v15 携带 `memories` 列表；0.62.0 在不再发现扁平的 `agent/instrumentation.ts` 时不再写入可选的 `instrumentation` 模块引用，且没有提升版本号，Eveland 也从未读取过该字段。
- Session Stream 是 **v27**（由 0.84 引入）：每次状态变化写一行 Commit，包含它产生的全部 Fact（`{ at, facts }`），流式文本与工具输入作为单独的 Progress 记录发送，每个 Fact 以所在行与行内序号定位而不是事件 ID（`startIndex` 按行计数），每个条目以一个 Settled Fact 结束，其 `outcome` 说明结束方式（`turn.settled`、`session.ended`、`call.settled`、`task.ended`、`interaction.settled`、`delivery.settled`）。Provider 用量是由 Model Run 拥有的独立 `usage.recorded` Fact；审批、提问、登录与预算提示统一为一个 `interaction`，以 `{ interactionId, optionId?, text? }` 作答。1.0 的 `eve/client` 只读取 v27，Dashboard 的 Playground 打包的就是这一个 Client。每个响应都在 `x-eve-stream-version` 中带上版本，Eveland 的 Playground 与 Agent Gateway 原样转发；自定义 NDJSON 消费者应继续读取它，而不是假设形状。Stream 带有 0.57 加入的可选 Transport Lease（`?streamControlVersion=1`：心跳，以及空闲 60 秒后的 `stream.lease-ended` 控制行），并会在跳过的行之后写入 `{"$eve":"position"}` 标记。Agent Gateway 原样转发 Query String，并保留自己的 5 秒心跳。
- Eve 的隐式默认 Model 是高推理强度的 `openai/gpt-6-luna-fast`；请显式钉住 `model` 以控制 Provider、行为与成本。
- Durable 委托与 Invocation Channel 属于基线：远端子 Session 流经父 Agent 在 `GET /eve/v1/session/:parentSessionId/subagents/:callId/:childSessionId/stream` 跟随、`operationId` 幂等创建 Session，以及 `mcpChannel()` 的 Durable Agent Tool 都走 Eveland 的 Durable Deployment 路由边界。根 Session 还会在 `GET /eve/v1/session/:sessionId/descendants/stream` 提供所有被跟随的后代，Agent Gateway 像 Session Stream 一样按根 Session 固定它；并在 `POST /eve/v1/session/:sessionId/end` 退役 Session，Agent Gateway 像 `reset`（仍作为别名提供）一样固定它。0.84 移除了 `POST /eve/v1/task-input/:token`（它在没有认证的情况下结算审批），因此 1.0 的 Agent 会以自己的 404 应答。由于每条受支持的线都说这些路由，Agent Gateway 不再维护按操作划分的 Eve 版本下限——窗口本身就是闸门。
- 前端 `stop()` 已不存在；取消是 Durable、由 Hook 持有的 `cancel()` 命令。Eveland 的 Playground 会等待它（包括第一条事件确定 Durable Turn 之前的窗口），并在 Settlement 完成前保持 Stream Attached。
- Workflow 运行在存储 Spec v8（Hook 强制接管）上：自 `@evelandhq/workflow-world` 0.27.0 起，World 声明 `mintedSpecVersion()`（默认 8，Deployment 设置 `WORKFLOW_SEALED_LOG=0` 时为 6），用 0.18.0 到 0.26.x 构建的 Release 保留其 Spec 7（Sealed Log）的运行，用 0.17.0 及更早版本构建的 Release 保留其 Spec 6 的运行，因为平台同时接纳这三个世代。1.0 的运行时接受声明 6 到 8 的 World（它自带 core `5.2.3`、world 与 errors `5.0.5`、world-local `5.1.2`），并且只比较 World 所声明 `@workflow/*` 的 Major 与 Prerelease 标签（Eve 自带的 Bundle 在 0.61.0 移到 `5.0.0-beta.53/21/36/45`，0.62.0 带的就是它；0.64.0 又移到 `5.0.0-beta.55/22/37/46`，其中的 `@workflow/world` 新增了一个可选的 `invoke` 能力，Eveland 的 World 不声明它；0.66.3 再移到 `5.0.0-beta.56/23/38/47`，其中的 `@workflow/world` 铸造 Spec 8——Hook 强制接管的读取者契约，另一个 Run 可以用 `createHook({ experimental_force: true })` 接管某个 Hook 的 Token；0.67.2 又移到 `5.0.0-beta.57/24/39/48`，所有 Spec 常量原地不动，0.68.0 带的就是它；0.70.2 再移到同一组的稳定版 `5.0.1`，所有 Spec 常量原地不动、只新增可选的 World 成员，0.72.1 带的就是它；0.73.0 再移到 core `5.1.0` 与 world、world-local、errors `5.0.2`（0.74.0 与 0.75.0 带的是同一组），World 调用与 Spec 常量不变，只新增可选成员（Stream Writer 的 `release`、建议性的 `afterStepBody` 标记、Hook 的 `nodeVersion`）；0.75.1 又移到稳定版 5.2 系列——core `5.2.0`、world 与 errors `5.0.3`、world-local `5.1.0`——World 调用与 Spec 常量依然不变，0.83.0 再移到它的补丁版本——core `5.2.3`、world 与 errors `5.0.5`、world-local `5.1.2`——只新增 Eveland 的 World 不声明的可选 World 成员（`regionForRunId`、`inBandFence` Capability、Queue 路由注册、投递次数元数据、事件写入上的 `eventCursor`）；任何一侧是稳定版时都与同一 Major 的任何 Prerelease 匹配），因此同一个 World 能服务整个窗口。平台为每个新构建注入 `@evelandhq/workflow-world@0.29.0`，它钉住 1.0.0-rc.5 自带的 `@workflow/world` 5.1.0 与 `@workflow/world-local` 5.2.1（0.28.0 钉住的是 rc.1 与 rc.2 自带的 5.0.5 与 5.1.2，0.27.0 钉住的是 0.81 的 5.0.3 与 5.1.0，World 调用相同；World 5.1.0 只新增可选能力，0.29.0 一个都没有声明），声明 `capabilities.deploymentAffinity`，使 eve 无论 Eve 版本如何都在持有 Session 的 Deployment 上继续它（自 eve 0.76.1 起），声明并实现 `capabilities.hookForceClaim`——`createHook({ experimental_force: true })` 从打戳 8 及以上、仍在运行的 Run 接管 Token 时，先在该 Run 的日志里写入带 `forceClaimedBy` 的 `hook_disposed`，再改指 Token；对打戳低于 8、仍在运行的 Run 则以带 `forceRefusedReason: "victim-spec-version"` 的 `hook_conflict` 拒绝；已解析到旧持有者的投递会得到 `HookForceClaimedError`，从而跟随 Token——eve 0.81.1 及之后的版本需要它才能把 Session 移到新的 Run（自 eve 0.81.1 起），并且对运行时以 `resolveData: "skip-step-inputs"` 发出的事件读取，应答与对 `"all"` 完全相同；0.23.0 到 0.26.x 在 0.62.0（其运行时会在启动时拒绝高于 7 的 World）仍在窗口内时把声明上限定在 Spec 7，也从不接管 Hook Token。它还改用 Node 核心 HTTP 客户端投递被持有的 Dispatch，运行超过五分钟的 Step 不会再被全局 `fetch` 的 300 秒期限截断并重投，把跨 Deployment 的 `start()` 投递给它所指定的 Deployment 而不是发起入队的那个，把一分钟以后才到期的投递挪出 Run 的队列、到期再放回（自 0.26.0 起，休眠中的 Session 不再让 Dispatcher 的每次 Claim 多锁一行），在 Run 的队列被正在运行的 Step 占住时让 Hook 唤醒越过它、使取消能中止这个 Step 而不是等它跑完（自 0.26.1 起），不受 0.83 拒绝未经认证的 `/.well-known/workflow/v1/flow` 请求的影响——eve 只把这项检查接在它自己的 Local World 上，Dispatcher 的投递照常送达——并且（自 0.21.0 起）在同一个事务里提交一个 Run 及其 `run_created` 事件；`@workflow/world-postgres@5.0.0-beta.34` 只存在于历史 Release 中，从不为新构建选用。更老的 Spec v5 World 会在启动门禁处失败。共享 World 还通过 Snapshot 剥离、Block 打包、Checkpoint 与截止期驱动的 Retention 约束物理 Stream 存储。
- MCP Channel 默认 `/eve/v1/mcp` 且可声明其他 `route`；Eveland 的路径透明 Agent Gateway 会保留任一路径及对应的 OAuth Protected-resource Metadata Route。
- Durable Tool 用 `eve/tools` 的 `defineWorkflowTool` 声明，委托写法是 `ctx.agent()`——`ctx.agent(name)` 返回一个 Session，其 `send(message, { outputSchema })` 给出一个 Response，用 `result()` 取得该 Turn 的结果；Eve 自行推导可重放的调用身份；父 Turn 上的 Workflow Tool 经由一个有序 Inbox 处理、重试的 Dispatch 可能再开一个 Run，`defaultTools: false` 可让 Agent 跳过 Eve 的可选默认工具。`experimental.workflow.retention: 0` 与 `experimental.workflow.modelCallsPerStep` 在整个窗口内都是可选的 Agent 选项：Retention 偏好以保留属性 `$retention` 记录在 Run 上，Eveland 的共享 World 会存储但不执行它，而更大的 Step 批次会在中断后扩大重放单元。
- `task_update` 工具、其子到父的进度回调以及后台任务在整个窗口内都已不存在：一次调用会占住所在 Turn，直到它结束（`call.settled`，任务另有 `task.ended`）。
- OpenTelemetry Agent Trace Schema 在整个窗口内都是 4：每次 Activation 都是按 `gen_ai.conversation.id` 分组的 `invoke_agent` Span，模型输入只以 `gen_ai.input.messages` 记录一次，Memory 的 Recall/Capture 有自己的 Span 与 `memory.operation.*` Hook 事件。Eveland 的 Observer 与 Collector 映射不依赖任何 Schema 4 之前的名字，但基于 Agent 自己 `otel()` 导出搭建的 Dashboard 必须面向 Schema 4。
- Extension 契约：0.84 把按能力划分的契约 Epoch 换成了构建该 Extension 分发包所用的 Eve 版本与分发代际，1.0 在加载任何 Extension 代码前就会以重建提示拒绝基于 Epoch 的 Manifest。因此预构建的 Extension 必须针对项目所用的线重新构建（为 0.83 构建的不能在 1.0 上加载）；Eveland 自己注入的 Extension 在每个 Release 内从源码编译，不受影响。
- Extension 可以提供 Channel、Schedule 与带命名空间的 Subagent；其完整的平台调度与观察集成作为单独的兼容性跟进交付。
- `chatgpt()` 是稳定 API，由 Codex 负责认证——但 ChatGPT 订阅模型在设计上仅限本地：Eveland Deployment 内没有 Codex 登录，钉住 `chatgpt()` 的 Agent 可以部署成功但会在运行期失败。部署的 Agent 请使用 AI Gateway 或服务端认证的 Model。
- `glob` 与 `grep` 不在默认 Agent 工具集中；依赖它们的 Agent 必须在对应 Tool 文件从 `eve/tools/glob` / `eve/tools/grep` 再导出提供的定义（`defineGlobTool()` / `defineGrepTool()` 工厂已随 0.44 一起移出窗口）。
- 子 Agent 可以通过导出 `defineParentSandbox()` 共享发起调用的父 Agent 的活 Sandbox；这样的子 Agent 不能再声明受管 Workspace 或 Skill 资源，Eveland 的平台 Sandbox 照常作用于父 Agent。

## 窗口内各版本支持情况

- **Eve 1.0.x（推荐，验证版本 `1.0.0-rc.5`；v27 Session 协议）**：Eve 1.0 把稳定 API 纳入 Semver（见其 Stability Policy）；1.0.0-rc.1 在 Eveland 读取的每个面上都与 0.91.0 逐字节一致。1.0.0-rc.2（2026-11-03 验证）保持所有钉住的面不变——Discovery Manifest 15、Compiled Agent Manifest 55、Checkpoint 18、Stream 27、稳定 Workflow 名称以及全部依赖——并放宽了两个 v27 Fact：`call.requested` 可以由所在 Turn 拥有（`owner: { turnId }`），`content.completed` 可以不带 `runId`，由 `scope.turnId` 指明所在 Turn。Observer、Session 转录与 Trace 都把这两者归到所在 Turn 下。从 rc.2 起，`eve dev` 也会像 `eve start` 一样通过 `globalThis.AI_SDK_DEFAULT_PROVIDER` 解析字符串模型。1.0.0-rc.5（2026-11-05 验证；途中审阅了 rc.3 与 rc.4）保持 Stream 27 与 Session 协议不变，变化的是：Discovery Manifest 16，它把 Agent（以及每个 Extension Mount）编写的 Source 列在一个 `sources` 数组里，而不再按类别各一个数组——构建摘要与注入的 Scheduler 同时读取 15 和 16，因为窗口里有在两者上构建的 Release；Compiled Agent Manifest 56 与 Checkpoint 19；Nitro 3.0.261103-rc（Rolldown 1.2.16、srvx 1.0.8），已知路径对不支持的方法应答 405，而导入 `nitro/storage`、`nitro/kv`、`nitro/database` 或从包外导入资源会让构建失败；以及 `eve start` 在 SIGKILL 服务端之前改为等待 25 秒而不是 20 秒（平台的停止超时覆盖两者）。面向 Agent 作者的工具变化：rc.3 的 code Extension 去掉了 `code__grep` 与 `code__worker`；rc.4 为每个 Agent 提供默认的 `edit_file` 工具（凡是限制了 `write_file` 的地方，也要同样限制它），去掉 `code__apply_patch`，失败的 `bash` 结果以 `[exit code: N]` 结尾，命令在 60 秒（而不是 30 秒）后转入后台。仍在 0.83 上的 Agent 需要按 Eve 自己的"Upgrade to 1.0"指南迁移；与平台相关的部分是：（1）**Session 事件是 v27**（见上面的基线）。Hook 仍是 `(event, ctx)`，但收到的是 v27 Fact，并带有 `ctx.position` 与 `ctx.view`；未处理的 Hook 错误现在会让正在运行的 Turn 失败。Eveland 注入的 Observer 从不抛出。（2）**编写**：构建会拒绝不是 `defineAgent(...)` 的 `agent.ts`、不是 `defineMcpClientConnection` / `defineOpenAPIConnection` 的 Connection，以及与 `agent/sandbox/` 并列的 `agent/sandbox.ts`；`sleep`、`askQuestion` 与 `noReply` 直接导出而不再调用；Durable 原语来自 `eve/workflow` 与 `eve/workflow/api`（裸 `workflow` 导入会失败）；`compaction.thresholdPercent` 改为 `compaction.threshold`（0–1 的比例）；Schedule 的提示词是 `content` 而不是 `markdown`，`send()` 解析为 `Delivery`（`sessionId`）而不是 Session——Eveland 注入的 Scheduler Channel 读取的就是它。`defineChannel` 不再读取 `kindHint`；每个 Channel 的 Kind 都是 `channel:<name>`（HTTP Channel 是 `channel:eve`），Session 投影按该名称归类 Trigger。（3）**HTTP**：eve Channel 以 400 拒绝未知的顶层 Body 字段，并以 `answers` 代替 `inputResponses`；`reset` 改为 `end`（旧路径保留为别名）；`GET /eve/v1/info` 现在只应答运维身份（service、runtime 或 `localDev()` 调用方），Eveland 从不调用它；Client 默认拒绝重定向。（4）**Sandbox**：Provider 连接契约保留 0.83 的形状，但把 `abortSignal` 改名为 `signal`，并新增可选的 `spawn({ stdin: true })`。Worker 注入的 `@evelandhq/sandbox-bwrap` 0.7.0 同时读取两种 Signal 名称，并实现了 `spawn({ stdin: true })`（以管道接通的 stdin，关闭即发送 EOF）。（5）**Workflow**：rc.5 打包 core 5.4.0 与 world 5.1.0，由 `@evelandhq/workflow-world` 0.29.0 钉住（rc.1 与 rc.2 打包 core 5.2.3 与 world 5.0.5；eve 只比较 World 的 Major Line，因此同一个 World 能同时服务两者）；Session Checkpoint 为 19（rc.1 与 rc.2 上为 18）。eve 1.0 会请求 Spec 9 Run（`WORKFLOW_SPEC_VERSION=9`），这需要共享 World 尚未声明的 In-band Writer Fence，因此新 Run 仍是 Spec 8，运行时每个进程会记录一次相应日志。World 声明 `capabilities.deploymentAffinity`，因此 eve 总在持有 Session 的 Deployment 上继续它。（6）**用量**：Provider 用量以由 Model Run 拥有的 `usage.recorded` 到达；Eveland 每个 Run 存一行用量（`run_key`），只计入 Run 与 Change 拥有的记录（Call 拥有的记录是在重报子 Session 自己的花费），并且由于 v27 会把缺失的 Token 数填为零，没有记录的 Model Run 被视为用量缺失。（7）**构建**：Dynamic Model 从构建时记录的 AI Gateway Catalog 读取 Context Window，因此无网络的构建需要缓存该 Catalog 或设置 `modelContextWindowTokens`；`eve start` 不再把 `CI` 与 `NITRO_UNIX_SOCKET` 传给服务端。（8）**`eveland` SDK**：0.21.0 之前的 SDK 版本声明的 eve Peer 都低于 1.0，因此 npm 拒绝把它们与 eve 1.0 一起安装；导入 `eveland` 的 Agent 需随 `eveland@^0.21.0`（第一个 Peer 接受 1.0 的版本）一起迁到 1.0。Starter 模板（`eveland init` 复制的内容，也是内置 Agent 部署的内容）固定为 `1.0.0-rc.5` 与 `eveland@^0.21.0`。对当前最新线，Agent 项目应刷新 Lockfile 并重新部署，才能实际获得 `1.0.0-rc.5`。

npm 上出现新版本并不自动扩大窗口。新的 Minor 只有在 Changelog 与源码审阅加上完整兼容矩阵之后才会进入；移除旧 Minor 同样是显式的产品变更。

## 强制执行点

当依赖缺失、超出窗口或无法证明兼容时，Eveland 在以下环节 Fail Closed：

- Source Import 与 Preflight
- Build 与 Restart
- 冷激活（构建时装入窗口外 Eve 版本的 Release 在激活请求时即被终态拒绝：绑定它的 Workflow Run 只会被 Dead-letter 一次，而不是每次冷启动后反复重试）
- Playground 流量
- 公开 Session 的 Create、Continue、Cancel 与 Stream
- 公开 Session Reset
- 到达所选 Deployment 的其余全部公开 Agent Gateway 请求，包括自定义 Channel Route 与 Webhook（休眠的窗口外 Deployment 直接回答 409，而不会被唤醒）
- Schedule Execution

诊断信息会请项目所有者升级，而不是猜测旧协议。在生产环境升级 Eve 或 Eveland 之前，请先阅读对应 Release Notes。

## Model Gateway 依赖的 eve 行为

[Model Gateway](/zh/docs/reference/model-gateway) 依赖的几项 eve 行为不在 eve 的公开 API 承诺之内，所以扩大兼容窗口时，还要用真实安装运行 `pnpm --filter @evelandhq/worker smoke:model-gateway`（把 `EVE_VERSION` 设为候选版本）：

- `eve build` 信任预先写入、`fetchedAt` 在 5 分钟以内的 `.eve/cache/model-catalog.json`（`kind: "eve-model-catalog-cache"`，`version: 2`）；
- instrumentation 的 `setup` 在所有 instrumentation 模块加载完之后运行，`eve start` 通过 `globalThis.AI_SDK_DEFAULT_PROVIDER` 解析字符串模型 ID；
- eve 把 `providerMetadata.gateway.cost` 记为 `usage.recorded` 的 `costUsd`；
- `eve dev` 同样遵守默认 Provider（从 1.0.0-rc.2 起；vercel/eve#5787）。
