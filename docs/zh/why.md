> **一家企业最终运营的 Agent 数量将超过员工人数。**
>
> **Eveland 就是为那个世界而生的基础设施。**

今天，Eveland 为 Eve Agent 提供生产级自托管基础设施：既支持以十倍、百倍于团队规模运行 Agent 舰队，又让它们直接运行在企业自有的基础设施与数据环境中。

## 拥抱复数：运营一百个 Agent，而不是一个

真正将 Agent 引入业务的组织，最终拥有的绝不会只是*一个* Agent。重复性流程分布在每个部门——客服、市场、行政、财务——每个环节都值得拥有专属的 Agent。稳态之下，Agent 的数量必然超过员工人数。

这种“复数规模”会迅速压垮为单一用例设计的工具：为每个 Agent 单独维护部署脚本、登录入口、聊天界面与监控看板，乘以一百后几乎无法维系。

Eveland 从第一天起就为“复数”而建：导入一个项目，部署、域名路由、密钥管理、定时调度、用户身份与可观测性一应俱全——这些能力在平台层统一共享，无需每个 Agent 重复造轮子。这也是平台高度重视[运行时密度](/zh/docs/reference/design/runtime)的原因：当百个 Agent 共享一台机器时，基础设施本身多消耗一份资源，能跑的 Agent 就少一个。

## 就近运行：在你的基础设施上，与数据同在

除了数据主权与合规考量，工程上的理由更为直接：**Agent 只有紧邻业务系统时才能真正发挥作用。**

现代企业极少能将全部核心资产迁移至公有云——内部财务系统、经营数据库、自建业务系统往往保留在局域网或私有云中。脱离了这些环境，Agent 便寸步难行；而强迫内部系统向外部云平台妥协，成本极其高昂。Eveland 选择主动走向数据所在的地方。

此外，自托管带来了双重成本优势：

- **运行成本**：在托管平台上，LLM 调用网关、工作流状态存储、代码沙箱执行无一不是计量账单；而在自有硬件上，这些均属于已有算力。借助 [systemd 宿主机高密度运行时](/zh/docs/reference/design/runtime)、[轻量级 bubblewrap 沙箱](/zh/docs/reference/design/sandbox)、[按需激活与缩容至零](/zh/docs/reference/design/scale-to-zero)以及[外置轻量调度](/zh/docs/reference/design/workflow)，一台普通云服务器即可平稳承载数十个生产级 Agent。
- **管理与透明度**：托管平台通常只面向运维提供黑盒状态；业务人员难以看清 Agent 到底执行了什么。Eveland 为开发、运维和业务角色提供同一视角的清晰界面：会话树、推理链路、工具调用、定时记录与 Token 用量均为一等公民看板，底层由[透明的 OpenTelemetry 遥测管道](/zh/docs/reference/design/observability)与[零信任网关](/zh/docs/reference/design/gateway)提供保障。

## Eveland 的由来

通往真正自主运行的 Agent 之路漫长：我们经历过难以无人值守的编排框架、失败后无法追溯的运行器，以及各种过渡方案。

[Eve](https://eve.dev) 是首个符合我们期待的开源框架——“代码即 Agent”、执行可确定追溯、多模型与多云支持，适合以工程化方式演进。Eveland 则补全了从“本地开发调试完成”到“企业生产稳定交付”之间缺失的另一半拼图。

这不是纸上空谈。[金数据](https://jinshuju.net)在 Eveland 上稳定运行着 20+ 个生产 Agent——覆盖客服、市场、行政与财务职能，经受了持续数月的真实业务考验。平台中的绝大多数[设计决策](/zh/docs/reference/design)，均源于真实生产场景的倒逼与提炼。

## 适用对象

- **拥有重复性业务流程的团队**：借助现代 AI 编程助手，编写专属业务 Agent 的门槛正迅速降低；一人团队亦可拥有全天候值守的“数字团队”。
- **追求确定性与自主性的团队**：区别于普通的聊天助手，Eveland 上的 Agent 支持定时调度（Cron）、Webhook 与通道自主唤醒，无需人工守候；区别于玩具级运行器，Eveland 提供严格的进程隔离、确定性的故障恢复机制与工业级可观测性。

如果你正面临类似的生产交付挑战，欢迎从[部署 Eveland 平台](/zh/docs/production)开始，为你的第一支 Agent 舰队安家。
