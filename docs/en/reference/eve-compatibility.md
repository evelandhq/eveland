---
title: Eve compatibility
description: Understand Eveland's verified Eve version window and fail-closed policy.
---

Until Eve publishes a stable compatibility contract, Eveland supports only minor lines that have passed the complete compatibility matrix, and changes that window explicitly. The checked-in product contract supports `0.62.x` and `0.67.x`, verified at `0.62.0` and `0.67.0`. Eve 0.66 (retired on 2026-09-26 when 0.67 entered, two days after 0.66 itself had, before any Eveland release carried it), Eve 0.63, 0.64, and 0.65 (skipped on 2026-09-23 and 2026-09-24: 0.63.0 failed every session whose background subagent call met a hook subscribed to subagent events, which Eveland's own observer is, 0.64.0 shipped the fix, 0.65.0 superseded 0.64.1 within a day, and 0.66.0 superseded 0.65.0 within six hours, before any Eveland release carried any of them), Eve 0.58 (retired on 2026-09-23 when the window narrowed to the 0.62 floor), Eve 0.59, 0.60, and 0.61 (skipped on 2026-09-19: each was superseded within a day, before any Eveland release carried it), Eve 0.55 (retired on 2026-09-19 when 0.62 entered), Eve 0.56 and 0.57 (skipped on 2026-09-17: 0.58.0 superseded them before any Eveland release carried either), Eve 0.54 (retired on 2026-09-16 when 0.56 entered a window that was already two lines wide), Eve 0.52 and 0.53 (retired together on 2026-09-15), Eve 0.50 and 0.51 (retired together on 2026-09-12), Eve 0.49 (retired on 2026-09-07), Eve 0.48 (skipped when 0.49.0 superseded it on 2026-09-02, before any deployment ran on it), and Eve 0.47 and older are no longer accepted for import, build, restart, activation, Playground, Agent Gateway, or schedule execution.

The Eve dependency declarations a project's `package.json` may carry are: an exact patch inside a supported line, a `~`/`^` range anchored on a supported minor's patch, and the `0.62` / `0.62.x` / `0.62.*` and `0.67` / `0.67.x` / `0.67.*` forms. A missing Eve dependency, a broad cross-minor range, or any declaration that could resolve outside the window fails closed. The project Overview, Source, and Playground pages show the Eve dependency version of the current deployment's source revision alongside the platform requirement.

The window is a set of verified lines, not "everything at or above the floor": `0.67.x` entered on 2026-09-26, the day `0.67.0` was published, and `0.66.x` — which had entered two days earlier, on the day `0.66.1` was published — left with it; `0.63.x`, `0.64.x`, and `0.65.x` sit inside the hull but were never verified — 0.63.0 failed every session whose background subagent call met a hook subscribed to subagent events or `"*"` (Eveland's observer is such a hook), 0.64.0 shipped the fix three days later, 0.65.0 superseded 0.64.1 within a day, and 0.66.0 superseded 0.65.0 within six hours, before any Eveland release could carry them, and no release carried `0.66.x` either; all four are rejected with the same upgrade diagnostic as a retired line. `0.58.x` retired the same day, which makes `0.62.x` the floor (still verified at `0.62.0`) and moves the SDK's peer floor to `>=0.62.0`. A Deployment whose Release was built on a retired line stops being servable as soon as Eveland carries the narrower window: the Agent Gateway answers it with 409, activation refuses it, and the platform settles the workflow runs still parked on it instead of retrying them; Eve cannot continue a session under a different Eve version, so a rebuild starts new sessions rather than resuming those. The wire surfaces are unchanged between `0.62.0` and `0.67.0` — message stream v25, discovery manifest v15, the route set, and the unstamped workflow names apart from `taskRunWorkflow`, which 0.63 removed together with background `defineTool`; Workflow runs still stamp storage spec 7, which both lines read, although 0.66.3 taught the runtime to read spec 8 as well — so what separates the two lines is the sandbox API, background work, the built-in tool set, the skill and tool-schema surface, the session lifecycle (see the 0.67.x entry below), and the bundled Workflow set. Every line in the window acknowledges messages with a delivery id, so every accepted Deployment is reachable from the Playground. The peer range is the union of the two contiguous runs (`>=0.62.0 <0.63.0 || >=0.67.0 <0.68.0`), never their hull, which would admit the skipped lines. `0.59.x`, `0.60.x`, and `0.61.x` (skipped on 2026-09-19) and `0.48.x` — never verified, superseded by 0.49.0 within hours as 0.46, 0.43, and 0.40/0.41 were before it — stay below the floor together with `0.58.x`, `0.57.x`, `0.56.x`, `0.55.x`, `0.54.x`, `0.53.x`, `0.52.x`, `0.51.x`, `0.50.x`, `0.49.x`, `0.47.x`, and older; `0.68.x` is not admitted before it has passed the matrix.

The UI marks only the latest supported line, `0.67.x`, in green. Eve 0.62.x stays operational but appears in red with an upgrade reminder; unsupported versions also appear in red and remain blocked.

## Window baseline

Everything the platform once carried for older Eve lines is now the baseline of the whole window, and the pre-0.42 compatibility paths have been removed from Eveland entirely:

- Sessions are addressed only by their ID. Continuation tokens do not exist anywhere in the platform anymore: the token columns, the token-based reset translation, and the `POST /eve/v1/session/reset` token route are gone. Clear, compact, and reset live at `POST /eve/v1/session/:sessionId/{clear,compact,reset}`.
- `localDev()` is process-based and admits nothing under `eve start`; Agents on Eveland must authenticate with `evelandIdentity()`, `httpBasic()`, or OIDC.
- Channel message sends default to `turnPolicy: "steer"`; Eveland's injected scheduler adapter always asks for `"queue"` so a schedule never preempts a turn a person is waiting on.
- Eveland decides where every sandbox runs: it injects its managed bwrap sandbox (`@evelandhq/sandbox-bwrap`) into each Release, in the shape the Release's Eve line compiles, chosen from the Eve dependency the project declares. On 0.62.x it generates a `defineSandbox({ backend })` module that replaces an authored backend with the bwrap backend while keeping the authored `bootstrap()`, `onSession()`, `description`, and `revalidationKey`. On 0.67.x, where a sandbox module exports a provider `environment` and a `defineSandbox()` selector (the shape 0.64 introduced), it keeps an authored module and redirects its `eve/sandbox` imports so that every built-in provider (`DefaultSandbox`, `DockerSandbox`, `VercelSandbox`, `MicrosandboxSandbox`, `JustBashSandbox`) builds the bwrap environment instead: the authored `prepare` and selector still run, and provider-specific options such as images and Dockerfiles are ignored; a slot the project left empty gets a generated module. On 0.67.x `eve build` prepares every template and records the provider that prepared it, and Eveland refuses a Release in which any sandbox was prepared by another provider — an environment built in a helper file, a custom provider from `eve/sandbox/provider`, or a sandbox shipped by an Extension.
- Supported builds emit discovery manifest v15; the projector accepts nothing else (v14, emitted only by 0.45.0, left with the 0.45 line). v15 carries the `memories` list; 0.62.0 stopped writing its optional `instrumentation` module reference without a version bump when flat `agent/instrumentation.ts` stopped being discovered, and Eveland never read that field.
- The message stream protocol is uniform across this window: every supported line speaks **v25**, whose append events carry the delta alone (the v24 cumulative `messageSoFar` / `reasoningSoFar` snapshots and the UTF-16 `inputTextOffset` left with 0.49). Every response still carries the version in `x-eve-stream-version`, which Eveland's Playground and Agent Gateway forward verbatim; a custom NDJSON consumer should keep reading it rather than assuming the shape. Both lines carry the optional, separately negotiated transport lease 0.57 added on top of v25: a client that opts in with `?streamControlVersion=1` (the `eve/client` reader does so whenever reconnection is enabled and it reads from an absolute cursor) receives blank-line heartbeats every 10 seconds and, after 60 idle seconds, a `{"$eve":"stream.lease-ended","version":1}` control line that ends the response so the client reconnects from its cursor. The Agent Gateway forwards the query string verbatim and keeps its own 5-second heartbeat.
- Eve's implicit default model is `openai/gpt-5.6-luna-fast` on 0.62.x and `spacexai/grok-4.7` on 0.67.x; pin `model` explicitly to control provider, behavior, and cost.
- Durable background work and invocation channels are baseline: remote child streams follow through the parent at `GET /eve/v1/session/:parentSessionId/subagents/:callId/:childSessionId/stream`, create-once `operationId` sessions, `POST /eve/v1/task-input/:token` callbacks, and `mcpChannel()`'s durable agent tools all ride Eveland's durable Deployment routing boundary. Because every supported line speaks these routes, the Agent Gateway no longer maintains a per-operation Eve version floor — the window itself is the gate.
- Frontend `stop()` is gone; cancellation is the durable, hook-owned `cancel()` command. Eveland's Playground awaits it, including the interval before the first event identifies the durable turn, and keeps the stream attached through settlement.
- Workflow runs on storage spec v7, the sealed log: since `@evelandhq/workflow-world` 0.18.0 the World declares `mintedSpecVersion()` (7 by default, 6 for a Deployment that sets `WORKFLOW_SEALED_LOG=0`), and Releases built with 0.17.0 or earlier keep their spec-6 runs because the platform admits both generations. Every line's runtime accepts a World declaring 6 or 7 (0.62.0 reads 6 through 7, 0.67.0 6 through 8), and every line compares only the major and prerelease tag of the World's `@workflow/*` declaration (Eve's own bundled set moved to `5.0.0-beta.53/21/36/45` at 0.61.0, which is what 0.62.0 carries, to `5.0.0-beta.55/22/37/46` at 0.64.0, whose `@workflow/world` adds an optional `invoke` capability that Eveland's World does not declare, and to `5.0.0-beta.56/23/38/47` at 0.66.3, whose `@workflow/world` mints spec 8 — the hook force-claim reader contract, under which another run may take over a hook's token with `createHook({ experimental_force: true })` — which is what 0.67.0 carries), so one World serves both lines. The platform injects `@evelandhq/workflow-world@0.23.0` for every new build, whose `@workflow/world` beta.38 and `@workflow/world-local` beta.47 match what 0.67.x bundles while it keeps declaring spec 7 (`Math.min(mintedSpecVersion(), 7)`), because a runtime refuses a World above its ceiling at startup and 0.62.0's ceiling is 7, and because it never takes a hook token over — a forced creation is answered with an ordinary `hook_conflict`, so no run it stamps is ever stranded; and which delivers held dispatches over Node's core HTTP client so that a step running longer than five minutes is no longer cut off and redelivered by the 300-second deadline of the global `fetch`, addresses a cross-deployment `start()` to the Deployment it names instead of the one that enqueued it, and (since 0.21.0) commits a run and its `run_created` event in one transaction; `@workflow/world-postgres@5.0.0-beta.34` exists only in historical Releases and is never selected for a new build. Older spec-v5 worlds fail the startup guard. The shared World also bounds physical stream storage with snapshot stripping, block packing, checkpoints, and deadline-driven retention.
- MCP channels default to `/eve/v1/mcp` and may declare another `route`; Eveland's path-transparent Agent Gateway preserves either path and the corresponding OAuth protected-resource metadata route.
- Durable tools are declared with `defineWorkflowTool` from `eve/tools` and delegate with `ctx.agent(target, input)` — Eve derives the replay-stable invocation identity itself and an inline `outputSchema` types the result; workflow tools on the parent flow through one ordered inbox where a retried dispatch may start another run, and `defaultTools: false` opts an Agent out of Eve's optional default tools. `experimental.workflow.retention: 0` and `experimental.workflow.modelCallsPerStep` are opt-in Agent options across the window: the retention preference is recorded on the run as the reserved `$retention` attribute, which Eveland's shared World stores but does not enforce, and a larger step batch widens the replay unit after an interruption.
- The `task_update` tool and its child-to-parent progress callbacks are gone across the window; follow a background task through the child session's stream instead, and expect overlapping background-task results to reach the parent together across launch turns.
- The OpenTelemetry agent trace schema is 4 across the window: every activation is an `invoke_agent` span grouped by `gen_ai.conversation.id`, model input is recorded once as `gen_ai.input.messages`, and memory recall/capture emit their own spans and `memory.operation.*` hook events. Eveland's observer and collector mappings key on none of the pre-4 names, but a dashboard built on an Agent's own `otel()` export must target schema 4.
- The `tool`, `dynamicTool`, `channel`, `connection`, `hook`, and `state` extension contracts drop versions as Eve reworks them, and 0.67.x refuses every one of them that a 0.62.x build emits: 0.63 dropped `tool` 28, 44–46, and 49–52, `dynamicTool` 28–30, 41, and 48–50, and `channel` 23–26 when it removed background `defineTool` and `TaskExec` and stopped exposing executor bindings in task views, and 0.64 dropped `tool` 53, `dynamicTool` 51, `channel` 27–28, `connection` 23, `hook` 24, and `state` 6 when sandbox sessions stopped exposing a core identity and mutable networking became provider-specific. 0.67.0 is at `tool` 58, `dynamicTool` 56, `channel` 33, `schedule` 16, `subagent` 21, `connection` 28, `hook` 28, `skill` 2, `dynamicSkill` 23, `dynamicInstructions` 24, and `state` 9 (0.65 added `tool` 55, 0.66 added `tool` 57, `dynamicTool` 54, `channel` 31, `connection` 26, `hook` 27, `skill` 2, and `state` 9, and 0.67 added `tool` 58, `dynamicTool` 56, `channel` 33, `schedule` 16, `subagent` 21, `connection` 28, `hook` 28, `dynamicSkill` 23, and `dynamicInstructions` 24, none of them dropping anything, so a 0.65.x or 0.66.x build still loads), and still loads the `schedule`, `subagent`, `dynamicSkill`, and `dynamicInstructions` contracts a 0.62.x build emits. A prebuilt Extension must therefore be rebuilt against the line the project builds on; Extensions Eveland injects itself are compiled from source and unaffected. Eve's CLI reports usage to Vercel unless `EVE_TELEMETRY_DISABLED` is set; Eveland sets it for every build and deployment it runs.
- Extensions may provide channels, schedules, and namespaced subagents; their full platform scheduling and observer integration is delivered as a separate compatibility follow-up.
- `chatgpt()` is stable with Codex-owned authentication — but ChatGPT subscription models are local-only by design: there is no Codex sign-in inside an Eveland deployment, so an Agent pinned to `chatgpt()` deploys and then fails at run time. Use an AI Gateway or server-authenticated model for deployed Agents.
- `glob` and `grep` are not in the default Agent tool set; an Agent that relies on them must export them from the corresponding tool files by re-exporting the provided definitions from `eve/tools/glob` / `eve/tools/grep` (the `defineGlobTool()` / `defineGrepTool()` factories left the window with 0.44).
- A child agent can share the dispatching parent's live sandbox — by returning `parent.sandbox` from its `defineSandbox` callback on 0.62.x, or by exporting `defineParentSandbox()` on 0.67.x; such a child cannot also declare managed workspace or skill resources, and Eveland's platform sandbox applies to the parent as usual.

## Supported version lines

- **Eve 0.62.x (verified at `0.62.0`)**: Instrumentation is authored as path-named files under `agent/instrumentation/`. A flat `agent/instrumentation.ts` is no longer discovered, and `experimental.instrumentationProviders` is gone because instrumentation discovery is always on: split an existing module into lifecycle instrumentation, one `otelIntegration()` file per OpenTelemetry destination, and shared `otel()` settings (Eve ships the mapping as `docs/guides/instrumentation/migration.md`). The deprecated shapes left with it — providers reject `capture` in favor of `tracePolicy`; destination `recordInputs` / `recordOutputs` throw at declaration; `redactSpanInputs()`, `redactSpanOutputs()`, `content`, and `composeSpanExportPolicies()` are removed; and `exportPolicy` takes one policy or an ordered array whose span and attribute callbacks return object decisions (`{ emit }`, `{ redact, inputs, outputs }`, `{ replace, value }`). The default moved as well: the removed API exported no content unless asked, whereas an OpenTelemetry destination now records content in development and for `public` conversations. An Eveland Deployment is always `production`, so only `public` audiences are affected; declare a metadata-only `tracePolicy` to keep the old behavior. None of this reaches Eveland's own observer, which is injected as a hook and keeps its private telemetry runtime, and the platform's capture settings are unchanged. A client may create a session before its first message (`POST /eve/v1/session` with no body; `prewarm` on the TypeScript client, `prewarm: true` on the React bindings); the Agent Gateway forwards it like any other create, and Eveland's Playground does not opt in. `message.received` carries `kind: "execution.background_task"` when Eve rather than a participant authored the input, and Eve's default reducer no longer renders those as user messages. `agentRouter()` from `eve/tools/agent-router` routes a task across the declared subagents — including ones hidden from the model with `tool: false` or `disableTool()` — as the version-stamped `executeAgentRouterTool` workflow, and `agent` is now a reserved subagent name; workflow steps fail immediately when they touch the body-only `ctx.agents`, `ctx.agent()`, or `ctx.ask()`. `auto` from `eve/models` and `evaluate` from `eve/ai` replace `autoModel` and `eve/experimental/evaluate`, tool approvals can be delegated to an evaluation model with `auto({ model, instructions, criteria })`, and eval suites move to `t.session()` and `t.judge()`. Dynamic tool schemas replay through durable schema factories, so a prebuilt Extension or provider package must be rebuilt with the current compiler (`defineDurableSchema`). Effective instructions and tool schemas count toward context compaction before each model call. Eve's bundled Workflow set moved at 0.61.0 (see the window baseline) and `@vercel/sandbox` to the stable 3.3 SDK. Eve lets an idle session with resumable subagents move to a newer deployment; that handoff stays inert on Eveland, where the Agent Gateway routes every session to the Deployment it is bound to.
- **Eve 0.67.x (recommended, verified at `0.67.0`)**: Sandboxes are provider environments (since 0.64). A sandbox module exports an `environment` built from a provider (`DefaultSandbox.environment()` from `eve/sandbox`, or `DockerSandbox`, `VercelSandbox`, `MicrosandboxSandbox`, and `JustBashSandbox` from their `eve/sandbox/*` entry points) and a `defineSandbox()` selector that opens it; object-form `defineSandbox({ backend, bootstrap, onSession })`, `defaultBackend`, and `revalidationKey` are gone. Setup every sandbox inherits moves into the environment's `prepare`, which `eve build` runs once while it prepares the template — on Eveland inside bwrap at build time — and per-session setup moves into the selector, after `open()`. A module in one shape does not compile on the other line, so a project moving to 0.67 rewrites its sandbox module; Eveland chooses the matching injection itself (see the window baseline). 0.63 moved durable background work onto workflow tools: `defineTool({ execution: "background" })`, background dynamic tools, `TaskExec`, and `postMessage` are gone in favor of `defineWorkflowTool`, the unstamped `taskRunWorkflow` run went with them, and each background cohort's completed, failed, and cancelled outcomes reach the parent in one automatic report. A background subagent call now returns its receipt only as the call's `action.result`, and `subagent.completed` fires once, after the parent records the child's actual result; Eveland's observer keeps the call's span open from the receipt until then, or until the child session ends, so the child's spans stay under it. Message sends accept `taskDeliveryPolicy: "auto" | "cohort"`: channel sessions default to `"auto"`, which may report independently useful background results early, and Eve's own schedules to `"cohort"`; Eveland's scheduler asks for `"cohort"`, so an Eveland schedule reports like an Eve one. `/eve/v1/info` answers in version 5, with provider-based sandbox fields that Eveland does not read. The implicit default model is `spacexai/grok-4.7`. 0.65 reworks the built-in tool set: the `todo` tool and its `eve/tools/todo` entry point are gone, and an `agent/tools/todo.ts` — even one that only exports `disableTool()` — now fails the build, which on Eveland surfaces as a failed Release build. `ask_question` left the default tool set and became an opt-in workflow tool: add it with `eve add tool/ask_question` (an `agent/tools/ask_question.ts` that default-exports `askQuestion()` from `eve/tools/ask_question`); a file that disables it fails the build the same way, and an Agent that relied on the default tool simply loses it and asks in its reply text instead. The model now asks one `question` with up to three `{ label, description }` options, the user can always answer in free text, and the tool returns `{ status: "answered", answer }`, `{ status: "dismissed" }` when the user moved on, or `{ status: "unavailable" }` when the session cannot request input. `ctx.ask()` resolves to the same `status` shapes (check `status` before reading `optionId`), a plain-text message answers the only pending question when it matches an option or free text is allowed, and `dismissible: true` resolves it as dismissed on an unrelated message; a request's `requestId` is no longer its tool call ID, so relate them through `action.callId`. Eveland's Playground renders and answers these questions as before. Compaction no longer resets `write_file` read tracking, and `eve dev` mounts development-only extensions (the local self-modification subagent) unless `--no-default-extensions` is passed; production builds, which are what Eveland runs, do not. Consecutive deployment handoffs now keep a session on its original stream, but handoff stays inert on Eveland, and no session could move across the 0.62→0.67 boundary anyway because the session checkpoint version changed at 0.64, 0.66, and 0.67. Eve's bundled Workflow set moved at 0.64.0 and again at 0.66.3 (see the window baseline). 0.66 removes `ctx.getSkill()` and the `SkillHandle` and `SkillFile` types from `eve/skills` — the model still reads a skill's supporting files with its sandbox tools, and tool or hook code that needs them imports from a module in `lib/` instead — and dynamic skills no longer start a sandbox just to announce or load their instructions; existing extension builds keep loading unless they called `ctx.getSkill()`. `setNetworkPolicy` left the common `SandboxSession` type: pass the configured environment to `ctx.getSandbox(environment)` to keep that provider's session capabilities on the handle (Eveland's bwrap environment still offers it). Tool schemas reach the model as JSON Schema, MCP and other JSON Schema tools are advertised exactly as published and validated with a standard JSON Schema validator, the `*_INPUT_SCHEMA` and `*_OUTPUT_SCHEMA` constants from `eve/tools/*` are JSON-Schema-backed Standard Schemas rather than Zod objects, and Eve ships one private copy of Zod, so a project that installs its own Zod version no longer breaks MCP or file-memory tool turns; `eve/client` no longer exports its Zod schemas (`inputRequestSchema` and its siblings — use the exported types with `isInputRequest`, `isInputResponse`, and `parseInputResponse`), none of which Eveland's Playground imported. `subagent.called` and `subagent.completed` hooks can call `ctx.getSandbox()` for the parent session and keep their sandbox changes for the parent's next turn, and the new built-in `eve/extensions/code` extension (`apply_patch`, `gh`, `grep`, computer use, coding skills, and a read-only worker subagent) uses the application's own sandbox, so on Eveland it runs inside bwrap. Compaction summaries leave temperature at the provider's default. 0.66.1 adds `session.streamSubagent(called)` to `eve/client` for following a delegated child's stream, hands `eveChannel({ trustedForwarders })` the asserted principal as a second argument (Eveland does not use trusted forwarders), keeps a delegated task open while its yielded child still has background work running, and has `eve build` build mounted, source-backed workspace extensions (packages declaring `eve.extension.source` and `eve.extension.dist`) before compiling the agent, so a build no longer depends on the package manager having run their `prepare` script — on Eveland that build now happens inside the build sandbox. No wire surface changed between 0.66.0 and 0.66.1. 0.66.2 ignores `*.test.*` and `*.spec.*` modules and `__tests__/` directories during agent discovery, so a project's colocated tests no longer register as agent files. 0.66.3 moves the bundled Workflow set to `5.0.0-beta.56/23/38/47`, whose runtime reads storage spec 6 through 8 (see the window baseline for why Eveland's World keeps stamping 7), marks new session handoffs as protocol version 2 while reading unversioned ones as version 1, and lets `slackChannel` and `callSlackApi` take an `api` option that points Slack Web API calls at another host. 0.67 changes the session lifecycle: the `conversation` / `task` run mode is gone, so every session — a schedule's, an MCP `agent_start` invocation's, a delegated child's — parks after each turn instead of ending, and only its `limits.sessionTimeoutMs` (seven days by default) ends it; `mode` left `ChannelAddress`, the Chat SDK `send(...)` options, and the audience and trace-policy inputs, and the eve HTTP channel ignores a `mode` field on session creation. A channel send now always grants the request-input capability, so a session a channel starts parks on a tool approval or a `ctx.ask()` until someone answers, where a task-mode session used to fail fast; Eveland's scheduler therefore emits `mode: "task"` only for a 0.62.x Release, and a schedule that reaches a tool approval on 0.67.x sits parked rather than failing — keep schedules on tools that need no approval, or answer the question from the Playground. Eve's own markdown schedules have no channel and still fail fast. `outputSchema` is removed from `defineAgent`, `defineRemoteAgent`, `defineWorkspaceAgent`, dynamic subagent configs, agent info, the model-facing subagent and `agentRouter()` tool inputs, MCP `agent_start`, and the channel `from(address).send()` / `respond()` options: request structured output per turn through the session API or `ctx.agent()` instead. The default `eve/client` reducer keeps approval, question, and session-limit prompts pending until the server confirms the answer, so a frontend disables its response controls while the store is `submitted`, `streaming`, or `resuming` — Eveland's Playground already does. `/eve/v1/info` still answers in version 5 but lists only the priority-tier indicator among a model provider's options, so credentials stored under an unexpected key cannot leak there. Instrumentation setup now completes before the server's dependencies load, so OpenTelemetry can instrument packages such as `pg`; MCP connection calls carry OpenTelemetry context in their metadata and MCP semantic attributes on their tool traces; parent stream-event hooks run after proxied input requests and authorization events are published and receive the published event ID; `step.completed` carries a `stepIndex`; a parent's steering text no longer resolves a delegated child's pending `ctx.ask()`; and turn-scoped dynamic connections are restored before an approval response is authorized, including after a cold start. On the CLI, `eve remote connect <url>` and `eve remote invoke <url>` replace `eve dev <url>` and `eve invoke`, and `eve set model [model] [--reasoning <effort>]` replaces `eve set --model` and `eve set --reasoning`; `eve dev` now starts only local development. Extension contracts stay additive (`tool` 58, `dynamicTool` 56, `channel` 33, `schedule` 16, `subagent` 21, `connection` 28, `hook` 28, `dynamicSkill` 23, `dynamicInstructions` 24), and the compiled agent manifest moves to version 52. For the current latest line, Agent projects should refresh their lockfile and redeploy to receive `0.67.0`.

An npm publication alone does not widen the window. A new minor enters only after changelog and source review plus the complete compatibility matrix; removing an older minor is also an explicit product change.

## Enforcement points

Eveland fails closed when the dependency is missing, outside the window, or cannot be proven compatible during:

- source import and preflight
- build and restart
- cold activation (a Release whose build installed an out-of-window Eve version is refused at activation-request time — terminally, so a workflow run bound to it is dead-lettered once instead of retried after every cold start)
- Playground traffic
- public session create, continue, cancel, and stream
- public session reset
- every other public Agent Gateway request to the selected Deployment, including custom channel routes and webhooks (a dormant out-of-window Deployment answers 409 instead of being woken)
- schedule execution

The diagnostic asks the project owner to upgrade instead of guessing an older protocol. Review the release notes before upgrading either Eve or Eveland in production.
