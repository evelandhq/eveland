title: Eve compatibility
description: Understand Eveland's verified Eve version window and fail-closed policy.
---

Until Eve publishes a stable compatibility contract, Eveland supports only minor lines that have passed the complete compatibility matrix, and changes that window explicitly. The checked-in product contract supports `0.74.x` and `0.76.x`, verified at `0.74.0` and `0.76.0`. Eve 0.75 (retired on 2026-10-10 when 0.76 entered, one day after 0.75 itself had, before any Eveland release carried it), Eve 0.68 (retired on 2026-10-09 when 0.75 entered; Eveland v0.61.0 had carried 0.74 since the day before, so every 0.68 Release already had a newer line to rebuild on), Eve 0.73 (retired on 2026-10-08 when 0.74 entered, hours after 0.73 itself had, before any Eveland release carried it), Eve 0.72 (retired on 2026-10-08 when 0.73 entered, one day after 0.72 itself had, before any Eveland release carried it), Eve 0.70 (retired on 2026-10-07 when 0.72 entered, five days after 0.70 itself had, before any Eveland release carried it), Eve 0.71 (skipped on 2026-10-07: 0.72.0 superseded it within four days, before any Eveland release carried it), Eve 0.69 (retired on 2026-10-02 when 0.70 entered, one day after 0.69 itself had, before any Eveland release carried it), Eve 0.62 (retired on 2026-10-02 when 0.69 entered), Eve 0.67 (retired on 2026-09-29 when 0.68 entered, three days after 0.67 itself had, before any Eveland release carried it), Eve 0.66 (retired on 2026-09-26 when 0.67 entered, two days after 0.66 itself had, before any Eveland release carried it), Eve 0.63, 0.64, and 0.65 (skipped on 2026-09-23 and 2026-09-24: 0.63.0 failed every session whose background subagent call met a hook subscribed to subagent events, which Eveland's own observer is, 0.64.0 shipped the fix, 0.65.0 superseded 0.64.1 within a day, and 0.66.0 superseded 0.65.0 within six hours, before any Eveland release carried any of them), Eve 0.58 (retired on 2026-09-23 when the window narrowed to the 0.62 floor), Eve 0.59, 0.60, and 0.61 (skipped on 2026-09-19: each was superseded within a day, before any Eveland release carried it), Eve 0.55 (retired on 2026-09-19 when 0.62 entered), Eve 0.56 and 0.57 (skipped on 2026-09-17: 0.58.0 superseded them before any Eveland release carried either), Eve 0.54 (retired on 2026-09-16 when 0.56 entered a window that was already two lines wide), Eve 0.52 and 0.53 (retired together on 2026-09-15), Eve 0.50 and 0.51 (retired together on 2026-09-12), Eve 0.49 (retired on 2026-09-07), Eve 0.48 (skipped when 0.49.0 superseded it on 2026-09-02, before any deployment ran on it), and Eve 0.47 and older are no longer accepted for import, build, restart, activation, Playground, Agent Gateway, or schedule execution.

The Eve dependency declarations a project's `package.json` may carry are: an exact patch inside a supported line, a `~`/`^` range anchored on a supported minor's patch, and the `0.74` / `0.74.x` / `0.74.*` and `0.76` / `0.76.x` / `0.76.*` forms. A missing Eve dependency, a broad cross-minor range, or any declaration that could resolve outside the window fails closed. The project Overview, Source, and Playground pages show the Eve dependency version of the current deployment's source revision alongside the platform requirement.

The window is a set of verified lines, not "everything at or above the floor": `0.76.x` entered on 2026-10-10, the day after `0.76.0` was published, and `0.75.x` — which had entered on 2026-10-09 in place of the `0.68.x` floor — left with it before any Eveland release carried it. `0.74.x` stays because Eveland v0.61.0, released on 2026-10-08, ships it, so the window is gapped again and the SDK's peer floor stays at `>=0.74.0`. `0.75.x` sits inside the hull and is rejected with the same upgrade diagnostic as a retired line. A Deployment whose Release was built on a retired line stops being servable as soon as Eveland carries the narrower window: the Agent Gateway answers it with 409, activation refuses it, and the platform settles the workflow runs still parked on it instead of retrying them; Eve cannot continue a session under a different Eve version, so a rebuild starts new sessions rather than resuming those. Between `0.74.0` and `0.76.0` the discovery manifest (v15), the message stream (v26), the compiled agent manifest (54), the routes Eveland forwards, and the observer's instrumentation pin are byte-identical; what moves is the session checkpoint (12 to 13, at 0.75), the bundled Workflow set (core 5.1.0 / world 5.0.2 to the stable 5.2 family — core 5.2.0, world 5.0.3, world-local 5.1.0 — with the same World calls and spec range, at 0.75.1), the sandbox provider handle, whose lifecycle hooks 0.75 renamed and which now releases a finished session's sandbox (`@evelandhq/sandbox-bwrap` 0.5.0 serves both lines), and the names of eve's own tools, which 0.76 moved into the `eve` namespace (see the 0.76.x entry below). Every line in the window acknowledges messages with a delivery id, so every accepted Deployment is reachable from the Playground. The peer range is the union of the two contiguous runs (`>=0.74.0 <0.75.0 || >=0.76.0 <0.77.0`), never their hull, which would admit 0.75. `0.68.x`, `0.69.x` through `0.73.x`, `0.62.x`, `0.63.x` through `0.67.x`, `0.59.x` through `0.61.x`, and `0.48.x` — never verified, superseded by 0.49.0 within hours as 0.46, 0.43, and 0.40/0.41 were before it — stay below the floor together with `0.58.x`, `0.57.x`, `0.56.x`, `0.55.x`, `0.54.x`, `0.53.x`, `0.52.x`, `0.51.x`, `0.50.x`, `0.49.x`, `0.47.x`, and older; `0.77.x` is not admitted before it has passed the matrix.

The UI marks only the latest supported line, `0.76.x`, in green. Eve 0.74.x stays operational but appears in red with an upgrade reminder; unsupported versions also appear in red and remain blocked.

## Window baseline

Everything the platform once carried for older Eve lines is now the baseline of the whole window, and the pre-0.42 compatibility paths have been removed from Eveland entirely:

- Sessions are addressed only by their ID. Continuation tokens do not exist anywhere in the platform anymore: the token columns, the token-based reset translation, and the `POST /eve/v1/session/reset` token route are gone. Clear, compact, and reset live at `POST /eve/v1/session/:sessionId/{clear,compact,reset}`.
- `localDev()` is process-based and admits nothing under `eve start`; Agents on Eveland must authenticate with `evelandIdentity()`, `httpBasic()`, or OIDC.
- Channel message sends default to `turnPolicy: "steer"`; Eveland's injected scheduler adapter always asks for `"queue"` so a schedule never preempts a turn a person is waiting on.
- Eveland decides where every sandbox runs: it injects its managed bwrap sandbox (`@evelandhq/sandbox-bwrap`) into each Release. Every line in the window compiles sandbox modules that export a provider `environment` and a `defineSandbox()` selector (the shape 0.64 introduced), so Eveland keeps an authored module and redirects its `eve/sandbox` imports so that every built-in provider (`DefaultSandbox`, `DockerSandbox`, `VercelSandbox`, `MicrosandboxSandbox`, `JustBashSandbox`) builds the bwrap environment instead: the authored `prepare` and selector still run, and provider-specific options such as images and Dockerfiles are ignored; a slot the project left empty gets a generated module. `eve build` prepares every template and records the provider that prepared it, and Eveland refuses a Release in which any sandbox was prepared by another provider — an environment built in a helper file, a custom provider from `eve/sandbox/provider`, or a sandbox shipped by an Extension. The object-form `defineSandbox({ backend })` module Eveland generated for 0.62.x left with that line. 0.75 renamed the provider handle's lifecycle hooks (`onSessionStop()` / `onSessionDelete()` became `onSandboxStop()` / `onSandboxDelete()`, with no fallback to the old names) and releases a durable session's sandbox once the session has completed, expired, or failed — through the provider's optional `onSessionEnd()`, or, when the provider has none, by resuming and deleting it. The injected `@evelandhq/sandbox-bwrap` 0.5.0 answers both name pairs and implements `onSessionEnd()` directly, removing the session's workspace and metadata without resuming anything and tolerating a retry, so one injected copy serves both lines and a finished session's bwrap workspace is reclaimed on 0.76.x, as it was on 0.75.x (on 0.74.x it stays until the sandbox cache is pruned).
- Supported builds emit discovery manifest v15; the projector accepts nothing else (v14, emitted only by 0.45.0, left with the 0.45 line). v15 carries the `memories` list; 0.62.0 stopped writing its optional `instrumentation` module reference without a version bump when flat `agent/instrumentation.ts` stopped being discovered, and Eveland never read that field.
- The message stream protocol is **v26** across the window (introduced by 0.69: its append events carry the delta alone — the v24 cumulative `messageSoFar` / `reasoningSoFar` snapshots and the UTF-16 `inputTextOffset` left with 0.49 — and it adds the task events `task.started`, `task.settled`, `agent.started`, and `turn.waiting` in place of `subagent.*`). The `eve/client` of both lines reads v21 through v26, so the Dashboard's Playground, built on it, reads both; the client keeps a held turn `streaming`, so a frontend must let people answer a pending question, approval, or sign-in while the turn runs, as Eveland's Playground does. Every response still carries the version in `x-eve-stream-version`, which Eveland's Playground and Agent Gateway forward verbatim; a custom NDJSON consumer should keep reading it rather than assuming the shape. Both lines carry the optional, separately negotiated transport lease 0.57 added: a client that opts in with `?streamControlVersion=1` (the `eve/client` reader does so whenever reconnection is enabled and it reads from an absolute cursor) receives blank-line heartbeats every 10 seconds and, after 60 idle seconds, a `{"$eve":"stream.lease-ended","version":1}` control line that ends the response so the client reconnects from its cursor. The Agent Gateway forwards the query string verbatim and keeps its own 5-second heartbeat. 0.75.1 opens the stream response while the durable tail-index lookup is still in flight and reads the durable source only as fast as the client consumes it; nothing on the wire changes.
- Eve's implicit default model is `openai/gpt-6-luna-fast` with high reasoning on both lines; pin `model` explicitly to control provider, behavior, and cost.
- Durable delegation and invocation channels are baseline: remote child streams follow through the parent at `GET /eve/v1/session/:parentSessionId/subagents/:callId/:childSessionId/stream`, create-once `operationId` sessions, `POST /eve/v1/task-input/:token` callbacks (0.69 no longer exports the route constant but still serves the route for callers on older lines), and `mcpChannel()`'s durable agent tools all ride Eveland's durable Deployment routing boundary. 0.69 removed `POST /eve/v1/activity/:token` together with its activity collector; the Agent Gateway forwards paths transparently, so a 0.69 Agent answers that path with its own 404. Because every supported line speaks these routes, the Agent Gateway no longer maintains a per-operation Eve version floor — the window itself is the gate.
- Frontend `stop()` is gone; cancellation is the durable, hook-owned `cancel()` command. Eveland's Playground awaits it, including the interval before the first event identifies the durable turn, and keeps the stream attached through settlement.
- Workflow runs on storage spec v7, the sealed log: since `@evelandhq/workflow-world` 0.18.0 the World declares `mintedSpecVersion()` (7 by default, 6 for a Deployment that sets `WORKFLOW_SEALED_LOG=0`), and Releases built with 0.17.0 or earlier keep their spec-6 runs because the platform admits both generations. Every line's runtime accepts a World declaring 6 through 8 (0.74.0 bundles the stable core `5.1.0` / world `5.0.2` Workflow set and 0.76.0, like 0.75.1, the 5.2 family — core `5.2.0`, world and errors `5.0.3`, world-local `5.1.0` — whose spec range is the same), and every line compares only the major and prerelease tag of the World's `@workflow/*` declaration (Eve's own bundled set moved to `5.0.0-beta.53/21/36/45` at 0.61.0, which is what 0.62.0 carries, to `5.0.0-beta.55/22/37/46` at 0.64.0, whose `@workflow/world` adds an optional `invoke` capability that Eveland's World does not declare, and to `5.0.0-beta.56/23/38/47` at 0.66.3, whose `@workflow/world` mints spec 8 — the hook force-claim reader contract, under which another run may take over a hook's token with `createHook({ experimental_force: true })` — to `5.0.0-beta.57/24/39/48` at 0.67.2, which leaves every spec constant where it was and is what 0.68.0 carries, and to the stable `5.0.1` release of the same family at 0.70.2, which leaves every spec constant where it was, only adds optional World members, and is what 0.72.1 carried, and to core `5.1.0` with world, world-local, and errors `5.0.2` at 0.73.0 (0.74.0 and 0.75.0 carry the same set), which keeps the World calls and spec constants and only adds optional members (a stream writer's `release`, an advisory `afterStepBody` mark, a hook's `nodeVersion`), and to the stable 5.2 family at 0.75.1 — core `5.2.0`, world and errors `5.0.3`, world-local `5.1.0` — which again keeps the World calls and spec constants; a stable version on either side matches any prerelease of its major), so one World serves both lines. The platform injects `@evelandhq/workflow-world@0.24.0` for every new build, which pins the stable `@workflow/world` and `@workflow/world-local` 5.0.1 that 0.72.1 bundled — 0.74.0's 5.0.2/5.1.0 runtime and 0.76.0's 5.0.3/5.2.0 runtime accept it because the major matches — and answers the runtime's `resolveData: "skip-step-inputs"` event reads exactly as it answers `"all"`, while it keeps declaring spec 7 (`Math.min(mintedSpecVersion(), 7)`) — a cap set while 0.62.0, whose runtime refused a World above 7 at startup, was in the window, and which every remaining line still reads — and never takes a hook token over — a forced creation is answered with an ordinary `hook_conflict`, so no run it stamps is ever stranded; and which delivers held dispatches over Node's core HTTP client so that a step running longer than five minutes is no longer cut off and redelivered by the 300-second deadline of the global `fetch`, addresses a cross-deployment `start()` to the Deployment it names instead of the one that enqueued it, and (since 0.21.0) commits a run and its `run_created` event in one transaction; `@workflow/world-postgres@5.0.0-beta.34` exists only in historical Releases and is never selected for a new build. Older spec-v5 worlds fail the startup guard. The shared World also bounds physical stream storage with snapshot stripping, block packing, checkpoints, and deadline-driven retention.
- MCP channels default to `/eve/v1/mcp` and may declare another `route`; Eveland's path-transparent Agent Gateway preserves either path and the corresponding OAuth protected-resource metadata route.
- Durable tools are declared with `defineWorkflowTool` from `eve/tools` and delegate with `ctx.agent()` — `ctx.agent(name)` returns a session whose `send(message, { outputSchema })` answers with a response whose `result()` resolves the turn; Eve derives the replay-stable invocation identity itself; workflow tools on the parent flow through one ordered inbox where a retried dispatch may start another run, and `defaultTools: false` opts an Agent out of Eve's optional default tools. `experimental.workflow.retention: 0` and `experimental.workflow.modelCallsPerStep` are opt-in Agent options across the window: the retention preference is recorded on the run as the reserved `$retention` attribute, which Eveland's shared World stores but does not enforce, and a larger step batch widens the replay unit after an interruption.
- The `task_update` tool, its child-to-parent progress callbacks, and background tasks are gone across the window: a call holds its turn until `task.settled` (see the 0.74.x entry).
- The OpenTelemetry agent trace schema is 4 across the window: every activation is an `invoke_agent` span grouped by `gen_ai.conversation.id`, model input is recorded once as `gen_ai.input.messages`, and memory recall/capture emit their own spans and `memory.operation.*` hook events. Eveland's observer and collector mappings key on none of the pre-4 names, but a dashboard built on an Agent's own `otel()` export must target schema 4.
- Extension contracts drop versions as Eve reworks them. 0.75 and 0.76 only added versions — 0.76.0 is at `tool` 84, `dynamicTool` 77, `channel` 56, `schedule` 29, `subagent` 33, `connection` 45, `hook` 43, `skill` 3, `dynamicSkill` 35, `dynamicInstructions` 36, and `state` 12 and still loads 0.74's `tool` 78, `dynamicTool` 73, `channel` 52, `schedule` 27, `subagent` 31, `connection` 41, `hook` 39, `skill` 2, `dynamicSkill` 33, `dynamicInstructions` 34, and `state` 10 (the versions dropped along the way — 79, 74, 53, 42, 40, 11, and `tool` 83 — never shipped in a release), while `extension` 1, `instructions` 2, and `config` 1 did not move — so an Extension built on 0.74 loads on 0.76. Older builds do not carry over: 0.69 dropped `tool` 58–62, `dynamicTool` 56–59, `channel` 33–35, `schedule` 16–17, `subagent` 21–22, `connection` 28–31, `hook` 28–30 (and the long-deprecated 10–19), `dynamicSkill` 23–24, and `dynamicInstructions` 24–25 when it removed background tasks and moved extension configuration and durable state onto each logical mount, and 0.72 dropped `tool` 54–55 and 63–75 and `dynamicTool` 71 when `evaluate` became `decide`, so an Extension built on 0.68 or earlier, or a tool Extension built on 0.70 or 0.71, must be rebuilt (0.73 through 0.75 only added versions, so a 0.72 build still loads). A prebuilt Extension must therefore be rebuilt against the line the project builds on; Extensions Eveland injects itself are compiled from source and unaffected. Eve's CLI reports usage to Vercel unless `EVE_TELEMETRY_DISABLED` is set; Eveland sets it for every build and deployment it runs.
- Extensions may provide channels, schedules, and namespaced subagents; their full platform scheduling and observer integration is delivered as a separate compatibility follow-up.
- `chatgpt()` is stable with Codex-owned authentication — but ChatGPT subscription models are local-only by design: there is no Codex sign-in inside an Eveland deployment, so an Agent pinned to `chatgpt()` deploys and then fails at run time. Use an AI Gateway or server-authenticated model for deployed Agents.
- `glob` and `grep` are not in the default Agent tool set; an Agent that relies on them must export them from the corresponding tool files by re-exporting the provided definitions from `eve/tools/glob` / `eve/tools/grep` (the `defineGlobTool()` / `defineGrepTool()` factories left the window with 0.44).
- A child agent can share the dispatching parent's live sandbox by exporting `defineParentSandbox()`; such a child cannot also declare managed workspace or skill resources, and Eveland's platform sandbox applies to the parent as usual.

## Supported version lines

- **Eve 0.74.x (verified at `0.74.0`)**: 0.69 removed background tasks, and 0.70 through 0.74 keep that model. Every workflow tool call and every agent call holds its turn until it settles: a `task()` workflow tool or an agent tool runs each call as a task whose call returns a plain-text receipt (`Started task …`), the result reaches the model later in a `<task_result>` message, the model waits with `task_wait` or stops a task with `task_cancel`, and a turn cannot end while its tasks work. A `serve(receive, ctx)` workflow tool runs one resumable task the model can call again with its `taskId`; every agent tool is now built that way, so the model continues or corrects a subagent by passing `taskId` (replacing `agentId`). `defineWorkflowTool` rejects `execution`, and `taskDeliveryPolicy`, `session.cancel({ tasks })`, task notifications, `dismissible`, and the `<eve-empty-delivery/>` marker are gone; Eveland's scheduler stops sending `taskDeliveryPolicy` to a Release on 0.69 or later. The `subagent.called`, `subagent.started`, `subagent.event`, and `subagent.completed` events and their hooks are removed in favour of `task.started` (`kind: "agent"` or `"tool"`), `task.settled` (its status, output or error, and `cancel.reason`), and `agent.started` (the child's `sessionId`, `name`, and `taskId`, and `remote.url` for a remote agent); `session.streamSubagent(called)` became `session.agent(started).stream()`. Eveland's observer and session projection read both generations: an agent call's span stays open from its receipt to `task.settled` and records the reply, a continued task's later child turns nest under the call serving them, the child SessionNode — an unresolved remote one included — is linked from `agent.started`, and the session replay shows the settled reply instead of the receipt. A question or sign-in raised inside a running call — a workflow tool's `ctx.ask()`, `ask_question`, or a subagent's question — no longer ends the turn: the stream emits `input.requested` (or `authorization.required`) and then `turn.waiting`, and the turn resumes under the same `turnId` once it is answered, with `input.resolved` marking the answer. Eveland moves the session back to running on `input.resolved` and parks a scheduled run on a `turn.waiting` under a pending question, as it does on `session.waiting`. In a root session the text the model writes before it waits on its tasks completes as an ordinary message right away; Eve keeps a single final reply only for child sessions and its own scheduler's sessions, and Eveland dispatches schedules through its own channel, so a scheduled turn that delegates can post that early text too. `ctx.agent(name)` returns a session (`send(message, { outputSchema, signal })`, then `result()`); `ctx.agent(name, { message, agentId })` is removed, and remote agents now check a protocol version (a 0.69 remote agent still serves callers on 0.66 through 0.68). Connection tools no longer enter the model's tool list: the model finds them with `connection_search` and calls them through the new `connection_execute`, which returns MCP `structuredContent` or text, and the `eve/tools/connection_search` export is removed. Approval response policies run for Cancel as well as Approve and read the responder from `response.principal`. Extension configuration and durable state belong to each logical mount, and every changed extension contract family dropped its 0.68 versions (see the window baseline), so prebuilt Extensions must be rebuilt. The session checkpoint moved to 10 at 0.69 and 11 at 0.70, and Eve rejects a handoff across either boundary in both directions; handoff stays inert on Eveland, which binds every session to its Deployment. Tools can end a turn without a reply (`endsTurn: true`, or the opt-in `no_reply` tool from `eve add tool/no_reply`). `eve/server` adds an in-process `sessions.attach(sessionId).stream()`, `eve/schedules` exports `isScheduleAuth(auth)`, which recognizes the app principal Eveland's scheduler sends, and the implicit default model is `openai/gpt-6-luna-fast`. Delegated usage now counts toward the parent's session budgets; Eveland still takes usage from each model step's own `step.completed`, so nothing is counted twice. Slack channels replace `slackChannel({ events })` with `renderers`, the Chat SDK bridge's `send()` takes `(message, { context, thread })` with a separate `respond()`, and sign-in challenges and approval feedback go privately to the Slack user behind the event's principal. 0.70 extends the held turn to tool approvals and connection sign-ins: instead of `turn.completed` and `session.waiting`, the stream emits `turn.waiting`, which now says what it waits `on` (`"input"` when a person must act, `"tasks"` when the turn waits on its own work), and the same turn resumes once the person acts; a message from that person steers the turn and cancels the pending approval or sign-in, and cancelling the turn withdraws both. Eveland counts a pending sign-in as waiting on a person like an approval — the session shows as waiting for review until `authorization.completed`, and a scheduled run that holds for one parks — and the Playground lets people answer while a turn is held. A plain `connection_search` no longer asks the user to sign in: unauthorized connections appear under `unavailable` with `requiresSignIn: true`, and the model signs in with `connection_search({ connection, signIn: true })`. `session.waiting`, `turn.waiting`, `session.completed`, and `session.failed` carry the session's running `usage` including what delegated agents spent; Eveland keeps taking usage from each model step's own `step.completed`, so nothing is counted twice. The frontend hooks and `EveAgentStore` share one conversation client: the default `useEveAgent` data is a `ConversationState` (messages plus turns, input requests, tasks, and agent sessions), and a held turn stays `streaming` with `turns[turnId].waiting` set. The first local subagent turn now joins its caller's trace; Slack identifies a person by the installation workspace (`slack:<team>:<user>`), so user-scoped connections ask Slack Connect and Enterprise Grid users to sign in once more, and Slack's `onMessage` receives only new messages. 0.71 and 0.72 keep the message stream at v26 — `input.requested` only gains an optional `callId` naming the call a relayed request serves — and leave the discovery manifest, the compiled manifest (54), the routes, and the sandbox provider API where 0.70 left them; they move the session checkpoint to 12 (handoff stays inert on Eveland) and bundle the stable Workflow SDK 5.0.1 set instead of the 5.0.0 betas (see the window baseline). The `bash` tool no longer blocks on a command still running after 30 seconds: it returns `status: "running"` with the process group's `pid` and an `outputDirectory`, and `exitCode` is present only on `completed` results; inside Eveland's bwrap sandbox each command runs in its own namespace, so such a command keeps blocking until it finishes, as on 0.70. Approvals without a `response` policy now answer only to the principal whose turn requested the call, and an approval granted by someone else runs only that call as the approver: a scheduled turn runs as the app principal, so an approval it raises cannot be granted from the Playground, and in a shared session only the member whose turn asked can approve. Answering some of several pending questions parks the turn again with `turn.waiting` (`on: "input"`), which Eveland projects as waiting for review; a plain-text answer is recorded as `message.received` before its `input.resolved`; pending input is withdrawn when a cancel, a context clear, or a finished workflow removes its owner, and a withdrawn approval renders as denied. The Playground shows every question a tool call asks at once and keeps answer buttons live only for requests that are still open. After compaction an idle session moves to a fresh workflow run on the same Deployment, so a long session stops growing one event log; it keeps its ID, stream, and Deployment binding. MCP connections that declare `auth` but hold no token connect anonymously and ask the user to sign in only when the server answers `401` or a `mcp/www_authenticate` challenge. `evaluate` from `eve/ai` is now `decide` (AI SDK 7.0.128), which drops the older `tool` and `dynamicTool` contract versions (see the window baseline); `defineInstrumentation` replaces `action.*` handlers with `tool.call.*` and exports one `execute_tool` span per tool call, which leaves Eveland's observer, built on stream events, unaffected. Channel route handlers gain `describe()` and `invokeTool(name, input, { auth })`, `mcpChannel` can publish the Agent's own tools with `tools: true`, frontmatter parses with js-yaml 4 and accepts only `---` or `---yaml` fences, and files people send reach the agent on more channels. 0.73 leaves every surface Eveland reads byte-identical to 0.72.1 — the message stream, hooks, the `eve/client` types, the sandbox provider API, the discovery manifest, the routes, and the stable workflow names — and moves the bundled Workflow set to core 5.1.0 / world 5.0.2 with the same World calls and spec range. It splits self-modification into `eve/self-modification/local` and `eve/self-modification/remote` mounts (unsupported on Eveland either way), ships skill files as eve-owned server assets and drops Nitro's default `server` asset entry (an app that read `assets:server` storage in production finds it empty), lets `mcpChannel({ tools: true })` run tools as a user a `trustedForwarders` caller forwards in the `eve-forwarded-principal` header (a channel without `trustedForwarders` answers that header with `403`; the Agent Gateway passes it through untouched), keys `invokeTool` tool sessions, serves skills over MCP with `mcpChannel({ skills: true })`, and answers the first open request when a typed reply meets several, posting one prompt at a time on channels without cards. 0.74 again leaves every surface Eveland reads byte-identical, the Workflow set included, and adds experimental schedule collections: `defineDynamicSchedules` from `eve/experimental/schedules` turns a module in `agent/schedules/` into operation tools that create, update, and delete schedules at run time, with Vercel Schedules as the production default provider. Eveland's scheduler only hosts static schedules, so it refuses such a module at build because it declares no static `cron`; use a static `agent/schedules` file instead. Turns started by eve's own scheduler expose their provenance on `ctx.session.schedule`; Eveland dispatches schedules through its own channel, so that field is not set on Eveland. A model call that is retried now settles its tool calls, and a turn that ends removes tool parts it never resolved.
- **Eve 0.76.x (recommended, verified at `0.76.0`)**: 0.75 keeps 0.74's execution model and leaves every surface Eveland reads byte-identical to 0.74.0 — the message stream (v26), hooks, the `eve/client` types, the discovery manifest (v15), the compiled manifest (54), the routes Eveland forwards, the stable workflow names, and the observer's instrumentation pin. The sandbox provider handle's lifecycle hooks are renamed: `onSessionStop()` and `onSessionDelete()` became `onSandboxStop()` and `onSandboxDelete()`, and Eve calls only the new names, so a custom provider built for 0.74 breaks on 0.75 (Eveland rejects custom providers anyway, and the injected `@evelandhq/sandbox-bwrap` 0.5.0 answers both). A durable session's sandbox is now released once the session completes, expires, or fails — through the provider's new optional `onSessionEnd()`, or by resuming and deleting it when the provider has none — as a step inside the session's own run, so a cleanup failure is logged and does not fail the session; bwrap implements `onSessionEnd()` directly and reclaims the session's workspace without resuming it. Sessions can be created with explicitly authorized, session-scoped JSON tool stubs for evals (first-match rules with argument matching and outcome sequences that continue across turns, verified through the new `/eve/v1/session/:sessionId/stubs` route); a caller may supply them only when the channel's authenticator grants `allowToolStubs`, which `evelandIdentity()`, `httpBasic()`, `none()`, and `localDev()` never do, and the Agent Gateway does not classify the stubs route and answers it with 404 inside the session namespace, so tool stubs are unsupported on Eveland — run such evals against `eve dev`. The session checkpoint moved to 13 with them, and Eve rejects a handoff across that boundary; handoff stays inert on Eveland. Schedules are created active (or already completed, for a one-time schedule in the past) and no longer take an initial state; Eveland's scheduler compiles static `agent/schedules` files into its own channel and is unaffected. A subagent's tool approval or session-limit prompt now stays open on the parent until the subagent settles it: a typed reply (`approve`, `continue`) answers it the way it answers a subagent's `ctx.ask()` question, someone else can answer when the subagent's response policy refuses the first responder, and the parent relays the child's `input.resolved`, which Eveland projects as it does for the parent's own requests; an approval answered before a cancelled turn settled is kept rather than asked again, and an approved call the cancellation interrupted gets an interrupted result instead of running twice. A conversation session stays available after a dynamic connection resolver fails, so a later message can retry. 0.75.1 moves the bundled Workflow set to the stable 5.2 family (core 5.2.0, world 5.0.3, world-local 5.1.0) with the same World calls and spec range (see the window baseline); runs context compaction's summary call the way a step runs — streamed, retried with the same policy, and counted toward session usage limits, reported with the turn an automatic compaction ran in, while a manual compaction between turns counts toward session totals only (Eveland keeps taking usage from each model step's own `step.completed`); resolves provider options, web search, and prompt caching from the model actually called rather than its catalog id; and opens a session stream while the tail-index lookup is in flight, reading the durable source at the client's pace. Eve's generated Web Chat app renders `ask_question` prompts with the shadcn `Questionnaire` component; Eveland's Playground renders questions with its own components and is unaffected. 0.76 moves eve's own tools into the `eve` namespace: `load_skill` is now `eve__skill({ name })` (the `load-skill` action carries the skill as `name` and `input.name` instead of `input.skill`, its result is a `load-skill-result` named the same way, the client part's `toolName` is `eve__skill` with the skill in `toolMetadata.eve.name`, and sessions recorded earlier replay with `name` filled from `input.skill`; the `eve/tools/load_skill` export is gone), `task_wait` and `task_cancel` are `eve__task_wait` and `eve__task_cancel`, `final_output` is `eve__reply`, and `connection_search` and `connection_execute` are replaced by `eve__search({ query })` and `eve__tool({ name, input })`, which also find and call tools marked `deferred: true`, agents marked `tool: "deferred"`, and skills marked `deferred: true` (such a skill leaves the system prompt); every connection tool is now named `<connection>__<tool>` in stream events, approvals, hooks, and traces, saved connection approvals reset, `eve__search` never asks the user to sign in (it lists a connection that needs it under the connection's own name, and `eve__tool({ name: "<connection>" })` asks), and an agent with no deferred entries, connections, or skills gets no catalog tools. The `eve` namespace is reserved: a tool, subagent, skill, connection, or extension mount named `eve` or starting with `eve__` fails to build, a connection owns every `<name>__` prefix, dynamic tool keys must be legal tool names, and skill names must be ASCII letters, digits, `_`, and `-` (64 characters at most); nothing Eveland injects uses those names. Evals, approval policies, hooks, and channel code that match the old names must be updated, and a turn held on `task_wait` at upgrade stays held until the next message or a cancel. The `parentCallId` field left `tool-call` actions in `actions.requested` (and the `agent.action.parent_call_id` span attribute); the subagent `parentCallId` on `session.started`, which Eveland's observer reads, is unchanged, so the observer and the session projection need nothing. A new built-in `eve/extensions/git` carries the GitHub work out of `eve/extensions/code` (`git__pr` with the shell's `gh`, `git__gh` with a Connect-brokered `github`; `code({ github })` is deprecated) and runs inside bwrap on Eveland like the code extension. Dynamic schedules gain an `update` operation (timing or complete payload replacement, which makes the updater the creator) that custom schedule providers must implement; Eveland's scheduler hosts static schedules only, as before. `webSearch({ provider: "native" })` uses the model vendor's own search on AI Gateway models, a newer parent accepts create responses from remote agents on 0.66 through 0.68, and the mock authored model calls `eve__skill` and `eve__reply`. The discovery manifest stays at v15 (skill-package refs gain an optional `deferred` flag the projection does not read), the message stream at v26, the session checkpoint at 13, and the bundled Workflow set, the routes, the hooks, the sandbox provider API, and the observer's instrumentation pin are byte-identical to 0.75.1; extension contracts only added versions (`tool` 84, `dynamicTool` 77, `channel` 56, `schedule` 29, `subagent` 33, `connection` 45, `hook` 43, `skill` 3, `dynamicSkill` 35, `dynamicInstructions` 36), so a 0.75 build still loads. For the current latest line, Agent projects should refresh their lockfile and redeploy to receive `0.76.0`.

An npm publication alone does not widen the window. A new minor enters only after changelog and source review plus the complete compatibility matrix; removing an older minor is also an explicit product change.

## Enforcement points

Eveland fails closed when the dependency is missing, outside the window, or cannot be proven compatible during:

- source import and preflight
- build and restart
- cold activation (a Release whose build installed an out-of-window Eve version is refused at activation-request time — terminally, so a workflow run bound to it is dead-lettered once instead of retried after every cold start)
- Playground traffic
- public session create, continue, cancel, and stream
- public session reset
- every other public Agent Gateway request to the selected Deployment, including custom channel routes and webhooks (a dormant out-of-window Deployment answers 409 instead of being woken)
- schedule execution

The diagnostic asks the project owner to upgrade instead of guessing an older protocol. Review the release notes before upgrading either Eve or Eveland in production.
