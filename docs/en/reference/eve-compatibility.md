The Eve dependency declarations a project's `package.json` may carry are: an exact patch inside a supported line (a release candidate such as `1.0.0-rc.2` counts, as an exact version), a `~` range anchored on a supported minor's patch, and the `1.0` / `1.0.x` / `1.0.*` forms. A `^1.x` range spans every later 1.x minor and is refused. A missing Eve dependency, a broad cross-minor range, or any declaration that could resolve outside the window fails closed. The project Overview, Source, and Playground pages show the Eve dependency version of the current deployment's source revision alongside the platform requirement.

The window is a set of verified lines, not "everything at or above the floor": `1.0.x` entered on 2026-11-02, two days after `1.0.0-rc.1` was published, and since `0.83.x` retired on 2026-11-04 it is the only line. The SDK's peer range is `>=1.0.0-0 <2.0.0`; the `-0` comparator is what lets npm accept a 1.0 release candidate. The platform's own peer range is `>=1.0.0-0 <1.1.0`. `0.84.x` through `0.91.x` speak the same v27 session protocol as 1.0 but were skipped, and are rejected with the same upgrade diagnostic as a retired line. A Deployment whose Release was built on a retired line stops being servable as soon as Eveland carries the narrower window: the Agent Gateway answers it with 409, activation refuses it, and the platform settles the workflow runs still parked on it instead of retrying them. Every line in the window speaks the v27 session protocol, so the injected observer, the Session/usage projection, the schedule outcome, the Agent Gateway's route classification, and the Playground's single Eve client all read one vocabulary. Sessions and usage that v26 (Eve 0.83) Deployments already recorded stay readable: session replay, traces, and the usage views keep reading the v26 events Eveland stored. `0.83.x`, `0.81.x`, `0.82.x`, `0.79.x`, `0.80.x`, `0.76.x`, `0.77.x`, `0.78.x`, `0.74.x`, `0.75.x`, `0.68.x`, `0.69.x` through `0.73.x`, `0.62.x`, `0.63.x` through `0.67.x`, `0.59.x` through `0.61.x`, and `0.48.x` stay outside together with `0.58.x` and older; `1.1.x` is not admitted before it has passed the matrix.

The UI marks only the latest supported line, `1.0.x`, in green; unsupported versions, retired 0.83.x included, appear in red and remain blocked.

## Window baseline

Everything the platform once carried for older Eve lines is now the baseline of the whole window, and the pre-0.42 compatibility paths have been removed from Eveland entirely:

- Sessions are addressed only by their ID. Continuation tokens do not exist anywhere in the platform anymore: the token columns, the token-based reset translation, and the `POST /eve/v1/session/reset` token route are gone. Clear, compact, and reset live at `POST /eve/v1/session/:sessionId/{clear,compact,reset}`.
- `localDev()` is process-based and admits nothing under `eve start`; Agents on Eveland must authenticate with `evelandIdentity()`, `httpBasic()`, or OIDC.
- Channel message sends default to `turnPolicy: "steer"`; Eveland's injected scheduler adapter always asks for `"queue"` so a schedule never preempts a turn a person is waiting on.
- Eveland decides where every sandbox runs: it injects its managed bwrap sandbox (`@evelandhq/sandbox-bwrap`) into each Release. 1.0 compiles sandbox modules that export a provider `environment` and a `defineSandbox()` selector (the shape 0.64 introduced), so Eveland keeps an authored module and redirects its `eve/sandbox` imports so that every built-in provider (`DefaultSandbox`, `DockerSandbox`, `VercelSandbox`, `MicrosandboxSandbox`, `JustBashSandbox`) builds the bwrap environment instead (an import of `eve/sandbox/microsandbox`, which 0.83 removed together with that provider, still lands on bwrap): the authored `prepare` and selector still run, and provider-specific options such as images and Dockerfiles are ignored; a slot the project left empty gets a generated module. `eve build` prepares every template and records the provider that prepared it, and Eveland refuses a Release in which any sandbox was prepared by another provider — an environment built in a helper file, a custom provider from `eve/sandbox/provider`, or a sandbox shipped by an Extension. The object-form `defineSandbox({ backend })` module Eveland generated for 0.62.x left with that line. The provider contract is a byte-level connection (`spawn`, `readFile`, `writeFiles`, `removePath`, `stop`, `close`): eve derives the session from it, seeds templates and runs the authored `prepare` itself, `start()` is an upsert keyed by the session id, and a durable session's sandbox is released through the provider's `onSessionEnd()` once the session has completed, expired, or failed. The injected `@evelandhq/sandbox-bwrap` implements `onSessionEnd()` directly, removing the session's workspace and metadata without resuming anything and tolerating a retry, so a finished session's bwrap workspace is reclaimed. The worker refuses to vendor a copy without the connection contract. Because the shim builds the bwrap environment, sessions record their sandbox under `bwrap`, never under the `default` name eve's `DefaultSandbox` records, and eve's lack of a just-bash fallback in production builds does not reach Eveland. Eve's built-in sandboxes run commands with `AI_AGENT=eve` since 0.78; the injected bwrap sandbox does not set it.
- Supported builds emit discovery manifest v15; the projector accepts nothing else (v14, emitted only by 0.45.0, left with the 0.45 line). v15 carries the `memories` list; 0.62.0 stopped writing its optional `instrumentation` module reference without a version bump when flat `agent/instrumentation.ts` stopped being discovered, and Eveland never read that field.
- The session stream speaks **v27** (introduced by 0.84): one commit line per state change holding every fact it produced (`{ at, facts }`), streamed text and tool input as separate progress records, each fact positioned by its line and index instead of an event id (`startIndex` counts lines), and one settled fact per item whose `outcome` says how it ended (`turn.settled`, `session.ended`, `call.settled`, `task.ended`, `interaction.settled`, `delivery.settled`). Provider usage is its own `usage.recorded` fact owned by a model run, and approvals, questions, sign-ins, and budget prompts are one `interaction` answered with `{ interactionId, optionId?, text? }`. The 1.0 `eve/client` reads only v27, and the Dashboard's Playground bundles that one client. Every response carries its version in `x-eve-stream-version`, which Eveland's Playground and Agent Gateway forward verbatim; a custom NDJSON consumer should keep reading it rather than assuming the shape. The stream carries the optional transport lease 0.57 added (`?streamControlVersion=1`: heartbeats, and a `stream.lease-ended` control after 60 idle seconds) and writes `{"$eve":"position"}` markers after skipped lines. The Agent Gateway forwards the query string verbatim and keeps its own 5-second heartbeat.
- Eve's implicit default model is `openai/gpt-6-luna-fast` with high reasoning; pin `model` explicitly to control provider, behavior, and cost.
- Durable delegation and invocation channels are baseline: remote child streams follow through the parent at `GET /eve/v1/session/:parentSessionId/subagents/:callId/:childSessionId/stream`, create-once `operationId` sessions, and `mcpChannel()`'s durable agent tools all ride Eveland's durable Deployment routing boundary. A root also serves every followed descendant at `GET /eve/v1/session/:sessionId/descendants/stream`, which the Agent Gateway pins by the root session like the session stream, and retires a session at `POST /eve/v1/session/:sessionId/end`, which it pins like `reset` (still served as an alias). 0.84 removed `POST /eve/v1/task-input/:token` (it settled approvals without authentication), so a 1.0 Agent answers it with its own 404. Because every supported line speaks these routes, the Agent Gateway maintains no per-operation Eve version floor — the window itself is the gate.
- Frontend `stop()` is gone; cancellation is the durable, hook-owned `cancel()` command. Eveland's Playground awaits it, including the interval before the first event identifies the durable turn, and keeps the stream attached through settlement.
- Workflow runs on storage spec v9, the single orchestrator: since `@evelandhq/workflow-world` 0.30.0 the World declares `mintedSpecVersion(env, { inBandFence: true })` — 9 under eve 1.0.0-rc.3 and later, which ask for it by default (`WORKFLOW_SPEC_VERSION=9`), served by the in-band writer fence spec 9 needs; 8 (hook force-claim) on rc.1 and rc.2, which do not ask, or where a Deployment sets `WORKFLOW_SPEC_VERSION=8`; 6 for a Deployment that sets `WORKFLOW_SEALED_LOG=0`. Releases built with 0.27.0 through 0.29.0 keep their spec-8 runs, Releases built with 0.18.0 through 0.26.x keep their spec-7 (sealed log) runs, and Releases built with 0.17.0 or earlier keep their spec-6 runs, because the platform admits all four generations. 1.0's runtime accepts a World declaring 6 through 9 from rc.3 (6 through 8 on rc.1 and rc.2, which bundle core `5.2.3`, world and errors `5.0.5`, world-local `5.1.2`), and compares only the major and prerelease tag of the World's `@workflow/*` declaration (Eve's own bundled set moved to `5.0.0-beta.53/21/36/45` at 0.61.0, which is what 0.62.0 carries, to `5.0.0-beta.55/22/37/46` at 0.64.0, whose `@workflow/world` adds an optional `invoke` capability that Eveland's World does not declare, and to `5.0.0-beta.56/23/38/47` at 0.66.3, whose `@workflow/world` mints spec 8 — the hook force-claim reader contract, under which another run may take over a hook's token with `createHook({ experimental_force: true })` — to `5.0.0-beta.57/24/39/48` at 0.67.2, which leaves every spec constant where it was and is what 0.68.0 carries, and to the stable `5.0.1` release of the same family at 0.70.2, which leaves every spec constant where it was, only adds optional World members, and is what 0.72.1 carried, and to core `5.1.0` with world, world-local, and errors `5.0.2` at 0.73.0 (0.74.0 and 0.75.0 carry the same set), which keeps the World calls and spec constants and only adds optional members (a stream writer's `release`, an advisory `afterStepBody` mark, a hook's `nodeVersion`), and to the stable 5.2 family at 0.75.1 — core `5.2.0`, world and errors `5.0.3`, world-local `5.1.0` — which again keeps the World calls and spec constants, and to its patch release at 0.83.0 — core `5.2.3`, world and errors `5.0.5`, world-local `5.1.2` — which only adds optional World members (`regionForRunId`, an `inBandFence` capability, queue route registration, delivery-count metadata, an `eventCursor` on event writes) that Eveland's World does not declare; a stable version on either side matches any prerelease of its major), so one World serves the window. The platform injects `@evelandhq/workflow-world@0.31.1` for every new build, which pins the `@workflow/world` 5.1.0 and `@workflow/world-local` 5.2.1 that 1.0.0-rc.5 through rc.8 bundle (0.28.0 pinned the 5.0.5 and 5.1.2 that rc.1 and rc.2 bundle, and 0.27.0 pinned 0.81's 5.0.3 and 5.1.0, with the same World calls), declares `capabilities.atomicStartHook` and implements it — a run is admitted together with a Hook on its start token in one transaction, so a second start on the same token is refused naming the run that owns it, which eve 1.0.0-rc.6 and later require before they start any session (since 0.31.0) — declares `capabilities.inBandFence` and `capabilities.maxConcurrency` and implements both — an orchestrator write whose expected in-band count is stale is refused before it writes anything, a spec 9 run's orchestrator deliveries wait in its run queue one at a time while its step messages keep full parallelism, and every delivery reports `x-vqs-message-delivery-count` (since 0.30.0), declares `capabilities.deploymentAffinity` so eve resumes each session on the Deployment that owns it whatever its Eve version (since eve 0.76.1), declares `capabilities.hookForceClaim` and implements it — a `createHook({ experimental_force: true })` takes a token from a running run stamped 8 or later by writing `hook_disposed` with `forceClaimedBy` into that run's log before re-pointing the token, refuses a running run stamped below 8 with `hook_conflict` and `forceRefusedReason: "victim-spec-version"`, and answers a delivery that resolved the old owner with `HookForceClaimedError` so it follows the token — which eve 0.81.1 and later need to move a session to a fresh run (since eve 0.81.1), and answers the runtime's `resolveData: "skip-step-inputs"` event reads exactly as it answers `"all"`; 0.23.0 through 0.26.x capped the declaration at spec 7 while 0.62.0, whose runtime refused a World above 7 at startup, was in the window, and never took a hook token over. It also delivers held dispatches over Node's core HTTP client so that a step running longer than five minutes is no longer cut off and redelivered by the 300-second deadline of the global `fetch`, addresses a cross-deployment `start()` to the Deployment it names instead of the one that enqueued it, holds a delivery due more than a minute out off its run's queue until it is due (since 0.26.0, so a sleeping session no longer costs every dispatcher claim a row lock), lets a hook wake past a run queue held by a running step so that a cancel aborts the step instead of waiting for it (since 0.26.1), serves eve's dispatcher-driven deliveries unaffected by 0.83's rejection of unauthenticated `/.well-known/workflow/v1/flow` requests, which eve wires only into its own local World, and (since 0.21.0) commits a run and its `run_created` event in one transaction; `@workflow/world-postgres@5.0.0-beta.34` exists only in historical Releases and is never selected for a new build. Older spec-v5 worlds fail the startup guard. The shared World also bounds physical stream storage with snapshot stripping, block packing, checkpoints, and deadline-driven retention.
- Workflow World 0.31.1 fixes a startup race in which an event read can see a concurrently created run without its in-band fence snapshot. When this happens it re-reads the snapshot, then the event page, so Eve receives events with the fence required by spec 9. The storage and dispatch protocol versions stay unchanged. Existing Releases keep their bundled World; rebuild and deploy a new Release to receive the fix.
- MCP channels default to `/eve/v1/mcp` and may declare another `route`; Eveland's path-transparent Agent Gateway preserves either path and the corresponding OAuth protected-resource metadata route.
- Durable tools are declared with `defineWorkflowTool` from `eve/tools` and delegate with `ctx.agent()` — `ctx.agent(name)` returns a session whose `send(message, { outputSchema })` answers with a response whose `result()` resolves the turn; Eve derives the replay-stable invocation identity itself; workflow tools on the parent flow through one ordered inbox where a retried dispatch may start another run, and `defaultTools: false` opts an Agent out of Eve's optional default tools. `experimental.workflow.retention: 0` and `experimental.workflow.modelCallsPerStep` are opt-in Agent options across the window: the retention preference is recorded on the run as the reserved `$retention` attribute, which Eveland's shared World stores but does not enforce, and a larger step batch widens the replay unit after an interruption.
- The `task_update` tool, its child-to-parent progress callbacks, and background tasks are gone across the window: a call holds its turn until it settles (`call.settled`, and `task.ended` for a task).
- The OpenTelemetry agent trace schema is 4 across the window: every activation is an `invoke_agent` span grouped by `gen_ai.conversation.id`, model input is recorded once as `gen_ai.input.messages`, and memory recall/capture emit their own spans and `memory.operation.*` hook events. Eveland's observer and collector mappings key on none of the pre-4 names, but a dashboard built on an Agent's own `otel()` export must target schema 4.
- Extension contracts: 0.84 replaced the per-capability contract epochs with the Eve version an Extension distribution was built with and a distribution generation, and 1.0 rejects an epoch-based manifest with rebuild guidance before loading any extension code. A prebuilt Extension must therefore be rebuilt against the line the project builds on (one built for 0.83 does not load on 1.0); Extensions Eveland injects itself are compiled from source inside each Release and unaffected. Eve's CLI reports usage to Vercel unless `EVE_TELEMETRY_DISABLED` is set; Eveland sets it for every build and deployment it runs.
- Extensions may provide channels, schedules, and namespaced subagents; their full platform scheduling and observer integration is delivered as a separate compatibility follow-up.
- `chatgpt()` is stable with Codex-owned authentication — but ChatGPT subscription models are local-only by design: there is no Codex sign-in inside an Eveland deployment, so an Agent pinned to `chatgpt()` deploys and then fails at run time. Use an AI Gateway or server-authenticated model for deployed Agents.
- `glob` and `grep` are not in the default Agent tool set; an Agent that relies on them must export them from the corresponding tool files by re-exporting the provided definitions from `eve/tools/glob` / `eve/tools/grep` (the `defineGlobTool()` / `defineGrepTool()` factories left the window with 0.44).
- A child agent can share the dispatching parent's live sandbox by exporting `defineParentSandbox()`; such a child cannot also declare managed workspace or skill resources, and Eveland's platform sandbox applies to the parent as usual.

## Supported version lines

- **Eve 1.0.x (recommended, verified at `1.0.0-rc.8`; v27 session protocol)**: eve 1.0 puts its stable APIs under semver (see its stability policy); 1.0.0-rc.1 is byte-identical to 0.91.0 on every surface Eveland reads. 1.0.0-rc.2 (verified on 2026-11-03) keeps every pinned surface — discovery manifest 15, compiled agent manifest 55, checkpoint 18, stream 27, the stable workflow names, and every dependency — and widens two v27 facts: a `call.requested` may be owned by its turn (`owner: { turnId }`), and a `content.completed` may leave out `runId`, with `scope.turnId` naming the turn. The observer, the Session transcript, and the trace place both under their turn. From rc.2, `eve dev` also resolves a string model through `globalThis.AI_SDK_DEFAULT_PROVIDER`, as `eve start` does. 1.0.0-rc.5 (verified on 2026-11-05; rc.3 and rc.4 were reviewed on the way) keeps stream 27 and the session protocol unchanged and moves: discovery manifest 16, which lists an agent's authored sources (and each Extension mount's) in one `sources` array instead of one array per kind — the build summary and the injected scheduler read both 15 and 16, since the window holds releases built on either; compiled agent manifest 56 and checkpoint 19; Nitro 3.0.261103-rc on Rolldown 1.2.16 with srvx 1.0.8, under which a known path answers an unsupported method with 405, and a build fails on a `nitro/storage`, `nitro/kv`, or `nitro/database` import or on an asset import from outside the package; and `eve start`, which now waits 25 seconds instead of 20 before it SIGKILLs the server (the platform's stop timeout clears both). Tools changed for Agent authors: rc.3's code extension drops `code__grep` and `code__worker`, and rc.4 gives every agent a default `edit_file` tool (gate it wherever you gate `write_file`), drops `code__apply_patch`, ends a failed `bash` result with `[exit code: N]`, and backgrounds a command after 60 seconds instead of 30. 1.0.0-rc.6 (verified on 2026-11-06) bundles exactly rc.5's Workflow runtime and keeps every version Eveland pins. A session now claims its channel address as it starts, with an atomic start Hook, so racing first messages to one address reach one session, `create()` and keyed sends answer before the session has booted, and a session accepts commands as soon as it exists. eve refuses to start a session on a World that does not declare `capabilities.atomicStartHook`, which the shared World declares from 0.31.0, so an rc.6 Agent needs a Release built by an Eveland that injects it. A send by session ID to a session that is shutting down gets `409 session_not_active` at once instead of `session_not_ready` retries. For Agent authors, `agentWithModel` is replaced by `agent({ models })` from `eve/tools/agent`, and an `agent.approval` span now covers every wait on a person, sign-ins included. 1.0.0-rc.8 (verified on 2026-11-10; rc.7 was reviewed on the way and never verified) keeps every version Eveland pins and bundles the same Workflow runtime, makes the same World calls and enforces the same World capabilities as rc.6, so the platform changes nothing to host it. Two v27 facts widen: a tool defined with `label: false` marks its calls `hidden: true` on the call's `capability`, and an interaction may carry `waitsOn`; Eveland's Session trace and transcript still list a hidden call. For Agent authors, `eve__task_wait` waits at most 30 minutes when a call omits `timeoutSeconds`, a workflow tool call from a model response that ended early is answered as not run, `decision <model>` spans cover `decide`, automatic model selection and tool approvals, and `eve/vite` adds the `eveVite()` plugin. An Agent still on 0.83 moves by following Eve's own "Upgrade to 1.0" guide; the parts that meet the platform are: (1) **Session events are v27** (see the baseline above). Hooks keep `(event, ctx)` but receive v27 facts, with `ctx.position` and `ctx.view`, and an unhandled hook error now fails the running turn; Eveland's injected observer never throws. (2) **Authoring**: builds reject an `agent.ts` that is not `defineAgent(...)`, a connection that is not `defineMcpClientConnection` / `defineOpenAPIConnection`, and an `agent/sandbox.ts` beside `agent/sandbox/`; `sleep`, `askQuestion`, and `noReply` are exported directly instead of called; durable primitives come from `eve/workflow` and `eve/workflow/api` (a bare `workflow` import fails); `compaction.thresholdPercent` became `compaction.threshold` (a 0–1 fraction); a schedule's prompt is `content` instead of `markdown`, and `send()` resolves a `Delivery` (`sessionId`) instead of a Session, which Eveland's injected scheduler channel reads. `defineChannel` no longer reads `kindHint`; every channel's kind is `channel:<name>` (the HTTP channel is `channel:eve`), and the Session projection classifies triggers by that name. (3) **HTTP**: the eve channel rejects unknown top-level body fields with 400 and takes `answers` instead of `inputResponses`; `reset` became `end` (the old path stays an alias); `GET /eve/v1/info` now answers only operator principals (service, runtime, or a `localDev()` caller), which Eveland never calls; the client rejects redirects by default. (4) **Sandbox**: the provider connection contract keeps 0.83's shape but renames `abortSignal` to `signal` and adds an optional `spawn({ stdin: true })`. The worker injects `@evelandhq/sandbox-bwrap` 0.7.0, which reads both signal names and implements `spawn({ stdin: true })` (a piped stdin whose close sends EOF), stdin included. (5) **Workflow**: rc.5 through rc.8 bundle core 5.4.0 and world 5.1.0, which `@evelandhq/workflow-world` 0.30.0 and 0.31.0 pin (rc.1 and rc.2 bundle core 5.2.3 and world 5.0.5; the World serves both, since eve compares only its major line); the session checkpoint is 19 (18 on rc.1 and rc.2). From rc.3 eve asks for spec 9 runs (`WORKFLOW_SPEC_VERSION=9`), which the shared World serves from 0.30.0 with an in-band writer fence; runs already in flight keep the version they were stamped with. From rc.6 every session starts with an atomic start Hook, which the shared World serves from 0.31.0. The World declares `capabilities.deploymentAffinity`, so eve resumes each session on the Deployment that owns it. (6) **Usage**: provider usage arrives as `usage.recorded` owned by a model run; Eveland stores one usage row per run (`run_key`), counts only run- and change-owned records (a call-owned record re-reports a child's own spend), and, because v27 fills a missing token count with zero, treats a model run with no record as missing usage. (7) **Builds**: dynamic models read context windows from the AI Gateway catalog recorded at build time, so a build without network access needs the catalog cached or `modelContextWindowTokens` set; `eve start` no longer passes `CI` or `NITRO_UNIX_SOCKET` to the server. (8) **The `eveland` SDK**: SDK releases before 0.21.0 declare an eve peer below 1.0, so npm refuses to install them beside eve 1.0; an Agent that imports `eveland` moves to 1.0 together with `eveland@^0.21.0`, the first release whose peer accepts 1.0. The starter template (what `eveland init` copies and the built-in Agent deploys) pins `1.0.0-rc.8` and `eveland@^0.21.0`. For the current latest line, Agent projects should refresh their lockfile and redeploy to receive `1.0.0-rc.8`.

An npm publication alone does not widen the window. A new minor enters only after changelog and source review plus the complete compatibility matrix; removing an older minor is also an explicit product change.

## Enforcement points

Eveland fails closed when the dependency is missing, outside the window, or cannot be proven compatible during:

- source import and preflight
- build and restart
- cold activation (a Release whose build installed an out-of-window Eve version is refused at activation-request time — terminally, so a workflow run bound to it is dead-lettered once instead of retried after every cold start)
- Playground traffic
- public session create, continue, cancel, and stream
- public session reset
- every other public Agent Gateway request to the selected Deployment, including custom channel routes and webhooks (a dormant out-of-window Deployment answers 409 instead of being woken)
- schedule execution

The diagnostic asks the project owner to upgrade instead of guessing an older protocol. Review the release notes before upgrading either Eve or Eveland in production.

## Behavior the Model Gateway relies on

The [Model Gateway](/docs/reference/model-gateway) depends on eve behavior that no eve API promises, so widening the window also reruns `pnpm --filter @evelandhq/worker smoke:model-gateway` (with `EVE_VERSION` set to the candidate) against a real install:

- `eve build` trusts a seeded `.eve/cache/model-catalog.json` (`kind: "eve-model-catalog-cache"`, `version: 2`) whose `fetchedAt` is under five minutes old;
- an instrumentation's `setup` runs after every instrumentation module has loaded, and `eve start` resolves a string model ID through `globalThis.AI_SDK_DEFAULT_PROVIDER`;
- eve records `providerMetadata.gateway.cost` as `usage.recorded` `costUsd`;
- `eve dev` honors the default provider too (from 1.0.0-rc.2; vercel/eve#5787).
