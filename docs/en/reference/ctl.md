`eveland-ctl` operates the platform installation on **this machine**: starting and stopping the platform processes, checking the machine's health, and (as the surface grows) installing and upgrading. It is the counterpart of `eveland`, the agent author's client — the two binaries cross-reference each other on unknown commands. Like the CLI, it ships with the source tree (`packages/ctl`), runs directly from TypeScript sources under Node ≥ 24's type stripping, and is never published to npm: the ctl always versions with the exact source tree it manages. From a checkout, run it as `pnpm eveland-ctl <command>`.

## Install

```bash
curl -fsSL https://eveland.ai/install.sh | bash
```

Every character of the one-liner is deliberate: `-f` keeps an error page from being executed as a script, `-sS` is silent but preserves errors, `-L` follows redirects, and the scheme is explicit `https://` (curl defaults a bare host to plaintext http). The script itself is served 200-direct from the static site with a short cache and a `install.sh.sha256` sidecar; `EVELAND_VERSION=vX.Y.Z` pins a release, `EVELAND_REPO_URL` redirects the clone (CI installs from a local checkout this way).

The installer is deliberately dumb (bounded at 500 lines, enforced by test): detect OS/arch, resolve Node, clone the source blobless at the newest exact `vX.Y.Z` tag (a pre-release that sorts above it is never chosen), `pnpm install`, lay down the two shims, hand off to `eveland-ctl start`. On a fresh **Linux host as root with apt**, it first installs whatever of `git`/`curl`/Docker/Compose v2 is missing (enabling the Docker daemon; `docker compose version` is a hard check everywhere). Docker and Compose always come from **one package family**: a host without Docker gets Ubuntu's `docker.io` + `docker-compose-v2`; a Docker CE host missing Compose gets `docker-compose-plugin` (Ubuntu's `docker-compose-v2` depends on `docker.io`, which conflicts with CE's `containerd.io`); a Docker of unknown provenance is told which package to add rather than guessed at. The manual Linux first boot applies the same rule, and a host without apt is verified for `docker compose` too _before_ the hard prerequisite checks, so the one-liner genuinely works on a bare Ubuntu — an existing Docker CE is never touched, and the install-smoke CI removes the runner's pre-baked Docker to prove it; elsewhere (macOS, non-root) a missing git or Docker is a clear failure with the install hint. Everything smart lives in the ctl — re-running the installer against a completed install just forwards to `eveland-ctl update` — unless the pinned Node no longer runs (`nvm uninstall`), in which case the re-run **repairs** the pin and regenerates the shims in place without moving the checkout, even with `EVELAND_VERSION` set (the shims exec that very interpreter, so forwarding to them would fail instantly). The repair re-resolves Node, rewrites the pin through a `0600` temp copy swapped in atomically and cleaned by the failure trap, writes the shims, **stops** the platform before reinstalling dependencies under the new interpreter, and then **restores service first** — a systemd-form install goes through `install --systemd` again so the units and the system-PATH toolchain (node links and a working pnpm **at the repo's pinned version** — via corepack when the interpreter ships it, otherwise the pnpm in its own bin dir or one installed there with its npm; any other runnable pnpm does not satisfy the pin) pick up the new interpreter, anything else through `start` — and only then forwards to `eveland-ctl update` exactly like any other re-run (newest release, or the requested version): update's own no-op and refusal paths never start anything, so going there directly could have left the platform stopped. `--no-start` after a repair says loudly that the platform stays stopped and names a requested version it therefore did not apply; a plain re-run with `--no-start` touches nothing at all (update would restart the platform) and prints the update command instead; a failed dependency install never suggests starting on top of it. It prints its full install plan before touching anything; `--dry-run` stops there, `--no-prompt` (or a `/dev/tty` that cannot actually be opened — existence checks lie inside `docker build`) takes every default, and the whole run is teed to `logs/install.log`.

**Node resolution is three tiers**, and the result is pinned once as `EVELAND_NODE` (an absolute path to the real binary — PATH never participates again): (1) a PATH `node` ≥ 24, probed **after sourcing nvm** because `curl | bash` runs in a subshell that never saw nvm's PATH injection; (2) with nvm present, an interactive offer to `nvm install 24` (non-interactive runs skip this rather than mutate the user's nvm); (3) a checksummed official tarball unpacked into `EVELAND_HOME/node` — zero sudo, hermetic. pnpm comes from corepack pinned by the repo's `packageManager`, with an `npm i -g pnpm@<pin>` fallback into the managed prefix for the day corepack leaves Node — and the installer verifies the **exact** pinned version resolves before going on; a shell's other pnpm never passes. The shims are real files (not symlinks) that put the pinned interpreter's bin dir at the head of `PATH` — with a private Node that is the only place pnpm lives, and a fresh shell has never seen it; the supervisor prepends the same dir for every child — installed verify-then-commit: probe `--version` on a temp copy, back up the old bin, then move into place. A broken source dir is moved aside with a timestamp, never deleted.

## The appliance root

`EVELAND_HOME` names the appliance root: `~/.eveland` on macOS, `/opt/eveland` on Linux, overridable via the environment. Its layout separates what an upgrade replaces from what an upgrade must survive:

| Path               | Role                                                                                                                                   |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| `source/`          | The git checkout, always on a release tag; replaced by upgrades                                                                        |
| `etc/eveland.env`  | The installation's configuration; the single source every supervised process receives                                                  |
| `etc/install.json` | Install metadata (method, time, OS mode). Lives in `etc/`, never `data/` — `data/` is bind-mounted into containers and would shadow it |
| `data/`            | `EVELAND_DATA_DIR` as an absolute path; Postgres bind mounts live inside                                                               |
| `logs/`            | Install and per-process logs                                                                                                           |
| `run/`             | Supervisor pidfile and state snapshot (advisory; liveness is always re-verified)                                                       |
| `backups/`         | `pg_dump` snapshots taken before each upgrade                                                                                          |

A development checkout needs none of this: without `etc/eveland.env`, the ctl falls back to the repository's own `.env` and supervises the checkout in place.

## Commands

| Command                                                        | Behavior                                                                                                                                                                                                                                                                                                                    |
| -------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `eveland-ctl start [--foreground] [--skip-infra]`              | Bring up the infra containers (the OTLP Collector, plus the bundled Postgres where the installation has one), then the five platform processes. Idempotent: a running platform short-circuits. `--foreground` keeps the ctl supervisor attached (Ctrl-C stops); `--skip-infra` assumes the containers are managed elsewhere |
| `eveland-ctl stop`                                             | Stop the platform — the units in reverse start order on the systemd form, or SIGTERM to the supervisor and a confirmed process-tree exit (escalating to SIGKILL). Infra containers keep running                                                                                                                             |
| `eveland-ctl restart`                                          | `stop`, then `start`                                                                                                                                                                                                                                                                                                        |
| `eveland-ctl status`                                           | The supervisor's process view joined with live health probes and infra reachability; exit 0 only when everything is healthy                                                                                                                                                                                                 |
| `eveland-ctl logs [process] [-f] [--tail N]`                   | The platform processes' own stdout/stderr from `logs/`. A deployed project's logs belong to `eveland logs`                                                                                                                                                                                                                  |
| `eveland-ctl doctor`                                           | The full machine checklist (below); collects every problem in one pass and exits 1 on any failure                                                                                                                                                                                                                           |
| `eveland-ctl update [--version <tag>] [--yes] [--skip-backup]` | Upgrade the appliance to a release tag (below)                                                                                                                                                                                                                                                                              |
| `eveland-ctl install --systemd`                                | Linux only, root only: promote the install to systemd system services (below)                                                                                                                                                                                                                                               |

## First boot

`start` is idempotent in the larger sense too: on a machine with no completed installation (no `etc/eveland.env`, or `etc/install.json` not marked complete) it runs the first-boot bootstrap before starting. A development checkout with its own `.env` is never bootstrapped.

The bootstrap asks only the decide-per-install questions — public origin (default `http://localhost:17300`) and admin email — and probes the shell for an existing `ANTHROPIC_API_KEY`/`OPENAI_API_KEY` to offer for the built-in agent. The admin password is never prompted and never printed (either would land in the teed install log): it is always generated — or taken from an `EVELAND_ADMIN_PASSWORD` already in the environment — and lives only in the `0600` `etc/eveland.env`, which the bootstrap output points at. Everything else is generated (`APP_SECRET_KEY`, `BETTER_AUTH_SECRET`, gateway/OTLP/scheduler secrets — all CSPRNG, scheduler secrets independent as the worker preflight requires) or derived per OS (Docker-shaped `host.docker.internal` addresses on macOS, loopback on Linux; `EVELAND_RUNTIME` docker vs systemd). The dispatcher activation token is rendered equal to the gateway service token because the API validates activations against exactly that credential. The rendered `etc/eveland.env` is `0600` and written **once** — a resumed bootstrap reuses it verbatim, so secrets are minted exactly once. `--no-prompt` (or no TTY) takes every default; `NODE_ENV=production` means placeholder secrets can never work. Release identity is **derived from the checkout, never stamped**: `EVELAND_REVISION` is the 12-character short SHA the upgrade contract documents (`git rev-parse --short=12 HEAD`), and `EVELAND_RELEASE_CHANNEL` is `stable` only on an exact `vX.Y.Z` tag (`prerelease` on a `vX.Y.Z-…` tag, `edge` for any other revision) — pinned at first boot and refreshed by `update`.

After rendering, the bootstrap prepares and starts the platform (the admin account is seeded by the API itself at boot from `EVELAND_ADMIN_*`). On **Linux as root** it first provisions the documented host contract itself — the sandbox toolchain via apt, the bwrap AppArmor profile, `/workspace`, the `eveland-app`/`eveland-build` service users, and the pinned node/pnpm on the system PATH — and then lands **directly on the production form** described under "The systemd production form" below: day-one production, no intermediate supervisor. On macOS (and Linux `--foreground`) it builds the Dashboard if needed, brings up the infra containers, waits for Postgres, applies migrations, and starts the ctl supervisor. Once the processes are ready it performs the **implicit CLI login**: the same RFC 8628 device flow `eveland login` runs — same seeded client, same `deploy observe` scopes, a normal revocable token — but approved headlessly over the loopback API with the admin session the bootstrap just created, and stored in the CLI's own credential store (`~/.config/eveland/credentials/`). The golden path `eveland init` → `eveland deploy` therefore never hits a login wall. A failed login is a warning, not a failed start (`eveland login` recovers it).

With the token in hand, the bootstrap seeds the **built-in agent** (`stella`): it shells out to the real `eveland` CLI — `eveland deploy templates/starter-agent --name stella` — so seeding walks the exact golden path a user's first deploy walks (preflight, upload, streamed build logs, promote) and cannot silently diverge from it. Model keys collected earlier land in the agent's project environment via `eveland env set KEY --stdin` afterwards — the value crosses stdin, never argv, which every local user can read through `ps` while the request runs. Seeding (or login) failures warn, print the manual recovery command, and record `seedCompleted: false` in `install.json`: every later `eveland-ctl start` retries the seeding until it sticks — including a `start` against an already-running platform, which short-circuits everything else but not this — and a first boot that died after the supervisor came up is likewise _finished_ (login, seed, completion) by the next `start` rather than swallowed by "already running"; the platform is fully usable without the built-in agent meanwhile. Finally the browser opens on the platform origin (headless installs just print the URL).

## Supervision

macOS has no systemd, so `start` daemonizes one supervisor that owns the five platform processes — Agent Gateway, Platform API, Dashboard, Worker, and the workflow dispatcher (the docs site is dev-only and never supervised). A crashed child restarts with exponential backoff (1 s doubling to a 30 s cap; a child that stays up a minute resets its streak) — and only after its whole process group is confirmed empty (SIGTERM, then SIGKILL): a `pnpm`/`tsx` wrapper that dies while the real server it spawned lingers must not be joined by a second copy fighting for the same port, and a group that survives even SIGKILL is never respawned into — the child stays in backoff and the reaper retries at the cap. Ownership itself is claimed atomically before any child spawns: the whole check-and-publish runs under a mutex directory (`mkdir` is atomic and exclusive) whose owner file names the holder by pid **and** start-time identity; a mutex is never broken by age, only when its holder is definitively dead or its pid was recycled by another process, by moving it aside atomically and re-checking whose it was (a waiter always outlasts the owner-less grace, so a crash remnant can never block every start for good), and every holder re-validates that the mutex still carries its own token immediately before publishing. The pid record is written completely and renamed into place, so no contender can ever read, misjudge or remove another's record at any point of the protocol. Two racing `start`s cannot each end up owning five processes. A liveness probe that cannot run (`ps` missing or failing) is an error, never "exited": no lock is broken and no record reclaimed on an unknown. Each child's output lands in `logs/<name>.log`, and one SIGTERM to the supervisor stops the set in order. Four of the five run their TypeScript sources directly (`tsx`), exactly as the systemd units do; only the Dashboard needs its production build (`pnpm --filter @evelandhq/web build`) before `start` will proceed. On Linux the same supervisor backs `--foreground`; installing the platform as systemd units is the `install --systemd` verb, which lands with `update`.

Configuration reaches every child the same way: the parent environment for PATH-style plumbing with the platform env file laid over it, so the file — not the invoking shell — is authoritative. `NODE_ENV` comes from the file too: the platform's fail-closed rule (dev fallback secrets only under an explicit `NODE_ENV=development`) applies unchanged.

## Update

`eveland-ctl update` moves the appliance's source checkout **forward** to a newer release tag (default: the newest exact `vX.Y.Z` tag — a pre-release sorting above it is skipped; `--version` pins one — a strictly newer `vX.Y.Z`). An older tag, a pre-release, or a bare revision is refused before anything moves: migrations are not reversed automatically, and the upgrade contract only vouches for forward moves — a rollback follows the release's rollback notes, never a casual `--version`. The platform's collected scars are productized as steps. It refuses a development checkout (that's `git pull`), and the whole state machine is serialized by `run/update.lock` — a second `update` while one runs (or races a resume) is refused, naming the running pid — while `start` takes the **same** lock for its whole run (so the two exclude each other outright, with no look-then-act window) and refuses while a live `update` holds it or an update is recorded (only the update's own phase 2 may start it). The order matters:

1. **Breaking changes first**: the target's `CHANGELOG.md` (read via `git show` — the running checkout has never heard of the new version) is scanned for every `⚠ BREAKING CHANGES` block between here and there, and the operator must confirm (`--yes` accepts non-interactively; an unconfirmed update aborts before anything moves).
2. **Backup**: `pg_dump` into `backups/`, named after the version it protects — written to a `.partial` file, fsync'd, and only then renamed, so a backup exists complete or not at all (a failed, interrupted or empty dump leaves nothing that could pass for one; the file is `0600`). A failed dump refuses to proceed (`--skip-backup` is the escape hatch).
3. **Stop before anything moves**: the whole platform stops before the checkout — replacing sources, `node_modules`, and the Dashboard build under running processes would let them restart from a half-updated tree. From here, any failure leaves the platform deliberately stopped and prints one explicit recovery plan: retry, or roll back **per the release's rollback notes** (the "Rollback boundary" in the operations upgrade guide) — checking out the previous tag is offered only for the case those notes declare compatible with the migrations already applied; otherwise the plan is to restore the named database backup first. It never claims migrations are forward-compatible. The in-flight update is recorded (`run/update-pending.json`, written before the checkout moves, carrying the source version, target, backup, the stash **commit** and the pre-update eve pin) and **re-running `update` resumes it** from that record — a checkout already reporting the target version is never mistaken for "already up to date" over a stopped platform, the record is cleared only after the last recovery action (so nothing an interrupted run still owed can be lost with it), the eve-window warning still fires on a resumed completion, and the stash is restored by its recorded sha — or, if the sha could not be recorded, by its unique name in the stash list — never as "whatever is newest".
4. **Dirty-tree handling**: an unmerged index is reset first (stash chokes on it); real local changes go into a **named** stash (`eveland-ctl-update-<ts>`) offered back — interactively — into the updated tree right after the checkout, _before_ `pnpm install` (local changes may touch the manifests it reads) and before anything runs from it; a restore that does not apply cleanly is a failure gate (the stash is kept, the conflicts are yours to resolve or discard, and the re-run resumes there), and the record remembers a restored stash so a resume does not look for it again. Ignored files are untouched.
5. Checkout → `pnpm install --frozen-lockfile`, and then phase 1 — still the **old** code — hands over to the **new checkout's own** `eveland-ctl` (the hidden `_finish-update`), because the old version must not decide the new version's artifacts or start sequence. The new ctl refreshes the release identity; on the systemd form it regenerates and reloads its own artifacts (the units, the per-service env files, the Compose overlay) so a topology or permission fix actually reaches installed machines, otherwise it builds the Dashboard; then `db:migrate` and start (with the normal readiness gate). A start that fails lands in the same recovery plan.
6. **Eve-window detection**: if the supported eve window moved with the update (the starter template's pin compared between the two _commits_, never read from a working tree a restored stash may have edited), the ctl warns loudly that Releases built against the old window attest as unknown and dead-letter their schedules until every project is rebuilt and promoted.
7. The pinned `EVELAND_NODE` is probed after restart — an interpreter silently removed by `nvm uninstall` gets an explicit re-run-the-installer instruction instead of a mystery.

Re-running the public installer against a completed install forwards here.

## The systemd production form

On Linux the platform runs in the **documented production topology**, orchestrated by the ctl instead of by hand — this is the first-boot default as root, and `eveland-ctl install --systemd` promotes an older or `--foreground` install onto it:

- **One unit per platform process**, all five, rendered from the same `PLATFORM_PROCESSES` table the macOS supervisor runs — a unit and a supervised child cannot drift apart, and neither goes through `pnpm exec` (corepack's shim wants a writable HOME cache no unit environment guarantees).
- **The unit is the privilege boundary, not an image — and every unit has its own uid.** `eveland-api` runs as `eveland-platform`, `eveland-web` as `eveland-web`, and `eveland-gateway` as a `DynamicUser` because the public front door owns no file that outlives a restart. Each gets `ProtectSystem=strict` over a read-only checkout, `ProtectProc=invisible`, and an explicit `ReadWritePaths`: the data dir for the API, `apps/web/.next` for the Dashboard, nothing at all for the front door. The separation is what makes the per-service environment files mean anything — same-uid processes read each other's `/proc/<pid>/environ`, so one shared "platform" user would have handed a compromised front door the API's `APP_SECRET_KEY`. `eveland-worker` is `User=root` on purpose — it drives `systemd-run`/`systemctl`/`chown`, which is how every deployed Agent gets its own unprivileged `DynamicUser` — and `eveland-workflow-dispatcher` is `DynamicUser=yes` with crash-loop caps. This is strictly stronger than the containerized form it replaced, where each service was container root with the whole host source tree bind-mounted in.
- **Each unit reads its own env file**, re-rendered from `etc/eveland.env` on **every start** so an operator edit takes effect on the next restart rather than the next install. The API and the worker get the whole configuration (both are trust roots by design, and narrowing them would silently drop whatever an operator added by hand); the public Agent Gateway, the Dashboard and the dispatcher get narrowed allowlists that never carry the admin password, `APP_SECRET_KEY`, `BETTER_AUTH_SECRET`, model keys, or the scheduler secrets.
- **Docker keeps the Collector** (stateless, and the Docker runtime attaches it to every Agent's telemetry network) **and the bundled database** where the installation has one. The Collector reaches the host-native API through `host.docker.internal`, where the API binds a second listener restricted to health, Collector Observation, Agent JWKS, and Scheduler Channel paths; the ctl re-detects that address on every start, because Docker renumbers its bridge on its own schedule. A unit that reboots onto a renumbered bridge cannot re-detect it, so the API treats that listener's bind failure as a degraded Observation path — logged as `eveland.api.docker_bridge_unavailable`, fixed by one `eveland-ctl start` — rather than taking the whole API down with it.
- **Unattended boot is gated on a marker, not on `systemctl enable`.** Every unit carries `ConditionPathExists=<root>/run/host-units-armed`. The ctl writes that file immediately before it starts the units — after the Dashboard is built and the schema migrated — and removes it before an update moves the checkout the units point at. Reboot inside either window and systemd _skips_ the units (`systemctl status` says so and names the path) instead of running new code against an old schema; re-running `eveland-ctl start` or `eveland-ctl update` finishes the remaining steps and re-arms.
- **Ownership is reconciled on every start**, not once at install: `apps/web/.next` to the Dashboard user, `<dataDir>/uploads` to the API user, and `<dataDir>/diagnostics` to `root:eveland-platform` `2750` — the whole file-level contract between the root worker and the unprivileged services, and the reason the worker's configuration snapshot is readable by the API without being world-readable.

From then on `start`/`stop`/`restart`/`status` manage the units (the systemd fast path applies only to a _completed_ install: a first boot interrupted after the units went in resumes the bootstrap on the next `start`), and `logs` reads journald (`-f` points at `journalctl` directly). The platform restarts with the machine.

## Doctor

Each check maps to a concrete incident class this platform has actually hit:

- **os / node / pnpm / docker / unzip** — the base toolchain, including Info-ZIP `unzip` (zip source import shells out to `unzip -Z1`, which BusyBox lacks).
- **pinned-node** — an appliance's `EVELAND_NODE` interpreter still runs (`nvm uninstall` silently breaks it).
- **config / node-env / placeholder-secrets** — the env file exists, required values are present, an unset `NODE_ENV` gets the fails-closed warning, and `eveland-dev-*` placeholders outside development fail.
- **ports** — with the platform down, a foreign listener on the fixed platform block means the next start will collide.
- **loopback-exposure** — API, Dashboard, and Postgres must not be reachable on non-loopback addresses; Postgres ships well-known default credentials.
- **proxy-env** — set proxy variables get a warning: an unreachable proxy breaks installs and builds in ways that masquerade as network flakiness.
- **sharp-libvips** — a global Homebrew libvips without `SHARP_IGNORE_GLOBAL_LIBVIPS=1` breaks a fresh install's sharp build on macOS.
- **disk / web-build** — free space thresholds and the Dashboard production build.
- **postgres** — reachable is not trusted: doctor connects with the configured `DATABASE_URL` and reads the migration journal, so a foreign Postgres answering on the platform port (the Lima port-forward hijack) is distinguished from "ours but unmigrated". Only the address is ever printed; a DSN carries a password.
- **pg_dump** — only for an installation on its own PostgreSQL, where `update` takes its pre-upgrade backup from the host. Better a finding than a failure halfway through an upgrade.
- **platform** — with the supervisor up, the Agent Gateway and Platform API health endpoints must answer.
